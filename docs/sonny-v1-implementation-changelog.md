## Feature Branch Checkpoint Workflow (v1, retired 2026-08-02)

Each roadmap row below is one feature branch, but a feature branch should be implemented as a sequence of small, reviewable checkpoints on that same branch. A checkpoint should map to one migrated capability, subfeature, or similarly coherent leg of the branch.

Checkpoint workflow:

1. Plan the full branch scope before editing.
2. Implement one checkpoint on the feature branch.
3. Run the relevant tests for that checkpoint.
4. Report the diff and test results to the user.
5. Wait for the user's manual review/testing and explicit approval before committing or pushing that checkpoint.
6. Continue on the same feature branch for the next checkpoint.
7. When all checkpoints for the branch are complete, run the full required test pass, fill this changelog entry, append the next-chat kickoff prompt, and send the branch for cross-agent review before merge to `main`.

Do not batch an entire feature branch into one large unreviewed implementation. Do not create extra branches for every checkpoint unless this roadmap is explicitly updated. Never commit, push, merge, or open/modify a PR without explicit user approval.

- **Branch 10 (`feature/routine-scheduling`)** was split out as its own branch rather than folded into branch 9, specifically because it surfaces a real, unresolved tension with Sonny's own existing safety principles — not something found via competitive research, but via cross-referencing Sonny's own docs against each other. A scheduled routine runs unattended, but tier 2+ actions elsewhere in the product require a human present to approve, and Power Mode explicitly forbids unattended sessions.

  **Resolved 2026-07-15, during the same UI/UX wireframe-fidelity design audit (implementation #3/Prompt B):** an explicit per-routine "unattended trust" opt-in, with silent-skip-and-notify as a hard backstop for tier-3+ steps only — tier-3+ never becomes unattended-eligible regardless of the opt-in, no matter what the toggle says. Rejected: tier-gating at save time (block scheduling unless every step is tier 0/1) — too weak to ship as a real feature, since the routine-defining examples people actually want (save routine, create a workspace, the zip-files example) are tier 2 by default per branch 2's entry above; and queue-for-approval-via-notification (pause and notify at the first tier-2+ step, resume on tap) — functionally reduces to "notify me it's ready, I'll finish it myself," undercutting the actual point of scheduling given how common tier-2 steps are.

  **A finding surfaced during the same audit, confirmed directly against the code and load-bearing for why the per-routine opt-in is the right shape rather than a blanket auto-run policy:** running a saved routine is *itself* tier 2 by default, independent of its steps' tiers. `RunRoutineCapabilityAdapter.defaultRiskTier` is `.tier2` (`Sources/MacAgentCore/RunRoutineCapabilityAdapter.swift:27`), and `assessRisk(plan:context:)` combines it with the nested plan's tier via `highestTier(metadata.defaultRiskTier, nested.defaultTier)` (line 44) — a floor, not a default that nested tier-0/1 steps can lower. So even a routine composed entirely of tier-0/1 steps still hits tier-2 gating today just from the act of running it. This means the real kickoff question was never only "what happens to tier-2+ *steps*" — it's whether a scheduled trigger gets an explicit, deliberately-designed exception to the outer routine-level tier-2 gate that a manual click keeps. That exception is exactly what the per-routine opt-in is: a routine owner explicitly consents, per-routine, to let that outer gate (and any tier-2 step gates) be bypassed unattended; tier-3+ is carved out as never-bypassable regardless of the toggle.

  **Implementation-level open item, not yet resolved, for whoever actually builds this:** the opt-in needs a new concept in `RiskApprovalPolicy`/`AgentRunner` (a per-routine override), not just UI — read both closely before committing to a specific mechanism, since this audit reasoned from this changelog's own description of the tier model, not a fresh implementation-level read of the current approval-gating code.

**Cross-feature decisions, recorded because both read as correct in isolation and wrong in sequence.**

**1. A scheduled run is excluded from the follow-up-correction context, and from retry, and from every other property that describes "your last task."**

The interaction: the user runs "zip my desktop files", their 9am routine fires a minute later, they type "use ~/Downloads instead" — and the correction lands on the routine. It is internally consistent (the scheduled run genuinely *was* the last task) but a silent redirect caused by something the user did not initiate is a different thing from correcting your own last action, and nothing in the phrasing reveals that a background event moved the target.

Decided: exclude. `performScheduledRun` does not call `recordPriorTaskContext` and does not touch `lastCommand`. Two reasons, and the second is the stronger one: a routine's steps are *saved and fixed*, so there is no command text for a correction to rewrite — correcting a scheduled routine run is not merely confusing, it is not a meaningful operation. The cost named against this option (you cannot follow up on a failed scheduled run) is therefore largely theoretical; the answer to a broken routine is to edit the routine.

`lastCommand` and `priorTaskContext` move together because `lastCommand` also feeds `hasRetryableCommand`/`retryLastCommand()`. Proven by re-introducing the old behavior: the widget's Retry button then produced "Approval needed before Sonny can act." for a routine instead of re-running the user's own calculation.

**The same review found a worse instance of the same class.** `performScheduledRun` was also clearing `errorMessage`, `finalSummary`, `suggestions`, `plan`, `stepStatuses`, `preparedRun` and the usage summary — so a background run silently erased an unresolved error, or an "open the file" suggestion the user had not acted on yet. Fixed under one principle rather than case by case: **an unattended run must not mutate any state that describes the user's own last task.** `isRunning` and `activeTaskOrigin` are the only exceptions, both needed during the run for re-entrancy and widget gating, and origin is restored on the way out. A scheduled run's entire output is `scheduledRunNotice`, task history, and the routine's run history. `runningCommandDisplayText` reads a separate `scheduledRunDisplayCommand` so Command Center's running indicator still has a label without claiming `lastCommand`.

Consequence worth stating: scheduled-run token usage is no longer reset/published into `taskUsageSummary`, so it is not separately metered today. Accurate per-run metering is branch 13's territory; under-reporting it is preferable to misattributing it to the user's next task.

**2. `scheduledRunNotice` persists until dismissed rather than clearing on the user's next task.**

The premise of the whole feature is that the user was not watching when the run happened, which makes their next action the moment they are *most* likely to be about to read it — clearing it exactly then would defeat the point. It has an explicit Dismiss control, and this matches `localStorageNotice`, which is already not cleared by task starts. A newer scheduled run overwrites an older notice, which is correct: the recent one is the one that matters.

Both behaviors are pinned by tests in `Tests/MacAgentTests/ScheduledRoutineRunTests.swift`, each verified by re-introducing the old behavior and watching them fail.

**`show()` and "focus the composer" are two different halves, and only one of them lives in AppKit.** This is the whole bug. `FloatingWidgetWindowController.show()` does `orderFrontRegardless()` + `makeKey()` — it has no way to reach `pillFocused`, which is a `@FocusState` private to `FloatingWidgetView`. Any future entry point that wants the widget must bump the counter; reaching for `widgetController.show()` re-creates this bug by construction.

**The Combine sink is synchronous, the SwiftUI `onChange` is not — and that ordering is load-bearing for push-to-talk.** `@Published` publishes in `willSet`, so `viewModel.widgetPresentationRequest += 1` runs `observeWidgetPresentationRequests()`'s sink (and therefore `show()`) inline, before the next statement. That preserves the hotkey's original "front the panel, then start recording" order exactly. `FloatingWidgetView`'s `onChange` lands later, on SwiftUI's next render pass — which is the right order anyway: focus set after the panel is key is what makes focus stick.

**The new signature is the protocol *requirement*, and the old one is the extension — deliberately that way round.** `BrowserOpening` now requires `open(_ url: URL, using browser: MacApp?)`, with `open(_ url: URL)` as a protocol-extension shorthand forwarding `nil`. **Browser recognition keys on bundle identifier, not display name.** `MacAppCatalog.resolve` already collapses aliases down to one canonical `MacApp` before recognition ever runs — "Google Chrome" and "Chrome" both land on `com.google.Chrome` — so matching the resolved app's bundle identifier means one source of truth instead of two that can disagree. `WorkspaceBrowserCatalog.browserBundleIdentifiers` also lists Arc, Firefox and Edge, which `MacAppCatalog.default` does not carry yet: adding one of those to the allowlist should make it browser-aware in that same edit, with no second place to remember to update. Architectural decisions / pitfalls discovered (required, write "none" if true):

**The correct segmentation for assessment is "mirror the executor's dispatch", not "always call `segmentPlans`".** `segmentPlans(in:)` splits any plan, but `preview`/`execute` only use it for `.chain`; a non-chain multi-step plan (`[scan, zip]`, the HN preset) is deliberately handed to one adapter whole because the adapter reads across those steps. The invariant worth stating: **assessment must see exactly the units execution sees — no more and no fewer.** That is also why `shouldChainWhenRepeated` did not need to change (SONNY-29's stop-and-report trigger): for the workflows it excludes, execution and assessment both stop at the first occurrence, so nothing is written unassessed.

**`WebResearchMarkdownCapabilityAdapter`'s both-kinds branch is deliberately kept although segmentation makes it unreachable from the executor.** `outputURLsForRiskAssessment` now checks the preset output *and* the research output instead of answering `isHackerNewsPreset` first and returning one of them. Once chains are segmented, no caller hands this adapter a plan carrying both kinds (`.webToMarkdown` maps to a different `Workflow`, so any plan holding both is a chain, and `segmentPlans` never absorbs a `.webToMarkdown` step into the preset's segment). It is kept because a future change to how segments are cut would otherwise quietly restore the under-assessment. **Honest limitation: this branch is therefore not pinned by a test** — mutation-checking it (restoring the either/or) leaves the whole suite green, and only reverting it *together with* segmentation turns `webResearchSegmentOfAHackerNewsChainIsAssessedForItsOwnCollision` red. Pinning it directly needs a `CapabilityExecutionContext` built in a test, which nothing in this suite does today. `resolveDefaultOutputs`'s equivalent fix *is* reachable and *is* pinned, because the executor calls it with the whole unsegmented plan.

**"One URL per kind" is the correct granularity inside that adapter, not "one URL per step".** An earlier draft assessed every `.writeMarkdown` and `.webToMarkdown` step. That over-assesses: `segmentPlans` absorbs consecutive `.writeMarkdown` steps into one preset segment, and `hackerNewsSpec` writes only the first, so a second step's output would gate on a file nothing ever writes. Same reasoning applies to `resolveDefaultOutputs` — resolving a second `.writeMarkdown` step would advertise a destination that is never written.

**Segmenting the walk fixes three distinct classes of under-assessment, not one — and only the first was obvious.** The ticket was written around escalations (a second step's file collision). But the aggregation reads two more things off each segment's assessment, and both were being read off the wrong segment: (1) `defaultTier`, which is *not* a constant per capability — `InvokeShortcutCapabilityAdapter` returns tier 1 or tier 2 depending on the named Shortcut's observed history, so a chain's baseline tier depends on which step you look at; (2) whatever an adapter computes by recursing, which for `.runRoutine` is an entire nested plan reached through `assessNestedPlan`. The second is the worst of the three, because nothing about the outer plan hints that a whole sub-plan went unassessed. **The reusable rule: when an adapter's `assessRisk` derives anything from step-specific state — not just escalations, but its baseline tier or a nested assessment — a first-match walk under-assesses every occurrence after the first.** Both were found by PR #25's review, not by the implementing session, precisely because the ticket's framing pointed at escalations.

**A per-segment walk multiplies an adapter's assessment side effects.** `InvokeShortcutCapabilityAdapter.assessRisk` shells out to `shortcuts list` (it carries a comment about doing this once per execute), so a chain invoking three Shortcuts now runs three enumerations at assessment time instead of one. That is the price of assessing each named Shortcut rather than the first one three times, and it matches what `executeChain` already does — but any adapter whose `assessRisk` is expensive or observable should now assume it is called once per segment.

**The scope verdict is four-valued, and that is the whole resolution of SONNY-12's recorded interaction flag.** `.inScope` / `.outOfScope` / `.unconstrained` / `.opaque`. A resource kind a workspace never configured is `.unconstrained` — it produces no new prompts and is *never eligible for branch C's relaxation*. So "users who never configured scope get relaxed tier-3 gating implicitly" becomes structurally impossible rather than something a toggle has to prevent, and no separate per-workspace opt-in is needed. Both two-valued readings fail against state that already exists on disk: "empty means deny all" would escalate every file action in every workspace on day one (no workspace has file locations — the field does not exist yet), and "empty means allow all" would blanket-bless every path, which is exactly the hazard the flag named. `CreateWorkspaceCapabilityAdapter` requires *at least one* of apps or URLs (`guard !apps.isEmpty || !urls.isEmpty` throws only when both are empty), so apps-only and URLs-only workspaces are already normal valid states that a two-valued model would break on the kind they never declared.

**Two hard constraints handed to branch C, recorded in the decisions doc and in row C's roadmap cell.** First, relaxation must be a *requirement* override and must never lower `effectiveTier` — the unattended gate (`approvedTier >= effectiveTier` against a fixed `.approved(.tier2)`), the stale-approval re-check, the `risk.assessed`/`risk.escalated` trace, and `UnattendedTrustAdvisory` all read that field, and lowering it would let in-scope tier-3 work run on a schedule with nobody present. Second, the in-scope tier-2 and tier-3 rules must be one function of `(tier, verdict)`, never two chained rules: branch C decided both that in-scope tier 2 auto-runs and that in-scope tier 3 drops to a lightweight confirmation, so implementing the tier-3 rule as a tier change (3 -> 2) would let the tier-2 rule fire next and make in-scope tier-3 actions silently auto-run. That is the single most likely way this feature ships as a security regression.

**The founder's escalate-and-prompt decision needs no new machinery, which is the largest thing this planning phase de-risked.** `AgentRunner.execute` gates once, entirely up front — the requirement is checked before `executor.execute(plan:)` is ever invoked — and `executeChain` runs every segment with no re-gating, which `.claude/rules/macagentcore-conventions.md` forbids adding. **`.opaque` is the honest name for what a pre-execution gate cannot see, and it is load-bearing rather than a fudge.** A Shortcut's internals (Sonny shells to `shortcuts run <name>`) and a search-driven `web_to_markdown`'s real URLs (returned by the search provider mid-execution) are unknowable when the one gate fires. **Count call sites with the compiler, not with grep — this branch's headline measurement correction.** The discovery note said nineteen direct `RoutineStore.save` sites; PR #28's re-check said 52 lines across 48 functions in 11 files. Both are wrong, and both were produced by grep, which cannot resolve a receiver named `store` to a type and silently misses dotted receivers (`fixture.routineStore.save(`) and multi-line calls. The reliable method is to make the compiler enumerate: annotate the method `@available(*, deprecated, message: "PROBE")`, build with `--build-tests`, and collect the warning locations. **The real population at `ca4fbe4` is 74 call-site lines across 57 enclosing functions in 12 files** — 1 in `Sources/`, 73 across 11 test files — and one further entry that is the synthetic `macro expansion #expect` buffer rather than a source line, which is exactly the kind of double-count a naive grep of compiler output would also get wrong. **Determine which call sites must migrate empirically, not by prediction.** The store check was added first and the suite run; the failures *are* the population that needed the bypass. Exactly two of 74, both writing `.openWorkspace` routines. Predicting would have been wrong in a load-bearing way: this branch's own contract, the discovery ticket, and the test's own doc comment all assumed SONNY-24's skip-branch test needed the bypass, and **it does not**. That routine is built entirely from legal operations; what the save capability refuses about it is `previewNestedPlan` failing on an unresolvable app name — something no store can evaluate, because it needs a capability execution context. So the store's check is deliberately a *subset* of the capability's, and plain `save` is still the correct door there.

**Keeping the bypass `internal` cost one import and was worth it.** `ProductShellTests` lives in `MacAgentTests`, which imported `MacAgentCore` plainly, so the choice was `public` on the bypass or `@testable` on that one import. `public` would have put a "write a routine the store would refuse" method on the app target's API surface, which is the exact property the ticket exists to remove. A test target reaching in through `@testable` is not the same thing as the app being able to.

**An enum with a payload is the only shape that makes the invariant structural, and hand-writing its `Codable` is part of the cost.** A private setter leaves `Decodable` open; validating in `RoutineStore.save` turns a decoded legacy file into a save failure rather than a repair. The enum closes both — but it changes the persisted shape, so it needs a decoder that reads the old one. Two decisions inside that decoder are worth carrying forward: (1) **the flat `{"state": "…", "reason": "…"}` payload rather than Swift's synthesized `{"pausedBySonny": {"reason": "…"}}`**, because `routines.json` is a file a person occasionally reads while debugging a schedule and because it survives a Swift-side case rename; (2) **the illegal legacy state repairs rather than throws.** Enabled is the fact the scheduler acts on, the reason is the stale half, so the reason is dropped — the same answer `setEnabled(true, now:)` has always given, applied at the last door it can be. A display glitch must never cost a user their routines file. A schedule carrying *neither* shape still throws, exactly as the synthesized decoder did, so the tolerant branch cannot quietly become "default to disabled" for a genuinely damaged file.

**A test that iterates the list it is testing is self-fulfilling, and needs a literal pin beside it.** `savingRejectsEveryForbiddenStepOperationWithTheOperationNamed` loops `StoredRoutine.forbiddenStepOperations`, so deleting an entry from the list would not fail it — it would silently stop testing that entry. Mutation M2 (drop `.openWorkspace`) proves the point: it reddens only `theForbiddenStepListIsExactlyTheSixOperationsRoutinesMayNotContain`, the test that asserts the literal set. Both tests are needed; either alone is a hole.

**The `previewNestedPlan` asymmetry is deliberate and should stay named.** SONNY-24's entry recorded the store/capability split as a defect. Half of it was — the forbidden-operation list, now closed. The other half is structural: the capability can preview a nested plan and the store cannot, so a routine refused for an unresolvable app name will always be writable at the store level. Neither end should read as the complete guarantee, and both now say so in their own doc comments.

The same reasoning is why an unknown identifier in the persisted array is carried harmlessly rather than treated as corruption.

**The collapse preference deliberately does not live on `AgentViewModel`.** The two existing plain-`UserDefaults` preferences (`usePointerCursors`, `displayFullNames`) are there because both the widget and Command Center read them. Nothing outside this one page reads this one, so putting it on the shared view model would add `@Published` state with exactly one observer. `TaskSectionCollapseStore` is injected into `TasksFoundationView` instead, defaulted to `.standard`, which is also what makes the round-trip testable without constructing a whole view model. The rule that actually mattered — plain `UserDefaults`, not `LocalStorageEncryption`, for a cosmetic preference — is followed.

**Seed `@State` in `init`, not in `onAppear`.** `TasksFoundationView.onAppear` already fires on every return to the page (it calls `refreshTaskHistory`), so loading the preference there would re-read defaults on every tab switch and, if a write ever lagged, discard an in-session collapse. `State(initialValue: collapseStore.load())` in a custom `init` seeds once per view identity and leaves the existing `TasksFoundationView(viewModel:)` call site unchanged.

**`count` is a property of the section, not of what got rendered.** The count-while-collapsed requirement is one line away from being wrong — `section.visibleRecords.count` compiles and reads naturally and silently shows 0 on every collapsed section. Architectural decisions / pitfalls discovered (required, write "none" if true):

**Escalation reasons are questions, not errors — everywhere.** Founder decision (user, 2026-08-06), taken on a two-part question put before any styling was written. The widget's escalation-reasons line moved from `WidgetTheme.errorGlyph` (#FF7474) to `WidgetTheme.secondaryCircular` (**#FF9230**, System B amber), the counterpart to Command Center's `SonnyTheme.warning`. The requirement "must be visually distinguishable from Sonny's error states" was made *checkable* rather than asserted, by enumerating first and subtracting after: `errorGlyph` had exactly three uses, of which the escalation line was the only non-error one; afterwards it is used exclusively by genuine error states, so the property is true by construction of the palette. **The two token systems are not mixed:** Command Center's panel already used `SonnyTheme.warning` (#F2BE00) and was correctly left with zero diff, because a System B token on a System A surface is the mistake this rule exists to prevent.

**The two-notions-of-empty class — three appearances on one branch, and the generalisable rule.** This is the single most valuable thing in this entry. Each time, a second, locally-obvious notion of "empty" was written beside the evaluator's, agreed with it in the common case, and diverged exactly where an inert entry exists:
1. **SONNY-40, first shipped state.** `removalEmptiesTheKind` counted raw surviving strings, so a removal taking a kind's last *working* entry while an inert one survived handed the approver the milder entry-naming consent and un-restricted the dimension anyway — precisely the failure the two-reason requirement exists to prevent.
2. **SONNY-40, cycle 2.** With emptiness fixed, the *escalation trigger* still diffed raw stored strings, so removing an entry that never restricted anything asked for tier-3 approval on a loss that could not occur.
3. **SONNY-41.** The detail sheet derived restricted/not-restricted from `entries.isEmpty` — reintroducing, under a different name and one commit later, the predicate SONNY-40 had just removed, on the surface whose entire job is telling the user whether a dimension restricts. Worse here than there, and inverted from the failure the ticket was written against: the user reads a dimension as restricting when nothing is, and the sheet withholds the one sentence that would say otherwise.
**The rule: ask the evaluator; never re-derive its answer.** `WorkspaceScope` reports `.unconstrained` whenever its *canonical* list is empty, and its own doc comment says that includes the all-inert case. **The reason this keeps recurring is that the wrong version is always the shorter expression** — `after.isEmpty` and `entries.isEmpty` both read naturally and both compile, and a suite whose every fixture has an unrestricted dimension that is *also* an empty one can never tell the two sources apart. The fixture that separates them is a workspace whose three lists are all non-empty and one of which is entirely inert; SONNY-41's `theFootnoteFollowsTheEvaluatorEvenWhenNoListIsEmpty` is that fixture, and it exists only because a mutation battery found the gap after the headline fix had already landed.

**Adding a field to a lifecycle whose clear sites are enumerated in several places, twice in two tickets.** SONNY-38's review filed F2 against `clearInMemoryLocalDataState` for `explicitWorkspaceBinding`; SONNY-39 then added `pendingWorkspaceBinding` and repeated it exactly (F4). The shape: *a new field joins a lifecycle whose clear sites are enumerated in four places, and nothing forces the enumeration to be revisited.* Both are fixed and pinned, and the enumeration is now written out in the function rather than trusted — but the class is the record, not the two instances. **A new binding-like field is not done when it is set and read; it is done when every clear site has been re-enumerated by hand.** The same shape produced SONNY-39's R1 (deleting a workspace left an arm naming it alive, so the chip promised a boundary the run would not apply) — a third instance, reached through a different function.

**The pending-arm lifecycle contract.** A pending card binding **binds exactly one task: the next composer dispatch.** It used to be consumed by *any* `start()`, which meant an armed-but-never-submitted chip was inherited by the next row action — arm "Drafting", get distracted, click Open on "Research", and Research opened under Drafting's boundary and raised a scope prompt naming a workspace the user never mentioned. Now: a composer dispatch consumes it, **every other dispatch kills it**, and either way it dies at the dispatch so it can never reach a second task. `fromComposer: Bool = false` is the safe default **by design, not by convention** — a call site added later that says nothing drops the arm rather than silently scoping itself with it. An explicit `workspaceBinding:` argument still wins over both, keeping the card-beats-free-text precedence a single slot.

**H1 — voice and typed dispatch must be gated by the same terms.** The typed composer is `.disabled(isTaskInFlight)`, which includes a pending clarification; `canUseVoice` had no clarification term. Recorded alternative for a future ticket: voice *answering* a clarification is a feature, and building the gate first does not foreclose it. **The auto-collapse ruling stands, but its safety basis was corrected**: the original argument rested on "an invisible live arm can bind nothing the user does not aim at the composer while seeing the chip," which H1 falsified. **Process pitfall: a mutation battery reverts `Sources/` with `git checkout`, so it must only ever run against a committed tree.** Running one over uncommitted work during SONNY-40 **destroyed a round of fixes that then had to be redone.** The battery is worth its cost — it found the two-notions-of-empty class, the `restricts(.webDomain)` blind spot, SONNY-41's task-count pluralisation and the badge-write boundary gap, none of which reading found — but its revert step is indiscriminate. Commit first, every time.

**Entry identity is not the evaluator's resource matching.** `verdict(for:)` answers "does this resource fall inside the boundary" — folder *containment* and a dot-suffix host match. That is the wrong question for "which stored entry does this removal name": under it, "remove `~/Documents/ClientAlpha`" would delete a stored `~/Documents`. Removal matching is *equality* of the same canonical forms, reused rather than re-derived. URLs deliberately carry two keys: removal matches by **host** (so a removal that left the host in scope would change no boundary at all), while addition dedupes by the whole URL (two pages on one host legitimately both belong). SONNY-41's sheet, which cannot see those key functions, recovers the same equality by asking the evaluator **twice, symmetrically** — a one-way probe would group a parent folder with its child, and symmetry turns those deliberately asymmetric rules back into equality.

**Removals are derived from the outcome, never from the request.** A request-derived list would call "remove Safari, add Safari" a loss, escalate for nothing, and make the answer depend on whether removals or additions applied first. What the user loses is a property of the outcome, so it is read from the outcome.

**A plan may edit one workspace only once.** `AgentRunner` gates once up front and `executeChain` never re-gates, so a second edit of the same workspace is assessed against a store the first has not yet written to — two "one of several" consents could between them empty a dimension with neither saying so. The rule lives in `resolveDefaultOutputs`, the one hook handed the whole plan; a per-segment count structurally cannot see the shape it needs to reject. Editing two *different* workspaces is allowed, because they share no record and each assessment is correct in isolation.

**`edit_workspace` is forbidden inside routines.** The capability's own new operation opened the hole: removal escalates to tier 3, which an unattended run structurally cannot satisfy, but *addition* stays tier 2, which it can — so a scheduled routine could have widened a workspace's restriction scope with nobody present. `PlanScopedResources` refuses a `default:` clause precisely so a new operation cannot land unclassified, but a `Set` has no such guard.
