Architectural decisions / pitfalls discovered (required, write "none" if true):

- **The archive was left whole rather than split, and the reading tools are what made that the cheaper answer rather than merely the lazier one.** Splitting 223 entries would rewrite 17,393 lines in one commit — a diff nobody can review by reading, which is the review this repository actually runs — and would move every byte that the citations above already reach. Against that, the only thing the split would buy is uniformity. The tools do not need it: `read` concatenates the directory and the archive into one stream, so a reader sees one document either way, and the archive's ordering arms keep working over a file that can no longer change, which turns them from a check on honest work into a guard against one specific mistake. **The archive is, in effect, a third era of the same document**, and this tool already had the concept — it has been telling the file's two eras apart since SONNY-225.
- **With one file per branch there is no position to get wrong, so the ordering arm has nothing to check in the new era — and a check that silently has nothing to do is the failure this repository keeps being caught by.** What replaces it is the completeness arm: a branch that merged and wrote no record. That fault is exactly as quiet as a misplaced entry was — nothing else in the tree goes red on a missing file — and it has already happened once, on PR #124, found only because the outgoing coordinator read two branches side by side (`WORKFLOW.md` step 7's record of it). The arm needs a boundary, so `DIRECTORY_ERA_BRANCH` in the script names this branch and every merge at or after it owes both files; the roughly thirty branches that merged before the rule existed and wrote nothing are the archive's and are not checked.
- **That boundary is a constant naming a branch, which is a clean zero waiting to happen**, since a rename would leave the arm vacuous forever while every run still exits 0. Two things answer it: the resolution is printed on every run, clean or not, and an entry naming a branch that *has* merged while the boundary has *not* is itself a finding — the exact symptom a stale constant produces.
- **A branch that owes no entry now writes one line saying so, instead of writing nothing.** It is the only way the completeness arm can exist at all, and it closes the gap `WORKFLOW.md` step 7 already records: #125 and #126 rightly wrote no entry, #124 wrongly wrote none, and nothing but a human comparison could tell those two apart. The alternative — a shared opt-out list — is a file every branch would edit, which is the coupling this whole ticket removes.
- **`git rev-parse <rev>:<path>` echoes its argument when the path does not resolve, so a tree-identity loop guarded on an empty answer reports IDENTICAL for a path that exists in neither tree.** `git rev-parse "HEAD:nosuchdir"` exits 128 and prints `HEAD:nosuchdir` on stdout; `--verify --quiet` exits 1 and prints nothing. This is a new member of the family `CLAUDE.md`'s Claims and evidence section already holds — the zsh `:s` modifier that answers a commit SHA for `$sha:server`, and the loop variable named `path` that destroys `PATH` — and it is worse than both in one respect: it was found by running that bullet's *own* recommended control, which says to refuse an empty answer, on a guard that had one. The bullet now carries it, and the rule it lands on is to read each side's **exit code** rather than the emptiness of its output.
- **The tool's own selftest shipped this repository's shared-marker gotcha, and a deliberately bad mutant is what found it.** Three loops emit the phrase `names a branch that does not exist` — the archive's, the entry directory's and the manual directory's — and three cases asserted the phrase bare, so disabling any one loop left all three green: the mutant that made every entry-file name read as an unmerged branch **survived a 44-case selftest**. That is `CLAUDE.md`'s "a source scan's `contains(token)` over a whole region is satisfied by any of the sites that share the token", arriving in a test file rather than a source scan. The two directory cases are anchored on their own paths now and the archive's on the wording only it produces, and three separate mutants — one per loop — each fail only the case or cases belonging to the loop it disabled: the entry directory's fails one, the manual directory's fails one, the archive's fails both archive cases.
- **Python buffers stdout and does not buffer stderr, so a tool whose findings go to stdout and whose summary goes to stderr comes out backwards in any caller that merges the two.** The stop hook captures this tool with `2>&1`, and before the fix the hook's transcript opened with `1 finding(s).` above the mainline line, the era line and the finding it counted — undoing, in the merged stream, exactly what PR #243's F1 established for stdout alone. One `sys.stdout.flush()` fixes it and a selftest arm reads the merged stream the way the hook does; removing the flush fails that arm, which is how the arm was shown to hold.

- **The same both-directions failure happened twice on this branch, in two different files, and the second time it was in the guard on the guard** (PR #259's review, F2). The tool's selftest shipped it first — three loops, one phrase, three cases asserting the phrase bare — and that is recorded above as found by a deliberately bad mutant. Then the *stop hook's* selftest shipped its mirror: every case exercising the entry directory wrote **both** directories, so `docs/manual-tests` alone kept the trigger firing and nothing pinned `docs/changelog`. Measured by the reviewer: dropping `docs/changelog` from `changelog_paths` passed **all 24 cases**, while dropping either of the other two killed the run. The failure that would have let through is a branch touching only `docs/changelog` — which `WORKFLOW.md` step 7 names explicitly, #122 and #123 being corrections to the record — finishing a turn with a real finding unreported: the real hook exits 2 with 942 bytes on stderr where the mutated one exits 0 and silent. **The lesson is not "write a mirror case", which this branch already knew and had already written down.** It is that a case exercising A *and* B pins neither, so the pair has to be built as one-path-each and each case has to assert the other path is absent — which is what `only_one_directory` now does, and what makes the pair unable to drift back. All three trigger paths are now killed by their own case and by no other: dropping the archive fails 11, dropping `docs/changelog` fails 1, dropping `docs/manual-tests` fails 1.
- **A source scan's population must be git's, not the filesystem's, once the directory is somewhere a person opens** (PR #259's review, F3). `directory_entries` walked with `os.walk`, so a `.DS_Store` — which macOS writes into any directory a Finder window touches, and which this repository ignores at `.gitignore:3` — became a finding, blocked the stop hook, and advised renaming it to `<branch>.md`. A false red rather than a false green, so it is loud; but it stops a session that did nothing, by advice nobody can act on, which is `CLAUDE.md`'s own description of how a check becomes one people turn off. `git ls-files --cached --others --exclude-standard` is the population now, which is not a filter on the symptom: it is exactly the set git tracks or would track, so every file the arm can fire on is one somebody added and the advice is true whenever it is given. `--others` is in there because a branch writes its entry before it commits it, and tracked-only would read a just-written entry as absent; the `isfile` guard is there because `--cached` names a path whose working file may be gone, and opening it raised instead of reporting the entry missing — which is the state the completeness arm exists to see.
- **A prefix-matched permission rule is spelling-sensitive, and `git -C <path>` walks straight through one.** The machine's own soft-deny list carries `Bash(git push --force:*)` — in `~/.claude/settings.json`'s `autoMode.soft_deny`, per-machine and outside the tree — and **whether it fires is unverified** (SONNY-511). This branch reported it refusing `git push --force origin <branch>` while running for `git -C "$W" push --force origin <branch>`, the form a session reaches for when the branch lives in another worktree, and concluded prefix-matching from the pair. The reviewer could not reproduce the refusing half: the bare form **ran** to a throwaway local remote and again as a `--dry-run` to `origin`, in a session where a bare `rm -rf` on a scratch path was refused in the same breath — the control that makes that an observation and not an absence. SONNY-511 carries the lead, which is that each of that list's three custom entries keeps its explanation *inside* the pattern string. What survives either way, from the rule's text rather than from a measurement: a prefix rule cannot match `git -C <path> push --force`, and a *complete* guard cannot be built in this repository while a **bounded one can** — a `PreToolUse` Bash hook reads the whole command string and `.githooks/pre-push` catches a non-fast-forward however it is spelled, both mechanisms this repository already runs. It is written here because the gap is invisible from a passing demonstration — the refusal fires for the spelling anyone tests with, and not for the spelling a script writes.
