Architectural decisions / pitfalls discovered (required, write "none" if true):
- **The comparison target is a table of rows, not a copy of `main`'s old function and not a bitmap.** A copy of the old function would read today's word list and today's Foundation, so it would move with the thing it is compared against. A bitmap of 177,155 verdicts is by value and unreadable. The verdicts repeat, though: walking the class token by token is a tree, and two addresses whose whole subtrees carry the same verdicts are one row. Merged that way the run is 18 rows, a verdict and the row each token leads to, and expanding the rows gives back every verdict, which the generator checks before it prints. A reader can follow `?/signup` through rows 0, 3, 7 and 11 with a finger. No rule about addresses is written in the table or the test, so neither can be wrong about the rule in a way the rule's own code was not.
- **Five tokens, and what that costs.** Four is the shallowest length that sees both cuts, by 114 addresses and by 4 (the scratch harness, whose source is on SONNY-539); five is lane-529's published population, where they are 2,110 and 146. Alone, the guard passed after 0.955 seconds and the whole suite after 0.955 (`--filter AccountCreationClassTests`, debug build, the clean baseline of the run at `3fca3481`); the table test took 0.111 seconds and the walk's own control 0.044. Inside the full suite the same three read 6.215, 5.161 and 5.160 seconds. That is waiting and not work: the control that takes 0.044 seconds alone read 5.160 there, because 3,514 tests share the machine's cores. It is about a second because only `main`'s refusals are asked about, and nothing is claimed of the rest. Six tokens is 1,948,716 addresses, eleven times the work, which is too slow for every suite; lane-529's zero over that population stands as a measurement, and `DEPTH` in the script is the one number to change to repeat it. The table does not limit the length: it is 14 rows at four tokens and 18 at five.
- **The counts the suite holds sit outside the generated block, on purpose.** A table regenerated from another commit, or from another class, would otherwise bring its own counts with it and pass. The commit, the tokens, the length, the addresses by length and the refusals by length are all written by hand in the test.
- **Counts alone cannot hold a table.** Swapping two of row 0's targets, so that `signup` goes where `x` went, leaves every count by length exactly as it was (measured by expanding the rows both ways in a scratch script: `[2, 32, 432, 5560, 69520]` each time). What catches it is the shapes held by name, which is why the doubled `?` and the second `#` are each held as a refusal by name and not only inside a total. It is mutant T2.
- **An address goes in through the decoder's door.** The pack decoder makes a URL with `URLComponents(string:)?.url`; lane-529's run used `URL(string:)`. Over the whole class the two give the same URL and the same verdicts from both matchers (0 unparsed, 0 different, of 177,155), so the published figures stand. That was measured, not assumed, because a sample that enters by another door tests a matcher the loader never calls.
- **Two independent runs agree.** A scratch harness with `main`'s old function copied in by hand, and the generator, which compiles `8f3d1d02`'s own four files, both answer 75,546 refusals and the same five figures by length. The scratch harness also reproduced all three of the ticket's measurements at `856bb7ee` before any test was written: 0, 2,110 with the cut at `/.`, and 146 with `/.?`. Its source is on SONNY-539.
- **`#require` on a `Bool?` is ambiguous, and the compiler says so as a warning.** It cannot tell "is not nil" from "is true". The held shapes compare with `== true` and `== false` instead, which also fails a shape that is not of the class.

Open questions (required, write "none" if true):
- **Should the floor move up to today's matcher?** Today's matcher refuses 15,900 addresses of the class that the floor loaded, and none the other way. Keeping the floor at `8f3d1d02` is what the ticket describes: the table never needs regenerating, and it is a different implementation's answers, which is what found the two shapes. Its cost is that those 15,900 are held only by the examples in `SkillPackTests`. Raising it is one command, `scripts/account-creation-class-table --commit <rev> --write`, and then re-holding the counts and the named shapes in the test, since some shapes the floor loaded are refused today (`signup-x` is one); every refusal the class can express is then held, and any later narrowing has to be made on purpose. Its cost is that the table becomes the live matcher's own answers, so it can never show a hole the matcher already has. This branch keeps the floor where the ticket put it. The founders decide.
