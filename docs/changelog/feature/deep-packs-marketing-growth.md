Architectural decisions / pitfalls discovered (required, write "none" if true):
- **A scripted fetch is not a reading, and the browser has to be connected before a single flow is written.** Review-255 measured 18 of 23 cited pages serving a scripted client nothing under HTTP 200. Every flow here cites a page opened and read in a browser in the session that wrote it.
- **`get_page_text` and the accessibility tree both reflect `innerText`, and two false claims on this branch came from treating that as the page.** `innerText` strips link targets and skips text that is not rendered. Buffer's help article was called a shadow-DOM case: it has **0 shadow roots and 0 iframes**, and `innerText` returns **29 characters** where `textContent` returns **233,786** and holds the article — 7,102 characters of clean prose once `script`/`style` are stripped. Separately, the Google Ads article was said to "name no URL", so a deeper start URL "would be a guess": its visible text carries none, but its DOM carries **5 hrefs to `ads.google.com`, including `https://ads.google.com/aw/campaigns` twice**, behind the very phrases the flows are built from. **When a claim rests on what a page does *not* contain, read the DOM rather than the rendered text** — SONNY-463 carries this as a rule. It is the *Claims and evidence* clean-zero family arriving through a browser: an instrument that cannot see the bytes you mean answers a clean zero, and a clean zero reads like good news.
- **A slow page and an unreadable one return the same thing on the first read.** `support.google.com/youtube/answer/57407` served a blank skeleton and answered "No text content found"; it rendered fully after about four seconds. Wait and retry before concluding a page cannot be read — that retry is what exposed the Buffer misdiagnosis.
- **A start page has to agree with step 1.** `ads.google.com/aw/campaigns` was available on the page and is still not what this pack declares, because steps 1 and 2 of both Google Ads flows navigate *from the front door to the Campaigns page*: a deeper start URL would land Sonny where step 3 begins and make the first two steps describe controls already passed. The reason is about the flow, not about what could be found.
- **A flow may compose across a page's sections but never across its screens.** Google Ads' download flow and both Search Console flows draw on more than one list and are correct to: each page delegates explicitly and the reader never leaves the screen. F1 was the one case that crossed.
- **An ads pack carries no flow that turns an ad *on*.** `metaads` is deep and carries three flows — find a campaign, view an ad's results, turn one off — so the rule is about the act, not about ads packs having no flows. Google Ads is deep here with two read-only flows; LinkedIn Ads is left out because both its documented pages either launch an ad set or create an ad account with a currency, billing admin access and an Ads Agreement to accept.
- **The credential rule refuses `secret`, which is a real control's real name.** Pinterest's board flow drops the page's "Keep board secret" clause rather than renaming the control: a fabricated label costs correctness, while an omission only costs an optional capability. The underlying collision is SONNY-508's.
- **A control has to be shown to change something before its firing means anything.** This branch's catalogue control first mutated `hootsuite.task_flow_docs` from `shallow` to `shallow` — a no-op that proved nothing and was caught only because the checker named 12 ids where 13 were expected.
- **A page read in a profile signed into someone's account is a different page.** All five Google-owned pages cited here were first read signed in. Re-read signed out — the profile check run both ways, the account widget absent *and* a sign-in link present — all seven affected flows still described what a signed-out reader sees, and nothing needed fixing. The check that only reports the answer you want is not a check: the first attempt found the profile still signed in and read nothing.
