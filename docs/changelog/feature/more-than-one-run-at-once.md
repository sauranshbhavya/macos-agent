Architectural decisions / pitfalls discovered (required, write "none" if true):

**A task-local names the run, rather than a `RunID` parameter threaded through every function.** There were 153 write sites of the run's state in the app target before this branch (`git grep -nP '\b(isRunning|approvalRequest|clarificationQuestion|plan|stepStatuses|finalSummary|errorMessage|preparedRun|runner|currentTask|activeTaskOrigin|suggestions|clarificationAnswer|visionSessionProgress|visionCapturePreview|visionDelegationRequest|visionSessionPause|activeTaskScope|currentTaskID|pendingTaskHistoryStartedAt|activeResumableTask|lastCommand)\s*(=[^=]|\[)' 8f3d1d02 -- Sources/MacAgent | grep -vE ':[0-9]+:\s*//' | wc -l` → 153; `-P`, because `git grep -E` does not honour `\b` and the same pattern under `-E` answers 0). The deciding question was which way a missed site fails. With a parameter, a missed site still compiles and writes to the focused run, which is a different run whenever two exist. With the scope, the only way to miss is to run outside the run's task — a timer, a notification, a `DispatchQueue` hop — and that also falls back to the focused run. Both designs share that one failure; the scope removes every other, and it let the pipeline keep its spelling. `RunScope`'s doc comment carries this.

**Outside any run the answer is the focused run, and that is right, not a fallback.** A view drawing a panel, a control pressed on that panel and a test reading state all mean the run on screen. What is *not* right is anything drawn for a run and pressed later — which is exactly the notification, and why it now carries its run and token rather than reading what is on screen.

**An answer names a run and a token, never a request.** `RiskApprovalRequest` is a value, so two runs asking the same thing park requests that compare equal, and a question asked twice parks an equal request both times. The token is minted on every park and cleared on every clear, in `approvalRequest`'s setter and nowhere else, so an answer can be matched to one asking of one question.

**An unstructured `Task` inherits its creator's task-local, so one of this branch's three bindings cannot be tested yet.** The sixth mutant dropped the binding inside `start()`'s `Task` and survived, correctly: the test starts its second run inside that slot's scope, and the `Task` inherits it; with no scope, `start()` works on the focused run and nothing on this branch can move focus while a run is going. The binding is there for the feature, where a pill click moves focus mid-run. The mutant is owed by that lane, with a test that moves focus.
