Behavior added:
- `CanaryBackstop.waitOrAbandon(for:…)`: polls until a condition holds; decides nothing before `deadline` (10 s); from the deadline on runs a canary — by default a request through `URLSession` to a stub host of its own, with nothing from `Sources/` on the path — and counts only trips begun after the deadline, each one completed, failed or unanswered. It gives up **stuck** once `canaryFloor` (100) trips completed with the condition still false, recording the declared give-up wording and a second sentence nothing declares; **broken** once 100 came back failed, recording the declared wording and a second undeclared sentence saying it was not a busy machine; or **starved** at `ceiling` (60 s) with neither, recording only declared wordings. All three throw `HangBackstop.Abandoned`. `CanaryBackstop.verdict` is `HangBackstop.verdict` on the completed count, with broken checked between stuck and starved.
- `CanaryBackstop.block` and `CanaryBackstop.Handoff`: the same wait from a stub handler's own thread, leaving its outcome for the test body, which is the only place an issue is recorded against the right test. `CanaryBackstop.Canary.actorHop`: a detached hop onto an actor of its own, the witness for a detached caller's hop onto a client.
- `BackendStubURLProtocol` runs every handler on a `Thread` of its own.
- `HangBackstop.waitRecordingAStuckWait`, shared by three suites.

Architectural decisions / pitfalls discovered (required, write "none" if true):
- **The stall was never the suite's own blocking handlers.** SONNY-515's earlier comments counted them as the likely cause. In the before run the longest `StubSignal` wait was 0.039 s and the longest `StubBarrier` wait 0.016 s, while 72 handlers queued for up to 7.352 s. Something else in the process held GCD's constrained pool — which is process-wide and capped at 64 threads (`sysctl kern.wq_max_constrained_threads` → 64 here). A thread per request takes the stub out of that pool whatever fills it.
- **The thread change alone does not close the manufactured-kill door, and that was measured rather than assumed.** In the second run no handler queued even 0.1 s, and the probe still found a window of 5.231 s in which it logged nothing at all — no request reached the stub, no handler started, no wait moved — and three `pollUntil` waits taking 7.21 s to 7.25 s to make two or three looks, all ending within 0.05 s of each other. In the burner run three real waits ran past their 10 s deadline — 12.67 s, 14.04 s and 14.04 s, two or three looks each — and ended held. The process as a whole stalls under load; only a witness that runs through the same kind of pipeline can tell that from a defect.
- **What this entry does not claim about those three late waits**: that the old `pollUntil` would have failed them. It took one last look after its deadline, and whether that look came before or after the request landed is exactly what the probe did not record.
- **Why the canary counts only trips begun after the deadline.** A canary running from the start banks trips completed before a stall began, and would then vouch for a pipeline that was frozen when the verdict was taken. `everyCanaryTripBeginsAfterTheDeadline` and `noCanaryIsSentBeforeTheDeadline` hold it, and the plan's M4 puts it back.
- **Why `BackendStubURLProtocolTests` uses `HangBackstop` and not `CanaryBackstop`.** The defect it pins — every handler waiting for a pool thread — exhausts the very pipeline a stub-transport canary travels, so that canary would call its failure starved and the mutant would never count. `HangBackstop` counts looks on the main actor, which the defect does not touch. **It is a witness the defect cannot slow, not the only one** — round one said "the one place", and a plain `Thread` is outside GCD's constrained pool too (PR #277's review, F5); the main actor was chosen because `HangBackstop` already carries the stuck-or-starved rule.
- **A wait that gives up must be the last thing its test does** (PR #277's review, F1). This branch's own new test asserted `allStarted` and the started count after `HangBackstop.waitRecordingAStuckWait` returned, which added `Expectation failed` issues no declaration covers to every starved give-up — the review watched both lines fire under M5 in a full run, and found the same shape in `VisionSessionRunTests` producing 88 counted kills at a load average near 100. It is the SONNY-259 cascade in the one branch written to close it, and it is invisible on a passing run because the lines are trivially true whenever the wait holds.
- **An assertion against `Date()` read at assertion time is a wall-clock bet, whatever its slack** (PR #277's review, F2). Round one swept waits — helpers, semaphores, deadline loops — and missed this, because it waits for nothing: `#expect(bound.timeIntervalSince(Date()) > -3700)` allowed 100 s and lost to a 134 s stall at a load average near 110, and to 112 s at 93 on a pack branch's review. Two independent reviewers is what settles that it is not rare. The fix is not more slack but a bracket the test reads itself, and it needed one fact that was not obvious from the test: the stub's `Date` header is formatted once, when the fixture is built, so the observed server clock is stale by however long the test took to reach its first response — the 100 s of slack had been absorbing that too.
- **A witness must not run through the code under test** (PR #277's review, F3). The first canary was a real `SonnyBackendClient.send`, so a mutant that broke `send` failed every canary trip on an idle machine — its pollers looked 26,574 to 26,580 times — and the wait reported "a busy machine rather than a defect". It cost attribution rather than coverage, since 28 other tests killed that mutant, but the sentence was false and nothing in the log could say so. Two changes, because either alone leaves a hole: the canary now takes a path with nothing from `Sources/` on it, and a trip that comes back failed is an answer rather than silence, with its own verdict.
- **A cheaper canary would have eaten the floor's margin, so it was measured before being assumed.** Round two's first draft of the floor's doc said the raw `URLSession` canary was cheaper per trip than the client's path; a throwaway timing test, never committed, found it roughly twice as slow — a hundred trips in 0.060 to 0.143 s against 0.027 to 0.066 s, five batches each at a load average between 23.50 and 58.81 — which is the safe direction for a race the canary must not win.
- **`ClientVersionClientTests`' window has a ceiling of `SonnyBackendTimeouts.auth * 0.9`**, not `CanaryBackstop.ceiling`, because the handler must answer before the client's own twenty seconds end the fetch; past that the second caller would send its own request and the count would fail in words no declaration covers.
- **SONNY-418: `Calendar(identifier: .gregorian)` with `timeZone = .current`, not `Calendar.current`.** The scheduler reads `Calendar.current`; the fixture needs only the same zone, and PR #198's review measured that explicit-Gregorian-at-the-machine's-zone is the property that matters for SONNY-403's fixture. Keeping the Gregorian calendar keeps "2026-07-15" meaning that date on a Mac set to another calendar system. Nothing under `Sources/` changes; passing the fixture's calendar to the scheduler at the call site, the ticket's other option, needs its own decision and was not taken.
- **A premise that only names the routine is not a premise that it ran** (found by the control run). `ResumableTaskRunTests`' `aScheduledRoutineRunLeavesNoRecordWhileAForegroundRunInTheSameFixtureDoes` passed under Kolkata with the Eastern pin still in place, because it checked the routine ran with `scheduledRunNotice?.contains("Morning")` and the notice for an occurrence missed past the catch-up window — `Sources/MacAgent/AgentViewModel.swift:8387` at `8f3d1d02` — names the routine too. It now asserts `"ran on schedule"`; with the old pin under Kolkata that assertion fails (exit 1, `1 test in 1 suite failed … with 1 issue`, the zone line flipped by hand and back, never by `git checkout`), and with the fixture on the machine's zone it passes.
- **A test whose failure depends on the host is invisible on the host.** The plan's M7 does not restore `America/New_York`: on a Mac in Eastern that mutant is SONNY-418's defect exactly and would come back SURVIVED on the machines the founders run batteries on. It pins twelve hours from the machine's own offset instead, which misses the catch-up window everywhere.
