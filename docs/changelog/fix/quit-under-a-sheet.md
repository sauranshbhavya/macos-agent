Architectural decisions / pitfalls discovered:
- **The cause, measured.** AppKit refuses termination outright while any window presented modally has `preventsApplicationTerminationWhenModal == true`, which is the default (the SDK's `NSWindow.h` says so beside the property), and a sheet is presented modally. The refusal is silent. `terminate(_:)` returns at once, `applicationShouldTerminate` is never called, and nothing is logged, so no reading of this repository could have found it. **It is refused, not deferred.** Closing the sheet afterwards does not quit, and two terminates back to back do not quit either. So the ticket's hypothesis (1) was half right (a sheet blocks quit) and half wrong (it does not defer). Hypothesis (2), a hang, is ruled out for this cause: `terminate` returns immediately. Both symptoms have this one cause. Relaunch Sonny only appears inside a sheet, so `open -n` started the new copy and the old copy's own terminate was refused.
- **The probe, so it can be re-run.** It was a standalone Swift program compiled with `swiftc` on macOS 26.6.2 (25G83), outside the repository. It sets `NSApplication` to the `.accessory` policy and shows one `NSWindow` hosting a SwiftUI view with `.sheet(isPresented:)`. It calls `NSApp.terminate(nil)` 1.5 s after launch and exits 3 if it is still alive 3 s later. It logs `applicationShouldTerminate` and `applicationWillTerminate`. Readings:
  - With no sheet: both delegate calls are logged, and it exits 0 (the control).
  - With a SwiftUI sheet, with an AppKit `beginSheet` sheet, with a sheet on a sheet, or with a `confirmationDialog`: exit 3, and neither delegate method is called.
  - With the flag cleared first: exit 0 in every case.
  The closing comment on SONNY-448 carries the source.
- **Cleared when a sheet begins, not when Sonny quits, because not every quit passes through Sonny.** An external quit Apple event, from `NSRunningApplication.terminate()` in a second process (the same event the Dock's Quit sends), was refused under a sheet too: exit 3. Its stack runs `_handleAEQuit` → `_shouldTerminate`, **without** `-[NSApplication terminate:]`. So a fix inside `AppDelegate.quit()`, or an `NSApplication` subclass overriding `terminate(_:)`, would have left the Dock, Activity Monitor, AppleScript and logout refused. With the flag cleared on `NSWindow.willBeginSheetNotification`, the same event quit the probe (exit 0).
- **Every window, synchronously.** When that notification arrives, the sheet is not yet in its parent's `sheets`, but it is already in `NSApp.windows` (measured). So clearing the whole list in the observer covers the new sheet with no gap for a quit to fall into. The property matters only for a window presented modally, and the app has no `runModal` or modal session: `git grep -n -E 'runModal|beginModalSession|beginSheetModal|NSAlert\(' 12aaf8b4 -- Sources | grep -vE ':[0-9]+: *//' | wc -l` → 0. Without the comment stage the same command answers 1, and the extra line is this branch's own doc comment saying there is none. With the stage in place, the same pipe over `NSApp\.terminate` finds the relauncher's line, so the stage is not what makes the zero.
- **`presentationPreventsAppTermination(_:)` exists in SwiftUI and was not used.** It is `@available(macOS 15.4, *)` in this SDK's interface, and the package targets macOS 14. It is also per sheet, so a new sheet written without it would bring the bug back.
- **Letting termination through makes SwiftUI write `false` to every open sheet's binding, inside `terminate` and before the delegate is asked.** The stack is `-[NSApplication terminate:]` → `_shouldTerminate` → `SheetPresentationWindow._dismissModalForTerminate` → the binding's setter. The first-run sheet's setter called `skipCurrentStep()`. Left there, the fix would have turned ⌘Q on sign-in into "Sign in later", and a relaunch from screen access into "Set up later", so the relaunched app would skip the Accessibility half the relaunch exists for. The setter now calls `FirstRunCoordinator.withdrawUnanswered()`, which clears the published step and records nothing. No other sheet's setter records anything. Of the 11 `.sheet(` sites (`git grep -n -E '\.sheet\(' 12aaf8b4 -- Sources | grep -vE ':[0-9]+: *//' | wc -l`; 15 without the comment stage), the ten besides first run are each driven by a `@State` property of `CommandCenterView`, read one by one with `git grep -P`. None passes `onDismiss:`: the one `onDismiss:` in the target is a parameter of a widget prompt, `FloatingWidgetView.swift:1255`.
- **Escape was the trap inside that change, and this branch walked into it once.** The first commit (`2e8bf84b`) said Escape reached the dialogs' close control, whose `.keyboardShortcut(.cancelAction)` would answer before the sheet did. That rested on a probe calling the sheet's `performKeyEquivalent` directly, which was the wrong instrument. Delivered through the sheet window's own `sendEvent` with a text field focused, Escape is answered by SwiftUI's sheet, which writes `false` to the binding: the same write a quit makes. That is also what the archive's SONNY-137 first-run row says ("Escape routes through the sheet's own dismissal"), and that row was right. So `FirstRunSequenceView` answers Escape itself with `.onExitCommand { coordinator.skipCurrentStep() }` (`05096b20`). Measured again with that in place: with a field focused, `onExitCommand` runs and the binding is not written. With the window itself first responder, the close control's `.cancelAction` runs. Termination still writes the binding, with `interactiveDismissDisabled` or without it.
- **A sheet cannot be attached in a test process to a window that was never on screen.** `beginSheet` left `attachedSheet` nil until the parent was ordered front. `aSheetAppKitBeginsIsAttachedAlreadyReleased` orders it front, the way `ProductShellTests` already shows Command Center.
