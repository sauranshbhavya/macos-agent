Architectural decisions / pitfalls discovered (required, write "none" if true):
- **The defect was an absent field, which is why the tests assert presence and value separately.** `expect(body.store).toBeFalsy()` passes on `undefined`, which is exactly the state being fixed — so a test written that way would have been green against the bug. Both tests assert `Object.hasOwn(body, "store")` is true *and* the value is `false`, and the mutation plan carries a *drop* mutant beside each *flip* mutant for the same reason: a plan holding only the flips would report coverage the tests do not have.
- **Cerebras deliberately gets nothing, the reason is conditional, and it is now a test rather than a comment.** The first version of this branch justified it as "`store` is a Responses-API property" — **that is false and review-267 caught it.** OpenAI's migration guide puts both in one breath: "Responses are stored by default. Chat completions are stored by default for new accounts." What is genuinely Responses-specific is Azure's *30-day figure*, not default storage. The founders confirmed on 2026-09-17 that the field stays off, on the two grounds that actually hold: `cerebras` appears in **no** chain in `DEFAULT_ROUTE_CHAINS` (`provider-router.ts`), so no user content flows through this body as shipped, and Cerebras does not list `store` among the parameters it accepts and documents nothing about unrecognised fields (read 2026-09-17), so sending one is an unverifiable change against an endpoint no test here can reach. **The first ground can be undone by one edit in another file, by someone with no reason to open the adapter** — which is why `cerebras.test.ts`'s `may only serve a route chain once it carries a store decision` now fails on exactly that combination. It drives the real adapter through the stubbed boundary and reads the real chain table rather than a held copy of either. Proved in three directions at `baacd9a0`: adding `cerebras` to the `plan` chain fails it **by name** (1 failed / 22 passed); emptying the whole chain table also fails it, on the walk-reached-something arm, so an unreadable table cannot read as a clean pass; and adding `cerebras` to a chain **together with** a `store` field passes (23/23), which is the other legitimate way to make it green. A first attempt at that middle mutant emptied only the `search` chain and passed — correctly, since three chains still had entries — and is recorded because a mutant too weak to fire is indistinguishable from a guard that does not work. **This remains a deliberate narrowing of SONNY-513's criterion**, which says "every model request that carries user content"; the founders ruled on it rather than a session.

Braced everywhere now; the figures did carry, confirmed with `HEAD:server` spelled literally.
