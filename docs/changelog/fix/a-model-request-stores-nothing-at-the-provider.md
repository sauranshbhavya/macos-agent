Architectural decisions / pitfalls discovered (required, write "none" if true):
- **The defect was an absent field, which is why the tests assert presence and value separately.** `expect(body.store).toBeFalsy()` passes on `undefined`, which is exactly the state being fixed — so a test written that way would have been green against the bug. Both tests assert `Object.hasOwn(body, "store")` is true *and* the value is `false`, and the mutation plan carries a *drop* mutant beside each *flip* mutant for the same reason: a plan holding only the flips would report coverage the tests do not have.
- **Cerebras deliberately gets nothing, and the reason is the provider rather than the API.** The first version of this branch justified it as "`store` is a Responses-API property" — **that is false and review-267 caught it.** OpenAI's migration guide puts both in one breath: "Responses are stored by default. Chat completions are stored by default for new accounts." What is genuinely Responses-specific is Azure's *30-day figure*, not default storage. The decision still stands on its other two legs, both provider-specific: Cerebras does not list `store` among the parameters it accepts and documents nothing about unrecognised fields (read 2026-09-17 at `inference-docs.cerebras.ai/api-reference/chat-completions`), so sending one is an unverifiable change against an endpoint no test here can reach; and the exposure is smaller than "a live route" implied, because `cerebras` appears in **no** chain in `DEFAULT_ROUTE_CHAINS` (`provider-router.ts:51-56` — `plan` and `synthesize` are `openai,anthropic`, `transcriptions` `openai`, `search` `tavily`), so the adapter serves nothing unless a deployment names it in a `MODEL_ROUTE_*` variable. **This remains a deliberate narrowing of SONNY-513's criterion**, which says "every model request that carries user content"; the purpose is met and the literal text is not, and it is on the ticket for a reviewer rather than resolved silently. The corrected reasoning is in the adapter's own comment, because that is what whoever moves the text route next will read.
- **A grep for `store:` over `server/src` answers with DI wiring, not with request bodies.** `git grep -nE '(^|[^a-zA-Z_])store:' dc73131c -- server/src` returns **15** lines at the branch base, of which **14** are a `store: someStore` constructor argument in `app.ts`, `content/hook.ts`, `routes/billing.ts` and their neighbours and **1** is prose inside a doc comment (`model/limits.ts:306`, "it reads the same store: it") — and **none** is a provider request body. The first draft of this sentence said all fifteen were constructor arguments; appending `| grep -vE 'store: [a-zA-Z]+Store'` printed the one that is not, which is how the overreach was caught. The count was right and the sentence resting on it was wrong — `CLAUDE.md`'s warning about the parenthesis getting less scrutiny than the figure, met while writing this very entry. Anyone sweeping this property later needs the population to be *upstream calls* — `git grep -nE 'fetch\(' dc73131c -- server/src/model` → **6**, at `anthropic.ts:246`, `cerebras.ts:182`, `openai.ts:131`, `openai.ts:233`, `tavily.ts:52`, `vision.ts:251` — and then to read what each one posts. That is `CLAUDE.md`'s "a grep count is evidence about text, never about behaviour" on the exact token this branch adds.
- **Both citations above carry a rev, and the `fetch(` one has to.** The line numbers are the branch base's, and this branch moves four of the six: the same command at `d89a0a2c` answers `cerebras.ts:205`, `openai.ts:137`, `openai.ts:239` and `vision.ts:268`, with only `anthropic.ts:246` and `tavily.ts:52` unmoved. Written without the rev — as the first draft of this bullet was — a reader running it at any later head gets six real hits whose numbers disagree with the four printed beside them, and nothing says which is stale. That is the eighth defect in `CLAUDE.md`'s write-the-command list, a right answer decaying, reached by omitting one argument.
- **That command is scoped to `server/src/model` and is not an enumeration of everything that leaves this gateway.** Two separate reasons, and the second defeats a widened scope as well. The scope: `server/src/billing/polar.ts` calls out too, and sits outside it. The aliasing: it reaches `fetch` through `const call = config.fetchImplementation ?? fetch` and then invokes `call(...)`, at **4** sites (`git grep -cE '^ *const call = config\.fetchImplementation \?\? fetch;' d89a0a2c -- server/src/billing/polar.ts` → 4; note `^ *` rather than `^\s*`, because POSIX ERE has no `\s` and the `\s` form answers a silent zero here — the `git grep` `\b` trap in `CLAUDE.md`, met on a different escape while writing this bullet), so `fetch\(` does not match them however wide the pathspec. Nothing on this branch needed them — Polar is a billing provider and carries no model content — but a later sweep for "what this gateway sends anywhere" that trusts the token alone will come back short, and a clean zero from a pattern that cannot see the bytes is the family `CLAUDE.md` names.
- **What settled the population was a probe, not reading.** A throwaway Node stub on a loopback port, driven by the three real adapter factories, printed each body's key list: `/responses` `["model","input"]`, `/responses` `["model","input","text"]`, `/chat/completions` `["model","messages"]` — three routes, `hasStore: false` on all three. Reading the files would have given the same answer; running them is what makes it a measurement, and it is the same harness shape PR #139 used for SONNY-131. The stub is not committed.
- **The half of the probe that a lane cannot run.** Whether the *upstream* honours the field is not established here and was not establishable: today's route is a proxy (`VISION_BASE_URL` defaults to `https://opencode.ai/zen/go/v1`), OpenCode documents neither `store`, retrieval by id, nor `previous_response_id` — silence, which is not a denial — and settling it needs a real credential, which this session had none of (`env | grep -cE '^(OPENAI|TAVILY|ANTHROPIC|CEREBRAS|VISION|OPENCODE)_API_KEY='` → **0**). That half is a founder-owned manual-test row on this branch rather than an unproven claim in this entry.
- **Contract §4.5 rule 5 says what this gateway *asks for*, never what the provider does, and the first version of it did not.** It read "There is no conversation state on the server, and none at the provider either" — a sentence with no evidence behind its second clause, which review-267 identified as re-creating this ticket's own defect one hop further out: a true statement about our code standing in for an unverified claim about someone else's. The rule now says the gateway asks the provider to keep none, and names the two things it does not assert. **The general shape is worth more than this instance**: a fix that closes a gap is exactly when the prose around it is most likely to over-claim, because the writer has just proved the hard part and the easy sentence rides along on that confidence.
- **A manual-test row has to be able to report a negative, and the first version of this one could not — twice over.** It asked the founder to run a screen-control session and then retrieve the response by id, and **no id exists to retrieve with**: the vision adapter's `VisionResult` carries only `outputText` and `usage` (`id` appears **0** times in `vision.ts`, against **9** for `model` on the same pattern shape, so the zero is measured rather than assumed), and the content store's `response_body` is this gateway's own reply captured in an `onSend` hook (`content/hook.ts:286`, `:297`), not the provider's. It also named `404` as the wanted answer — but a proxy that simply does not implement retrieval answers `404` to everything, which is indistinguishable from "it stored nothing", so the row's pass condition was satisfied by the case it was meant to detect. It is now two direct calls, `store:false` and `store:true`, each retrieved by its own id: the pair supplies the id the app never surfaces, and the second call is the control that separates an honoured field from an unimplemented endpoint. Only `404`-then-`200` is evidence, and all three other outcomes are written down as distinct findings.
- **One observation for whoever does SONNY-110's provider move.** OpenCode's own documentation gives its OpenAI-compatible surface as `https://opencode.ai/zen/v1/responses`, while this gateway is configured with `https://opencode.ai/zen/go/v1` — a `/go` segment their docs do not mention. Not this branch's to change and not a defect anyone has demonstrated; recorded because a provider move will re-derive that base URL and should not assume the configured one is documented.
