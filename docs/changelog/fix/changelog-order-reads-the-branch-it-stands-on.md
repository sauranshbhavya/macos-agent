Behavior added:
- **The completeness arm asks only for the branches whose work the checkout contains.** `reachable_from_head` reads `git rev-list HEAD`, and `holds_branch` asks whether the head a branch merged from — its merge's second parent — is in that set. A merge commit being reachable implies its second parent is, so the head alone is the whole test. It covers the three shapes a merge commit misses: a branch cut from `main` before the merge (not asked), a short stack's upper branch after the branch beneath merges (asked), and a lane's own worktree after its own merge (asked). Reachable, not first-parent: a branch brought up to date by merging `main` into it holds the newer heads through that merge's second parent.
- **Every run names what it did not ask**, and only what it measured. A new line reads `changelog-order: this checkout contains N of the M branches merged in the one-file-per-branch era. The other one — PR #… — is not asked for its files: this checkout holds neither its merge nor the head it merged from.`, or `contains all M` when there is nothing to skip. A skip that says nothing is a clean zero. A skip that says more than was measured is the ticket's defect again, which is what the first version of this line did.
- **A finding says which of two things happened, with the command that shows it.** The merge commit's own tree settles it. If the tree holds the file, the branch merged with its record and something on this checkout removed it since, and `git log --oneline <branch head>..HEAD -- <path>` names the commit, or it was an uncommitted deletion. If not, the branch merged without it, and the finding says the checkout contains the branch that merged, so its base is not the variable. Every era merge on `main` carries both files in its own merge tree today: 11 of 11, read with `git cat-file -e <merge>:<path>` for each merge in `git log --first-parent --merges c3bd9d8e^..0d645464`, against a nonexistent path at `0d645464` that exits 128 as the control.
- **The mirror is refused.** A checkout holding pull-request merges the mainline it read lacks, whether on its first-parent line or only through a merge of `main` into it, exits 1 with `run git fetch origin` inside the 200 bytes the stop hook quotes, and measures nothing. A stale `origin/main` beneath a newer branch, which `git fetch origin <branch>` alone leaves behind, is that shape.
- **`check <path>` on a path that does not exist refuses in words** rather than dying on a `FileNotFoundError` traceback. Exit 1 either way; only one of the two says it was the path.

Architectural decisions / pitfalls discovered (required, write "none" if true):
- **Why containment and not the whole reading moved to the merge base**, which the kickoff asked to be decided and written down. The ticket offered both: read the list from the tree the files come from, or restrict it to what the checkout can see. The merge base looks like the first done cheaply, and it is wrong for arm 2, which asks a different question. "Did this entry's branch merge?" is about the mainline, not the checkout: in a short stack the branch beneath merges while the one above still sits on its pre-merge head. So at the merge base the entry of the branch beneath reads unmerged, beside the branch's own, and the stack's two-entries finding returns for a branch that has done nothing wrong. Review-269 constructed that and measured it, rather than reading the argument: `0d645464`'s tool with its list read at `merge-base(HEAD, main)` gives exit 2, *2 entries name a branch that has not merged*, at #274's head after #271 merged. A stack's merge base is also a branch commit, not on the mainline's first-parent line, so its positions are not the mainline's. So the list stays the mainline's for resolving and ordering, and only the arm whose question is "what should be in this tree" asks the tree. `reachable_from_head`'s docstring carries this.
- **What "contains" means is the whole of the fix, and the first answer was wrong in a way this ticket exists to prevent.** The merge commit is the obvious reading, and two ordinary checkouts hold a branch's work without it. Review-269's F1 found them, and it matters beyond this tool. A short stack's upper branch is WORKFLOW's zero-hop case by construction, so for the whole window between the two merges nothing checks it but its own session's stop hook. The first fix made that hook silent on the one fault the stack clause most warns against, deleting the lower branch's record. The head a branch merged from is present in every checkout that holds its work, and a reachable merge implies it.
- **The same defect has a mirror, and it is live on this repository's own data.** In the table above, `main`'s tool reports **10** findings, each *names a branch that does not exist*, about five branches that merged. This branch's tool exits 1 and says to fetch. It is the same two trees disagreeing, the other way round, and it reaches through a second parent too (F2).
- **A `git grep -E` pattern with `\b` answered a clean zero inside this branch's own sweep**, on a file known to define the function it was looking for. `CLAUDE.md`'s bullet on it held; the `-P` re-run with a positive control answered correctly. And a shell parameter expansion `${rest##*/sauranshbhavya/}` failed to strip a subject that reads `from sauranshbhavya/`, since no `/` comes before the namespace. So every era merge read "no records" until the pattern was corrected to `*from sauranshbhavya/` and a nonexistent path was checked as the control. Both are the family `CLAUDE.md` names — a search whose engine cannot see the bytes you mean answers a clean zero — caught here because the zero was implausible, which is not a method.
- **Two figures this branch wrote were wrong, and only re-running the command found either.** The control count above read 3, from a listing cut by `head -3` (F3). SONNY-515's first comment said `startLoading` was called 49 times "in the four seconds before" the stall released. That 49 came from a 0.7 s window beginning before the stall. Over the stall itself, 816.948 to 820.954 on the probe's clock, the calls number **69** and the handler starts **0**. Both conclusions stood and both numerals did not. That is the parenthesis rule in `CLAUDE.md`'s *Claims and evidence*, arriving twice in one entry.
