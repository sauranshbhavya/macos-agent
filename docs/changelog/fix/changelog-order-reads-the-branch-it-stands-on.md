Behavior added:
- **The completeness arm asks only for merges the checkout contains.** `held_merges` reads `git rev-list --merges HEAD`; an era merge outside that set is skipped. Reachable, not first-parent: a branch brought up to date by merging `main` into it holds the newer merges through that merge's second parent, and their files are in its tree.
- **Every run names what it did not ask.** A new line, `changelog-order: this checkout contains N of the era's M merges. The other K — PR #…, … — merged after this checkout's base …`, or `contains all M` when there is nothing to skip. A skip that says nothing is a clean zero.
- **A finding says which of two things happened, with the command that shows it.** The merge commit's own tree settles it: if it holds the file, the branch merged with its record and something on this checkout removed it since (`git log --oneline <merge>..HEAD -- <path>` names the commit, or it is an uncommitted deletion); if not, the branch merged without it, and the finding says the checkout contains that merge, so its base is not the variable. Every era merge on `main` carries both files in its own merge tree today: 11 of 11, read with `git cat-file -e <merge>:<path>` for each merge in `git log --first-parent --merges c3bd9d8e^..0d645464`, against a nonexistent path at `0d645464` that exits 128 as the control.
- **The mirror is refused.** A checkout holding pull-request merges the mainline it read lacks — a stale `origin/main` beneath a newer branch, which `git fetch origin <branch>` alone leaves behind — exits 1 with `run git fetch origin` inside the 200 bytes the stop hook quotes, and measures nothing.
- **`check <path>` on a path that does not exist refuses in words** rather than dying on a `FileNotFoundError` traceback. Exit 1 either way; only one of the two says it was the path.

Architectural decisions / pitfalls discovered (required, write "none" if true):
- **Why containment and not the whole reading moved to the merge base**, which the kickoff asked to be decided and written down. The ticket offered both — read the list from the tree the files come from, or restrict it to what the checkout can see — and the merge base looks like the first done cheaply. It is wrong for arm 2, which asks a different question. "Did this entry's branch merge?" is about the mainline, not the checkout: in a short stack the branch beneath merges while the one above still sits on its pre-merge head, so at the merge base the entry of the branch beneath reads unmerged, beside the branch's own, and the stack's two-entries finding returns for a branch that has done nothing wrong. And a stack's merge base is a branch commit, not on the mainline's first-parent line, so its positions are not the mainline's. So the list stays the mainline's for resolving and ordering, and only the arm whose question is "what should be in this tree" asks the tree. `held_merges`' docstring carries this.
- **The same defect has a mirror, and it is live on this repository's own data.** In a clone at `0d645464` with `origin/main` moved back to `682f538d`, `origin/main`'s tool reports **10** findings, each *names a branch that does not exist*, about five branches that merged; this branch's tool exits 1 and says to fetch. Same two trees disagreeing, the other way round.

Known limitations / deferred scope:
- **SONNY-515 is not fixed on this branch.** It was handed back at the ninety-minute stop (`WORKFLOW.md` step 5), and its ticket carries the full findings. In short: every wait in the three tests is a poll on a signal the other side publishes (a counter the stub's handler increments, or a signal the test sends), and none is sleep-then-assert. But their 10-second backstops are reachable by load, which the rule for a hang backstop forbids — so in effect they are thresholds the tests race. A timing probe (uncommitted, now reverted) located the stall. In three full runs of the flagged suite — two at the machine's own load (load average up to 162) and one with ten CPU burners added (up to 239), all three green — **exactly 48** of the roughly 533 stub handler starts in each run waited a second or more in the stub's dispatch queue, and the longest wait grew with load: **3.992 s, 4.037 s, 6.980 s**. In the first run the 48 were released within **18 ms** of each other, while `startLoading` was being called 49 times in the four seconds before (`awk` over the probe log's `handler … queued` and `startLoading` lines). So URLSession was delivering and the client was sending. What stalled is the stub's shared concurrent dispatch queue being denied a thread, every run, for a span that scales with load toward the 10 s backstops the reviewer's run crossed. This suite's own blocking handlers park threads from that same pool. The proposed fix is on SONNY-515.
