# Sonny Founder Design Decisions

Source: meeting transcript, Sauransh Bhardwaj + Bhavya Singh (design), 2026-07-05. This captures product/design decisions made verbally that are not fully reflected in `docs/sonny-major-release-spec.md`, `docs/sonny-design-system-reference.md`, or the wireframe exports. Treat this as authoritative over a naive reading of the wireframe SVGs where they conflict — the wireframes are a static snapshot of a design conversation, this transcript carries reasoning the static files don't.

## Notifications
Native macOS notifications for v1, not a custom overlay. Rationale: native respects Do Not Disturb and other system-expected behavior; a custom overlay would look wrong when it collides with/covers other apps' notifications. Explicitly open to revisiting later, not a permanent decision. Error-state notification: step-level failure is orange with a retry button; total task failure offers retry or start a new task.

**Decision (2026-07-20):** the floating widget has no dismiss/hide action and stays visible on screen permanently (`.floating` window level, all Spaces, over full-screen apps) — this is deliberate, not a missing feature. One direct consequence: the native notifications above, whose whole purpose is covering "user is in another app," can't actually fire in practice, since the widget is always the thing already in front of the user. Confirmed and accepted: notifications ship as real, working code that's simply unused for now, not a bug to chase — same "open to revisiting later" status as the notification choice itself. The real cost lands on scheduled/background routine execution (routine scheduling is on the roadmap, not yet built): a routine running with no one watching the widget has no working fallback today, so that work needs its own real answer (see `docs/sonny-ui-backend-roadmap.md`), not an assumption that today's widget-only UI already covers it.

## Tasks <-> Workspaces association
The Linear-style wireframe's "project" tag on each task row maps directly to **which workspace that task belongs to/ran in**. This is a real intended association, not wireframe-template leftover. Sonny's task history data model does not currently capture this — adding it is a real scope item, not optional polish, and it's also the prerequisite for the Insights "Breakdown by Workspace" feature (see below).

## Routines
- Routines have real intended scheduling: a defined run time and an enabled/disabled state ("what time does it run and is it enabled or disabled"), grouped by cadence (daily/weekly/monthly) same as the home/Tasks screen's status grouping. This is a real feature, not decorative wireframe grouping — it implies an actual scheduler/execution-trigger component that does not exist in the current build (routines today are manually triggered only).
- Clicking into a routine should open a **detail view styled like the floating widget (liquid glass material)**, but embedded inside the main app window, not the literal floating widget window. It closes when the app closes. Explicit intent: give the user one consistent "how I watch Sonny work" experience regardless of which surface (menu-bar widget vs. main app) they're looking from, rather than two different UIs for the same concept. This is a real, previously-undocumented System-B-inside-System-A UI requirement — not covered by the current System A / System B split in the design-system reference doc, which treats them as fully separate surfaces.

## Insights
- Layout should be an **asymmetric bento grid** (uneven tile sizes, Apple-keynote style), explicitly *not* a uniform/symmetrical grid. The wireframe export's actual layout (stat cards + full-width chart + full-width sections, stacked) does not reflect this stated intent — the verbal description is more authoritative here than the static SVG.

  **Gap confirmed, deliberately deferred (2026-07-24):** `InsightsView` in `Sources/MacAgent/CommandCenterView.swift` (line 537) is, as of this date, exactly the rejected pattern above — a plain `VStack` of three equal-width stat cards (`InsightsOverviewBento`, an `HStack`) followed by three full-width panels stacked below (`WeeklyCompletionChart`, `WorkspaceBreakdownPanel`, `TaskHistoryListPanel`). No grid, no varying tile sizes, no real asymmetry. An earlier commit (`986c98d`, message: "restructure stat cards into an asymmetric bento grid") did not actually produce one — worth knowing the commit message overclaimed what landed, so it isn't mistaken for evidence this was already resolved. **Explicit decision: not fixed now.** This is queued for the last review/final-updates branch before the v1 release, not this branch — flagged here specifically so it survives as a real, findable item rather than being silently dropped or, worse, mistaken for "already handled" because a past commit message says it was. Whoever picks it up needs an actual product/design decision first (a real grid with varying column/row spans is a genuine layout redesign, not a small tweak) — this note plus the code pointer above is the starting context, not a ready-to-implement spec.
- Deliberately do **not** show usage/quota-consumption metrics (e.g. "you've used X% of your plan") on this page. Reasoning is explicit product strategy, not an oversight: it creates subscription-cancellation anxiety in heavy users and "am I getting my money's worth" doubt in light users. Take inspiration from Whisper Flow's insights instead — positive, non-anxiety-inducing stats like most-used app, most common action taken.
- A Spotify-Wrapped/"top 1%" style celebratory personal-usage insight is a deliberate v2/v3 idea, not v1 scope (needs a real user base first for the comparison to mean anything).
- A "Data Sent to AI" inspector — showing exactly what content/artifacts get sent to the external LLM provider — is an explicit, named competitive differentiator versus Clicky, which does not surface this anywhere in-product (only in a privacy policy page). Framing matters: must read as transparency, not as "we're just an API wrapper" — messaging needs care.

## Workspaces
- Card fields, confirmed real: workspace name, who's in it (solo vs. team — "team" ties to a future Enterprise tier, not v1's primary solo-user case, but the field/UI pattern should still exist), task count, and the apps in the workspace shown as an overlapping icon stack.
- Liquid glass material was tried for workspace cards and explicitly reverted — it was too visually distracting from the card content. Flat/opaque cards for Workspaces are a deliberate choice, not a corner cut.

## Floating widget — which main-app pages show it
Explicit, page-by-page decision, not "show it everywhere" or "show it on the homepage only":
- Tasks: yes.
- Routines: yes (creating/invoking routines via the widget is a real flow).
- Insights: no.
- Settings: no.
- Workspaces: ambiguous in the conversation — creating a workspace via the widget makes sense as a flow, but the page itself doesn't need the persistent widget affordance shown. Lean no unless a later decision says otherwise.

## Settings
Content was explicitly open/exploratory at design time ("I don't know what we're going to have in settings... this is a basic layout, Claude/Codex can add more on top of it"). The current build's simpler nav is not necessarily wrong against original intent — it just hasn't been elaborated. Treat Settings' final structure as still open for the UI/UX research phase to propose, not a fixed target to hit.

## Memory / history retrieval (relevant to branch 11, not immediate UI work)
Explicit architecture decision: persistent "memory" storage is for **user preferences only**. Anything fetchable live (calendar events, etc.) should be fetched fresh via the relevant API first. Only fall back to searching Sonny's own past conversation/task history (searched by date proximity to whatever date the user mentions, e.g. "the meeting on July 1st" searches roughly June 28-July 3) when a live API fetch isn't possible or doesn't apply. Conversations should be tagged with any dates mentioned in them so date-based search surfaces them later even if the conversation itself happened on a different date. This is not a new "memory" feature to build — it's a decision about what memory is *for* (preferences) versus what should just be live search over existing history.

## Approval panel — first-run moment
Branch 9's checkpoint 8 (proposed 2026-07-15): the approval panel renders identically on a user's 1st and 100th approval — five plain structured lines, no first-time explainer. That gap is real: most early real tasks already resolve to tier 2 by default under the existing risk model, so the natural-usage probability of hitting this moment early is already high without engineering a specific triggering task. The 2026-07-15 resolution called for two things: (1) first-time-specific framing on the panel itself, and (2) "a light, non-forced version of curating one good example in the empty-state/onboarding — explicitly not a forced onboarding walkthrough." That resolution was only ever recorded in `docs/sonny-v1-implementation-changelog.md`'s prose, never written back here — this entry backfills that gap.

**Decision (2026-07-24): split the two halves rather than build or defer both together.**

- **Shipping now:** first-time-only explanatory copy in `WidgetPermissionPanel` (`Sources/MacAgent/FloatingWidgetView.swift`), gated behind a persisted flag following the same plain-`UserDefaults` pattern already used for `displayFullNames`/`usePointerCursors` in `AgentViewModel.swift` — no new storage architecture needed. The flag flips permanently the first time the user resolves (allow *or* deny) any approval, matching "renders once, never again," not "shows until dismissed."
- **Explicitly deferred, not built: the curated-example surfacing.** Reasoning, recorded so it isn't re-litigated from scratch: the original resolution assumed an onboarding/empty-state surface to curate an example *into*. That assumption predates `feature/ui-ux-wireframe-fidelity` deleting Command Center's own command composer entirely and making the floating widget the sole command surface — the surface this was originally imagined to live in may not exist in the same shape anymore. Forcing an implementation today would mean guessing at a UI location rather than making a real product decision.
- **What actually unblocks this, for whoever picks it up next:** not "how do we build a curated example" — it's *where does curated-example surfacing even live now* that Command Center has no composer and the widget is the only command-entry surface. Candidates worth weighing when that decision gets made: Command Center's Tasks page empty state (visible before any task has ever run), the widget's own idle state (visible on every launch, arguably too persistent for a one-time nudge), or a dedicated first-launch-only surface (most correct fit, most net-new engineering). This needs founder-level input on which surface is even right, not an implementation-level guess.

## Instant utilities — quick-results-list / launcher palette
Traced back to its real origin (previously just an "open question" with no context attached in the changelog): this is **not** a small missing wireframe asset. It's a materially different interaction model — a Raycast/Spotlight-style palette that would surface *multiple* candidate results (e.g. several recent clipboard entries, several matching snippets) for the user to browse and pick from, layered on top of the instant-utility tier (§4A.6: calculator, clipboard history, snippet expansion, recent-artifact lookup, quick app/window switching). It has been explicitly deferred since branch 5 (`feature/instant-utilities-shortcuts`, 2026-07-0X), pending a wireframe that has never been produced, across every branch since.

The instant-utility **backend** itself is fully built and working today, independent of this — calculator, clipboard history, snippet expansion, and recent-artifact lookup have all been exercised for real throughout `feature/ui-ux-wireframe-fidelity`'s own manual QA pass. What's missing is specifically the multi-candidate browsing *UI* layered on top.

**Decision (2026-07-24): left open on purpose, not silently dropped — and the real open question has changed.** When this was first scoped, the open question was "when will the wireframe get made." It no longer is. The floating widget's product direction has since converged on a single command-in/single-result-out flow — type or speak one command, get one result — which is a fundamentally different shape than a multi-candidate browsing palette. Before this is picked up again, the question that actually needs answering is **whether a multi-candidate browsing UI still fits the product Sonny has become**, or whether the single-shot model has organically superseded the original Raycast-adjacent framing this idea was scoped under. That's a product call for a future session to make explicitly, not a missing-asset problem to route back to design.

## Menu bar treatment — Claude-style vs. ChatGPT-style
Raised during branch 11's original planning (see the roadmap notes in `docs/sonny-v1-implementation-changelog.md`, first flagged 2026-07-11) as a decision that needed to be made "before branch 11 UI work starts, not mid-branch." It never was — and critically, no document anywhere (spec, wireframe, this file) ever recorded what specifically distinguishes "Claude-style" from "ChatGPT-style" menu-bar treatment. That distinction exists only in the original conversation that raised it.

What actually shipped, confirmed directly against the code: an icon-only menu-bar item (no title text next to it), with a plain 3-item menu (New Task / Open Sonny / Quit Sonny) that responds identically to left- and right-click.

**Status (2026-07-24): left genuinely unconfirmed, recorded here explicitly so a future session doesn't assume it was silently settled by default.** What's built is minimal enough that it may well already satisfy whichever style was intended — but that's a guess, not a confirmation. Needs an explicit yes/no against the original intent, not an inference from the fact that something shipped.
