# Sonny Founder Design Decisions

Source: meeting transcript, Sauransh Bhardwaj + Bhavya Singh (design), 2026-07-05. This captures product/design decisions made verbally that are not fully reflected in `docs/sonny-major-release-spec.md`, `docs/sonny-design-system-reference.md`, or the wireframe exports. Treat this as authoritative over a naive reading of the wireframe SVGs where they conflict — the wireframes are a static snapshot of a design conversation, this transcript carries reasoning the static files don't.

## Notifications
Native macOS notifications for v1, not a custom overlay. Rationale: native respects Do Not Disturb and other system-expected behavior; a custom overlay would look wrong when it collides with/covers other apps' notifications. Explicitly open to revisiting later, not a permanent decision. Error-state notification: step-level failure is orange with a retry button; total task failure offers retry or start a new task.

**Decision (2026-07-20):** the floating widget has no dismiss/hide action and stays visible on screen permanently (`.floating` window level, all Spaces, over full-screen apps) — this is deliberate, not a missing feature. One direct consequence: the native notifications above, whose whole purpose is covering "user is in another app," can't actually fire in practice, since the widget is always the thing already in front of the user. Confirmed and accepted: notifications ship as real, working code that's simply unused for now, not a bug to chase — same "open to revisiting later" status as the notification choice itself. The real cost lands on scheduled/background routine execution (routine scheduling is on the roadmap, not yet built): a routine running with no one watching the widget has no working fallback today, so that work needs its own real answer (see `docs/sonny-ui-backend-roadmap.md`), not an assumption that today's widget-only UI already covers it.

## Tasks <-> Workspaces association
The Linear-style wireframe's "project" tag on each task row maps directly to **which workspace that task belongs to/ran in**. This is a real intended association, not wireframe-template leftover. Sonny's task history data model does not currently capture this — adding it is a real scope item, not optional polish, and it's also the prerequisite for the Insights "Breakdown by Workspace" feature (see below).

## Routines
- Routines have real intended scheduling: a defined run time and an enabled/disabled state ("what time does it run and is it enabled or disabled"), grouped by cadence (daily/weekly/monthly) same as the home/Tasks screen's status grouping. This is a real feature, not decorative wireframe grouping — it implies an actual scheduler/execution-trigger component that does not exist in the current build (routines today are manually triggered only).
- Clicking into a routine should open a **detail view styled like the floating widget (liquid glass material)**, but embedded inside the main app window, not the literal floating widget window. It closes when the app closes. Explicit intent: give the user one consistent "how I watch Sonny work" experience regardless of which surface (menu-bar widget vs. main app) they're looking from, rather than two different UIs for the same concept. This is a real, previously-undocumented System-B-inside-System-A UI requirement — not covered by the current System A / System B split in the design-system reference doc, which treats them as fully separate surfaces.

- **Decision (2026-08-04): a routine's browser comes from the routine's own steps — first browser-capable app wins, order-independent.** The first browser-capable app *anywhere* in a routine binds *all* of that routine's URL steps, regardless of step order: a URL step sequenced *before* the browser step still binds, and when a routine names two browsers the first in step order wins. This is deliberately byte-for-byte the rule workspaces already follow (`WorkspaceBrowserCatalog.firstBrowser(in:)`, reused rather than reimplemented so there is one definition of "browser-capable"), so that a routine and a workspace stay *one* mental model rather than two — "open Safari, then open github.com" means the same thing whichever surface it was saved on. Two alternatives were considered and declined, both for that same reason: **order-sensitive binding** (only the URL steps sequenced after the browser step bind), which would have made a routine's behavior turn on an ordering detail a workspace has no equivalent of; and **an explicit per-routine browser setting**, a second place to state what the routine's own steps already state. The cost of declining the setting, recorded so it isn't rediscovered as a bug: a routine that opens no browser cannot be made to prefer one without adding an app-open step to it.

  **The caveat travels with the decision: the binding follows a *seam*, not the word "URL".** It reaches every URL opened on the injected browser-opener seam — `.openURL`, `.openAppSearchURL`, and the Hacker News open, which all read `CapabilityExecutionContext.browserOpener` — and *not* `.playMedia`, which opens through `context.mediaOpener` and reaches `NSWorkspace.shared.open` directly, so a media step carrying an explicit `open.spotify.com`-style URL still lands in the system default browser. That gap is real, and **the founder decided on 2026-08-20 to leave it there** — see the entry below, which settles what this paragraph previously left open as SONNY-51. The unqualified "every URL the routine opens" was the original claim in both the changelog and the code comment, and it was too broad (PR #28, F4). Implemented in SONNY-24 on `feature/sonny-24-routine-browser-binding`; `RunRoutineCapabilityAdapter.browser(for:context:)` spells the same decision out at the code site.

- **Decision (2026-08-20, founder, SONNY-51): a media step's fallback link is playback, not the routine's browsing — it stays on the media seam.** A routine's browser binding does not reach `.playMedia`, and that is now a decision rather than an open gap. The alternative — giving `MediaOpening` a browser preference so http/https links route through the browser-aware open while `music://` and `spotify:` links keep going straight to the OS — was considered and declined.

  **What the seam actually does, measured at `031e308` rather than assumed, because the reach is narrower than "media URLs don't bind" suggests.** `context.mediaOpener.open` is called from exactly one place: the fallback taken when provider playback is blocked (not authorized, no Premium, no active device, no catalog match, provider outage). Of the ways that fallback can end, **two reach a browser unconditionally and one reaches it under a guard**:

  - Unconditional: an explicit `https://open.spotify.com/track|album/…` or an explicit `https://music.apple.com/…` supplied on the step. Those are opened as given.
  - Guarded: the Apple Music **catalog** result. `AppleMusicCatalogTrack.albumTrackAppURL` rewrites the scheme to `music://` *only when the host is exactly `music.apple.com`*, and returns the https `trackViewURL` unchanged otherwise — and `ITunesSearchAPIClient.bestTrack` takes `trackViewUrl` from whatever the iTunes Search API returns, with no host check of its own. (The same happy path also falls back to the https URL if `URLComponents` fails to reassemble.) In practice the API returns `music.apple.com`, which is what makes this a guard rather than a third open path; it is not an invariant this code enforces.
  - Neither: the Apple Music search fallback builds a `music://` URL and the Spotify search fallback builds `spotify:search:` — app-scheme, which the OS routes to the provider app with no browser in the picture.

  *(The first version of this paragraph said "only two endings reach a browser" and missed the guarded one — corrected 2026-08-20 by PR #81's review. The decision is unaffected: a third ending that can reach a browser is one more argument for leaving the routing to the OS, not fewer.)*

  **Why declined.** Forcing an https provider link through a named browser would override whatever handler the OS would otherwise pick. A user with Spotify or Music installed may well have those links claimed by the app, so binding could turn an app-open into a web-player open — a worse result than the inconsistency it fixes. That cannot be measured from this repository, because it depends on what each user has installed, and an unmeasurable downside on the common path is not worth trading for a cosmetic win on a narrow one.

  **The cost of the decision, recorded so it is not rediscovered as a bug.** A routine that opens a browser, whose media step carries an explicit https provider link, and whose provider playback is blocked at run time, opens that one link in the system default browser while every other URL in the same routine opens in the routine's browser. All three conditions are required. It is not a regression — it is the pre-SONNY-24 behaviour, left in place on one seam deliberately.

- **Decision (2026-08-06, founder batch Q5, Sauransh + Bhavya): ONE trust toggle per routine — the same grant covers scheduled and manual runs.** A routine the user has marked trusted skips the every-run tier-2 prompt when run by hand exactly as it already does on its schedule; label copy chosen verbatim: *"Trust this routine — runs tier-2 steps without asking, scheduled or manual."* Tier-3+ always prompts — the structural backstop in `AgentRunner` is untouched by the grant, on either path. The two-toggle alternative (separate scheduled and manual trust) was considered and declined: more surface, and it reintroduces exactly the two-mental-models confusion the one-toggle shape exists to avoid. Recorded rationale: per-routine, opt-in, same tier ceiling, and presence is safer than absence — the pre-decision state trusted the user's absence (unattended runs) more than their presence (manual runs), which is backwards. Implemented in SONNY-54 on `feature/routine-trust-manual-runs`; backfilled here by that branch's PR #34 review (cycle 2, F2), per the SONNY-53 precedent that founder decisions recorded only on tickets get an entry in this document.

## Insights

The wireframe export's actual layout (stat cards + full-width chart + full-width sections, stacked) does not reflect this stated intent — the verbal description is more authoritative here than the static SVG.

  **Gap confirmed, deliberately deferred (2026-07-24):** `InsightsView` in `Sources/MacAgent/CommandCenterView.swift` (line 537) is, as of this date, exactly the rejected pattern above — a plain `VStack` of three equal-width stat cards (`InsightsOverviewBento`, an `HStack`) followed by three full-width panels stacked below (`WeeklyCompletionChart`, `WorkspaceBreakdownPanel`, `TaskHistoryListPanel`). No grid, no varying tile sizes, no real asymmetry. An earlier commit (`986c98d`, message: "restructure stat cards into an asymmetric bento grid") did not actually produce one — worth knowing the commit message overclaimed what landed, so it isn't mistaken for evidence this was already resolved. **Explicit decision: not fixed now.** This is queued for the last review/final-updates branch before the v1 release, not this branch — flagged here specifically so it survives as a real, findable item rather than being silently dropped or, worse, mistaken for "already handled" because a past commit message says it was. Whoever picks it up needs an actual product/design decision first (a real grid with varying column/row spans is a genuine layout redesign, not a small tweak) — this note plus the code pointer above is the starting context, not a ready-to-implement spec.
- Deliberately do **not** show usage/quota-consumption metrics (e.g. "you've used X% of your plan") on this page. Reasoning is explicit product strategy, not an oversight: it creates subscription-cancellation anxiety in heavy users and "am I getting my money's worth" doubt in light users. Take inspiration from Whisper Flow's insights instead — positive, non-anxiety-inducing stats like most-used app, most common action taken.
- A Spotify-Wrapped/"top 1%" style celebratory personal-usage insight is a deliberate v2/v3 idea, not v1 scope (needs a real user base first for the comparison to mean anything).
- A "Data Sent to AI" inspector — showing exactly what content/artifacts get sent to the external LLM provider — is an explicit, named competitive differentiator versus Clicky, which does not surface this anywhere in-product (only in a privacy policy page). Framing matters: must read as transparency, not as "we're just an API wrapper" — messaging needs care.

- Card fields, confirmed real: workspace name, who's in it (solo vs. team — "team" ties to a future Enterprise tier, not v1's primary solo-user case, but the field/UI pattern should still exist), task count, and the apps in the workspace shown as an overlapping icon stack.

## Workspace restriction scope (roadmap row B)

Founder decisions taken by Sauransh with the co-founder on 2026-08-04, recorded on SONNY-12, plus the planning decisions SONNY-12 itself produced and the user approved the same day. This is the durable record for roadmap row B (`feature/workspace-restriction-scope`) and for row C, which is gated on it.

**Full planning rationale, including the per-operation resource-classification table, the architecture, and the analysis behind every decision below: `docs/sonny-branch-b-plan.md`.** The Plane tickets are the binding contracts; that document is the reasoning behind them. This section is the durable decision record and should be read first.

**The four founder decisions, verbatim in substance:** scope constrains **apps + web domains + file locations** (the complete model — the planning cost of file-scoping was accepted knowingly); scope is **on by default** for all workspaces, not opt-in; an out-of-scope action **escalates and prompts** ("this isn't part of X workspace — allow anyway?"), never hard-blocks; a task belongs to a workspace when **started from its card OR named in the command**.

### The model: a scope verdict has four values, not two

For any resource a plan touches, its verdict against the bound workspace is `.inScope` (matches an entry in that kind's list), `.outOfScope` (that kind *is* configured and the resource matches nothing in it), `.unconstrained` (that kind is *not* configured on this workspace — an empty list), or `.opaque` (the resource is not knowable from the plan at all). Only `.outOfScope` escalates. Only `.inScope` is ever eligible for row C's relaxation.

The empty-list case is the load-bearing one, and both two-valued readings fail against real persisted state rather than hypothetically. "Empty means deny all" would escalate every file action in every workspace on the day this ships, because no workspace on disk has file locations — the field does not exist yet; and `CreateWorkspaceCapabilityAdapter` requires *at least one* of apps or URLs (`guard !apps.isEmpty || !urls.isEmpty` throws only when both are empty, `:81-85`), so apps-only and URLs-only workspaces are already normal valid states that would each be broken on the kind they never declared — as is the both-populated case, which is equally valid and equally reachable. "Empty means allow all" would blanket-bless every path on the machine for any workspace without file locations, which is exactly the hazard SONNY-12's interaction flag named. `.unconstrained` means "this workspace has said nothing about this kind of thing" — neither permission nor prohibition, producing zero new prompts and zero new relaxation.

**Derived clarification, stated because it reads as a contradiction otherwise:** scope is default-on *per workspace*, not *per task*. A one-off command that names no workspace and was not started from a card is unscoped — no scope, no escalation, no relaxation. A task that is not in a workspace has no workspace scope to be inside.

### Resolution of the recorded interaction flag (default-on scope × row C's in-scope tier-3 downgrade)

The flag asked whether tier-3 relaxation needs an explicit per-workspace opt-in even though scoping itself defaults on. **Decided: no separate opt-in toggle.** Three structural gates, each independently sufficient:

1. **Relaxation is earned per resource kind, not granted per workspace.** Listing `~/Documents/ClientAlpha` on the workspace *is* the explicit act. A user who never configured scope is `.unconstrained` on every kind, and `.unconstrained` never qualifies for relaxation — so the flag's exact scenario is structurally impossible, not merely discouraged. A separate toggle would add a second consent surface for the same consent, which is how a security control ends up left in the wrong position.
2. **Relaxation must be a *requirement* override, never a tier change.** Row C must map `(tier, verdict) -> RiskApprovalRequirement` directly and must never lower `effectiveTier`. Things depend on that field staying honest — and the closed list of four this line first carried was incomplete (*count corrected 2026-08-13, SONNY-100: 151 references across 24 files at `0fdac1c`, and a fifth structural decision gate the list missed — SONNY-54's manual-routine-trust check in `AgentViewModel`, whose own comment says it mirrors `AgentRunner.execute`'s gate; also unlisted: the approved-tier write-back, `RiskApprovalError.errorDescription`, and the tier handed to `approvalCopy(for:metadata:tier:)`*). The gates: the unattended gate (`approvedTier >= effectiveTier` against a fixed `.approved(.tier2)`), the stale-approval re-check inside `AgentRunner.execute`, the `risk.assessed`/`risk.escalated` trace, `UnattendedTrustAdvisory`, which reads `effectiveTier` only, and the manual-routine-trust check above. **And the composition trap, which is the single most likely way this ships as a security regression:** row C decided both that in-scope tier 2 auto-runs *and* that in-scope tier 3 drops to a lightweight confirmation. If the tier-3 rule were implemented as a tier change (3 -> 2), the tier-2 rule would fire next on the result and in-scope tier-3 actions would silently auto-run. One function of `(tier, verdict)`, never two chained rules. (`InvokeShortcutCapabilityAdapter` *does* lower `effectiveTier` on clean observed run history — that trust is earned by observed successful runs; "the user typed this folder into a list once" is a weaker signal and must not buy the same structural power.)
3. **Scope answers "right place," never "right severity."** Which tier-3 *causes* stay at explicit approval regardless of verdict is row C's call, not row B's. The finding that makes it answerable: **no capability in v1 has a default tier of 3.** Every tier 3 reachable today comes from an escalation, and **every escalation site raises *to* tier 3**. So row C's tier-3 clause is entirely about escalated tier 3 today; the spec's real tier-3 capabilities (send, upload, delete, submit, purchase, share — §11.1) do not exist yet. **Count corrected 2026-08-13 (row C planning, PR #45 review residual): there are 8 such sites, not the six this line first recorded** — row B itself added the other two, and they are precisely the two that break the phrasing generalisation this line used to make. Six say some form of "X already exists": three use the literal *"already exists and would be replaced"* (`SaveRoutineCapabilityAdapter.swift:69`, `SnippetSaveCapabilityAdapter.swift:68`, `CreateWorkspaceCapabilityAdapter.swift:85`), three name a colliding output path (`LargestFilesZipCapabilityAdapter.swift:89`, `WebResearchMarkdownCapabilityAdapter.swift:119`, `CreateLocalDraftCapabilityAdapter.swift:67`). Row B's two say neither — the out-of-scope escalation (`AgentActionExecutor.swift:458`) names a resource that is not part of the workspace, and `edit_workspace`'s removal escalation (`EditWorkspaceCapabilityAdapter.swift:228`) names what a removal costs. What was load-bearing for gate 3 was always the tier, not the sentence, and that half held at both counts. *Scope, method and SHA:* syntactic construction sites in `Sources/` only, from `grep -rn "CapabilityRiskEscalation(" Sources/`, cross-checked against a `toTier:` sweep (10 lines; the two extras are the type's own property and `init` in `RiskApproval.swift`, and no site in `Sources/` **or** `Tests/` sets a `toTier` other than `.tier3`), against `.init`/factory/`escalations`-array indirection, and against a dead-code and compile-flag pass — **re-measured against `main` at `ae1ca3c`** (the PR #44 / row F merge), which this docs-only branch leaves byte-identical (`git diff ae1ca3c..HEAD --name-only -- Sources/ Tests/` → zero paths). The count was first taken at `0fdac1c` and was **8 there too**; row F moved three of the line numbers above without adding or removing a site, which is exactly why the number and the lines are stamped rather than stated bare. A site is not a runtime escalation: `EditWorkspaceCapabilityAdapter.swift:228` sits in a `compactMap` over the edit's lists and can emit one per scoped-resource kind.

Row B ships the verdict and uses it **only to escalate, never to relax.** No relaxation ships in row B. Row C inherits `CapabilityRiskAssessment.scopeVerdict` as a typed input plus the two constraints above.

### The guarantee is static and pre-execution, and says so

`AgentRunner.execute` gates once, entirely up front — the requirement is checked before `AgentActionExecutor.execute(plan:)` is ever invoked — and `executeChain` runs every segment with no re-gating, which the conventions forbid adding. So "allow anyway?" lands as a pre-execution, whole-plan prompt identical in shape and timing to every existing risk escalation. **No pause/resume/checkpoint infrastructure is needed**; this was the largest thing the planning phase de-risked.

It is also why `.opaque` is necessary rather than a fudge. A resource discovered only at execution time has no gate left to escalate at — the one gate already closed. Three real cases: a Shortcut's internals (Sonny shells to `shortcuts run <name>` and cannot see inside), search-driven web research (its real URLs come back from the search provider at execution time), and anything future with the same shape. These never escalate on scope grounds and are **never eligible for relaxation**; the plan-level roll-up is `.inScope` only if every resource was statically knowable, at least one matched, none is out of scope, and no step is `.opaque`. A plan containing a Shortcut therefore can never be relaxed, because Sonny never saw what it touches. Silently treating an unseeable resource as in-scope is how a scope feature grants exactly the permissions it cannot verify.

### Scope reuses the workspace's own contents

`apps` and `urls` serve as both "what opens when I open this workspace" and "what is in scope," with a new `fileLocations` alongside them. The rejected alternative — separate `scopeApps`/`scopeDomains` lists — means users maintain two lists that are 95% identical, a DRY violation at the product level and a guaranteed source of "why did it prompt, it's right there in my workspace." An in-scope-but-not-launched app, if ever genuinely needed, is an additive field later.

**Non-goal, recorded so it isn't read as an oversight:** file locations do not auto-open when a workspace opens. Changing `open_workspace`'s behavior is not part of a restriction-scope ask.

### Task binding is per-task; the persistent active-workspace rejection still stands

"Named in the command" reuses `WorkspaceTaskTagging.resolvedWorkspaceName` unchanged — it already does the phrase matching with the stores' own case/diacritic folding, a documented leftmost-then-longest tie-break, and deliberate non-`\b` boundary checks. "Started from its card" does not exist today: `openWorkspaceWidget` only synthesizes the literal `"Open my X workspace"`, so the card can start exactly one kind of task, and that path is not even a distinct signal from the free-text one.

The binding row B adds is **per-task**: set at dispatch, cleared the moment the task reaches a terminal state, never inherited by the next command, never rendered as a global mode. That distinction is the entire reason the earlier rejection is not being reversed. The persistent active-workspace concept was explicitly considered and rejected (see the changelog's task-to-workspace-association entry) because it silently mis-tags unrelated one-off tasks and leaks state across surfaces; the wireframes' evidence for it — the Home screen's "Personal" scope pill, the Workspaces screen's green "Active" badge and Open-vs-Switch branching — remains deliberately unbuilt. A reviewer of row B should check this hardest.

Scheduled runs are unscoped. A stored routine cannot contain `create_workspace` or `open_workspace` (`SaveRoutineCapabilityAdapter.validateRoutineSteps` rejects both), so a scheduled routine has no workspace binding available. Worth stating because it removes the one genuinely dangerous interaction: an out-of-scope escalation to tier 3 inside a scheduled routine would otherwise skip that run and, per SONNY-10, usually every future run too.

### Spec conflict, and how it resolves

§10.1 puts an "App/folder/domain scope" field on every capability declaration and §10.4 lists "Scope validation" among seven layers with "If any layer rejects, the action must not execute" — a hard block, which contradicts escalate-and-prompt on a literal reading. **Resolution: these are two different layers and both are correct.** §10.1/§10.4's scope is the *capability's own* declared operating bounds (an app-opener can only open allowlisted apps; a file capability can only touch the whitelist) and stays a hard block, because it describes what the capability is physically able to do. Workspace scope is a new, *user-declared* layer above it that escalates. **A workspace scope can never widen a capability's own bounds or `PathWhitelist`** — it only narrows, and it narrows by asking rather than refusing. One direct consequence: a workspace file location outside `~/Desktop`/`~/Documents` is inert, because `PathWhitelist` rejects the path before scope is ever consulted, so it must be validated and reported at save time.

The spec is amended in row B (SONNY-42): §6.9, §10.4, §11.2, §11.3, §9.2, §9.3.

### Editing a workspace escalates on removal, not on widening

`edit_workspace` is tier 2 (§11.1 lists "Change routine/workspace" as tier 2, and `CreateWorkspace` already is), escalating to tier 3 when an edit **removes** entries. The nearest precedent is the replacement-escalation family, but the copy there is less uniform than a quick read suggests: of the six escalation sites that existed when row B was planned, only `CreateWorkspace`, `SaveRoutine` and `SnippetSave` say "already exists and would be replaced"; `CreateLocalDraft`, `LargestFilesZip` and `WebResearchMarkdown` say only "… output already exists at `<path>`". (Row B then added two of its own — 8 sites at `ae1ca3c`; see the corrected count above. Both of row B's departed from the template, which is the point this paragraph was making.) The requirement is that the reason names what is actually lost, not that it matches a template.

**Rejected alternative, recorded:** escalating on *widening* instead. Widening does weaken the boundary, but the user typed the command asking for it, and putting explicit approval in front of normal setup taxes exactly the action the feature depends on.

**Forward flag — answered by row C (SONNY-98), 2026-08-13.** The flag as raised, kept for its reasoning: the rejection above rests on a *row-B* cost argument, and row B is the phase where being in scope buys nothing. Row C changes the trade: Gate 1 makes relaxation earned by listing a resource, so once relaxation is live, an ungated tier-2 edit that adds `~/Documents` to a workspace converts a large share of the filesystem into relaxation-eligible territory **in one un-escalated step** — the same hazard class the interaction flag was raised about, arriving through the edit path instead of the default path. Gate 1 does not already cover this: it answers which verdicts qualify for relaxation, not whether the act of creating a qualifying verdict should itself be gated. **The answer** is in "Approval relaxation (roadmap row C)" below — the origin grant never covers a boundary-changing edit, and adding a whitelist root itself escalates to tier 3 with a consequence-naming reason. *(That answer was itself superseded 2026-08-13 by "The consequence rule" below: the widening escalation survives with its consequence-naming sentence, classified advisory, so the root add now runs with the sentence on the ran-without-asking trace instead of a prompt. The hazard the flag named — one un-escalated step converting a large territory into relaxation-eligible ground — dissolved with the grants themselves: being in scope no longer buys silence, so there is no relaxation-eligible territory left to manufacture.)*

### Removing the last entry of a kind silently un-restricts that dimension

The sharpest edge in the model, and the generic removal rule above does not catch it. Removing one of several entries leaves the kind configured — non-matching resources still resolve `.outOfScope` and still escalate. **Removing the last entry empties the list, and an empty list is `.unconstrained`, so that entire dimension stops escalating on anything.** The user consents to losing one folder and actually loses file-scope enforcement for that workspace.

A test that removes one entry from a two-entry list satisfies a generic "removal escalates" criterion while never touching this case, so the flip carries its own requirement, its own acceptance criterion, and its own reason copy on SONNY-40: **when a removal empties a kind, the prompt says the dimension is no longer restricted rather than naming the entry.** "Removed ~/Documents/ClientAlpha" and "this workspace will no longer restrict file locations at all" are different consents.

### A configuration surface is what makes this a feature at all

Spec §6.9 requires "Edit workspace"; it does not exist. The only UI mutations on a workspace are mark-as-team and delete, and a code comment records a detail view being previously rejected as "inventing a surface to solve a placement problem" for a delete button. Without an edit path, `fileLocations` can never be set, every file resource stays `.unconstrained` forever, and one of the three founder-specified dimensions does nothing. **Decided: ship both** — an `edit_workspace` capability (natural language, matching how workspaces are already created) and a workspace detail sheet that shows the boundary. A boundary the user cannot see is a boundary they cannot trust, and "show workspace contents" is a §6.9 requirement in its own right.

**Wireframe exception, stated rather than silent (per CLAUDE.md's rule):** `13-MainAppWorkspaces.svg` is a card grid only; no wireframe exists for a workspace detail surface. It is net-new UI in **System A** — flat, opaque, Inter, zero shadows. It does *not* inherit the routine-detail view's System-B-inside-System-A treatment, because liquid glass was tried for workspace cards and explicitly reverted as too distracting (see the Workspaces section above).

### Sequencing, and things that will bite the implementer

Row B's assessment ticket edits `AgentActionExecutor.assessRisk`, which SONNY-29 is rewriting into a segment-walking shape, and SONNY-29 -> SONNY-31 -> SONNY-24 is a declared serial sequence over that surface. **Row B's assessment work starts only after SONNY-29 merges.** This is not just a merge-conflict concern: today `assessRisk` hands each deduplicated adapter the entire unsegmented plan once, so a plan with two steps of the same operation only ever has the first assessed — a scope check built on that shape would check the first URL in a two-URL plan and silently ignore the second.

Found during planning, each one a bug waiting:

- **`WorkspaceStore.save` fully replaces the record**, unlike `RoutineStore.save`, which merge-preserves `schedule`/`recentRunDates`. Re-creating a workspace by natural language would silently delete its boundary — and that path escalates to tier 3 *for replacing the workspace*, so the user consents to replacing contents, not to dropping a security boundary. It needs the same merge-preserve treatment.
- **Three app/URL touches bypass every existing allowlist**, with no plan field naming them: `MicrosoftWordDocumentConverter` AppleScript-controls Word from a hardcoded path, `NativeMediaOpener` opens provider URIs through its own private prefix check (bypassing both `MacAppCatalog` and `SafeURL`), and `AppleScriptFinderContextReader` controls Finder. Resource classification must be **per operation including implicit resources**, never per field. `open_app_search_url` is the other half of the same lesson: it carries `appName`, but that field holds a search-target name like "GitHub" and its real resource is the host baked into the template.
- **New persisted fields must be `Optional`** — synthesized `Decodable` calls `decode(_:forKey:)` for a non-Optional property even with a Swift-side default and throws `keyNotFound` on every existing `workspaces.json`. Already documented twice in `AutomationStores.swift`.
- **`AgentPlan.requiresConfirmation` gates nothing**: 22 construction sites in `Sources/` (16 in `InstantCommandResolver` alone), and nothing branches on the value. It is read once outside its own initializer — `AgentActionExecutor.swift:990-996`'s `segmentPlan` copies it into every chain segment — which makes it a worse trap, not a safer one: a scope flag wired through it would visibly propagate into segments while still gating nothing, so it would look wired up. Do not use it.
- **Power Mode is spec-only** — zero implementation anywhere in `Sources/`. §13.3's per-app "Allowed domains if browser" is not code this work can extend or collide with.
- **Stored `apps` are raw user strings** — "Chrome" and "Google Chrome" both persist as typed — so matching must canonicalize both sides through `MacAppCatalog.resolve` to a bundle identifier. Stored `urls` are full URLs, not domains, so domains derive from `SafeURL.validateWebURL(...).host` and match as `host == d || host.hasSuffix("." + d)`, never as a substring (`notgithub.com` contains `github.com`). File matching reuses `PathWhitelist`'s own containment rather than a second path comparison — divergence on `..` or symlinks between two implementations is a security bug, not a style one.

**Open question inherited rather than invented:** `save_routine` folds its nested plan's escalations onto the save itself (SONNY-10's largest recorded finding; SONNY-33 reframes the copy). Scope asks the identical question — does a routine that *references* an out-of-workspace path put the *save* out of scope, or only the run? **Decided for row B: only the run.** Saving a routine touches one file inside Sonny's own store, so `save_routine`'s own scoped resources are none, and the routine's steps are scoped when it actually runs. This keeps row B consistent with SONNY-33's decided direction instead of quietly contradicting it.

## The consequence rule (2026-08-13 — supersedes the row-C relaxation charter below)

**Founder directive, issued 2026-08-13 after row C's ratified scope-conditional relaxation was built and had passed review, before merge: Sonny asks permission only when an action is destructive — it destroys or replaces existing user data or user-built artifacts (file overwrites, replace-on-save of routines/workspaces/snippets, deletions) — or affects someone other than the user (send/post/share/publish/purchase). Everything else runs without asking**, made legible by the ran-without-asking trace SONNY-99 built. This supersedes the 2026-08-04 charter and the origin grant below wholesale — where the old preconditions (row B's scope gating, the frozen row-C plan's charter, the in-scope/origin grant conditions) conflict with the rule, the rule wins — and the grant machinery was deleted on the same branch rather than left dormant.

**Mechanics.** Every escalation carries a consequence class — `destructive`, `affectsOthers`, `advisory` — assigned at its construction site with no default, so a new escalation cannot land unclassified; when genuinely ambiguous, a site classifies fail-closed (ask) and is flagged. All nine sites at the pivot: the six replace/collision escalations (routine/snippet/workspace replace-on-save; zip/markdown/draft output collisions) are destructive; the out-of-scope escalation, both workspace-entry-removal wordings, and the whitelist-root widening are advisory. `affectsOthers` is **armed but empty** — no v1 capability reaches anyone but the user — so vision actions arrive into a class that already asks. The mapping: any asks-first escalation asks at every tier that can run (the rule decides, not the tier arithmetic); tiers 0–2 otherwise auto-run unconditionally; advisory-only tier 3 auto-runs with its reasons named verbatim on the trace; an escalation-free tier 3 fails closed to an explicit ask; tier 4 refuses.

**Coordinator operationalization calls, recorded and founder-vetoable:** (1) destructive always asks — there is no relaxing it; (2) affects-others is an armed-but-empty class today; (3) out-of-scope escalations, ALL workspace sheet edits (add, remove, dimension-emptying removals included — consciously superseding the week-old Q4 ratification), and the `PathWhitelist`-root add auto-run with the trace, from any origin (the classification is origin-blind). (4) What survives unchanged: tier-4 refusals; Safe mode, evaluated first, asking for everything — the cautious user's opt-back-in, still the seam SONNY-90 backs with Settings; the scheduled/unattended ceilings (every tier-3 an unattended run can reach is destructive — unscoped runs raise no out-of-scope advisory and `edit_workspace` cannot be a routine step — so it still asks and the tier-2 standing grant still pauses the schedule); and the branch's chassis — the ONE public requirement function with its exhaustive no-default switch, the SONNY-99 trace, and the SONNY-62 consent machinery, which now applies to whatever still asks.

**Consequences worth naming rather than discovering:** the manual half of SONNY-54's trust toggle is subsumed (nothing tier-2 asks anymore, trusted or not — the toggle's remaining door is the unattended one, and its tier-2 ceiling still refuses destructive routine steps by hand or on a schedule); the policy dials (`requireApprovalForTier1`, `tier2Mode`) no longer gate the ordinary path — `requireApprovalForTier1` has no observable effect anywhere and `tier2Mode == .previewOnly` shows only inside Safe mode — kept pending a founder decision on deleting them; `lightweightConfirmation` is no longer produced by the mapping at all, which likely collapses SONNY-101's lightweight-vs-explicit contract (flagged on the ticket for the founder, not decided); and workspace scope verdicts survive as data — computed, stored, rendered — gating nothing, with the out-of-scope fact traveling on the trace.

## Approval relaxation (roadmap row C)

> **SUPERSEDED 2026-08-13 by "The consequence rule" above — same day this section's design was
> ratified, before it merged.** Kept as the record of the superseded design; the grants below no
> longer exist in code.

Planned by SONNY-13, **founder-ratified 2026-08-13 — all ten planning questions as recommended, no modifications.** Full rationale: `docs/sonny-row-c-plan.md` (frozen). Shipped by `feature/approval-relaxation-structural` (SONNY-97/98/99); the surface half (`feature/approval-relaxation-surface`, SONNY-101 + SONNY-50) is separate and later.

**The charter (founder decision, 2026-08-04, deliberately beyond the conservative recommendation, which was offered and declined):** being inside a workspace's scope *reduces* prompting — in-scope tier 2 auto-runs, and in-scope tier 3 drops to a lightweight confirmation.

**The two grants, and why the origin grant exists at all.** `inScopeWorkspace` is the charter's verdict grant. `directUserAuthored` covers a plan the user built field by field on a UI surface (`PreparedPlanSource.directUserAction` — the workspace detail sheet is the first caller). It is load-bearing, not gold-plating: `edit_workspace` and `create_workspace` classify as `.none` scoped resources — a workspace's contents in an edit are *declared*, not touched — so a sheet edit produces zero findings, rolls up `.unconstrained`, and can never be `.inScope`. The verdict grant structurally cannot reach the friction the founder reported on 2026-08-07 (the sheet re-prompting for every Add/Remove); the origin grant is the only thing in the design that can. The two are kept as separate cases even though they map identically today, because "because this is inside Client Alpha" and "because you built this on screen" are different facts a user can act on.

**One function, and the strengthened invariant.** Both grants resolve in one exhaustive `(effectiveTier, grant)` switch — `RiskApprovalPolicy.requirement(for:context:)`, the sole public path to a requirement (there were three; two wrappers removed, the tier-only baseline demoted to private). Safe mode returns before the grant is computed. Relaxation never writes `effectiveTier`, `escalations`, **or `approvalCopy`** — the last two are the ratified 2026-08-13 upgrade to row B's constraint, because escalation reason strings render independently on three surfaces, so tier honesty alone does not mean "nothing user-visible changed". Relaxation changes the weight of the ask, never the sentence. Rows H and I land as *inputs* to this function (`safeMode` now, per-app consent as a future `ApprovalContext` field), never as rules applied to its output.

**The boundary-changing-edits rule (the row-B forward flag's answer, SONNY-98):** *the origin grant covers edits that move entries within a boundary; it never covers an edit that changes whether a dimension is a boundary at all.* Concretely: the first entry into an empty dimension, a removal that empties one (by the evaluator's canonical answer, so an all-inert dimension counts as empty), and an added folder that subsumes a stored entry all drop the origin grant and prompt as before; every other sheet edit auto-runs. On top: adding a `PathWhitelist` root itself (`~/Desktop`, `~/Documents`) as a file location escalates to tier 3 with a reason naming the consequence — the whole territory one entry converts. **Scoped to `.fileLocation` as a stated decision, not an omission:** file locations are the only kind matched by containment; `.app` has no hierarchy at all, and `.webDomain` is bounded by `SafeURL` and the specific host the user typed. The emptying removal keeps explicit approval — the sharpest edge in row B's model is now also the single edit that changes what the whole relaxation system does for that workspace, and it is rare, so excluding it costs near-zero friction.

**Default-on, Gate 1 restated (re-ratified 2026-08-13):** listing `~/Documents/ClientAlpha` on the workspace *is* the explicit act; no separate per-workspace relaxation toggle, which would be a second consent surface for the same consent. The declined alternatives (opt-in per workspace, trust-graduated relaxation) are recorded in the plan §7 so they are not re-litigated from scratch.

**The `.runRoutine` exclusion and its accepted cost:** routines are eligible for *neither* grant — SONNY-54's per-routine trust toggle stays the single door for skipping a routine's tier-2 prompt, scheduled or manual, because without the exclusion an untrusted routine running inside a workspace would auto-run through a second door the founder never opened, on its first run, with its arbitrary steps unreviewed. Scope answers "right place", never "right severity" — and never "right thing". The accepted cost: a user may ask why their routine still confirms inside a workspace where typing the same command does not. `.invokeShortcut` is excluded too — belt-and-braces on the verdict axis (already `.opaque`), load-bearing on the origin axis, which never consults the verdict.

**Visibility (SONNY-99, ratified as required, not optional):** we do not ship silent execution without a trace. A run that executed unprompted *because a grant made it silent* carries a one-line ran-without-asking trace on the widget's result panel naming the grant's reason; tiers 0/1 never trace (they auto-run in every grant column, and a trace there would make the signal meaningless), and a run that prompted never traces (the prompt was the disclosure). The one-line rendering is a founder-approved wireframe exception, bounded to one line of existing-token text on an existing surface.

**What has no user-visible effect yet, said here so no record overclaims it:** the in-scope tier-3 lightweight confirmation renders identically to explicit approval on every surface until the surface branch (SONNY-101) ships. The friction row C's structural branch actually delivers is in-scope tier-2 auto-run and the sheet-edit origin grant.

Three behavioral decisions worth not re-litigating:

- **Default is expanded, and the persisted value is the *collapsed* set.** Only that representation makes an absent or empty preference mean "everything expanded" — including for a section that did not exist when the value was written, which matters because `TaskHistoryGrouping.groupedByOutcome` drops empty sections, so the page's sections genuinely come and go.

It does *not* live on `AgentViewModel` beside `usePointerCursors`/`displayFullNames`, though: nothing outside this one page reads it, so shared published state would have exactly one observer. That departure from the two-preference precedent is deliberate; the rule that mattered (plain `UserDefaults`, not `LocalStorageEncryption`) is the one being followed.

A second, narrower gap is recorded with it: a shell *inside* an app that is not a terminal is controllable, and that one does not even narrow with more entries.
  **Extended 2026-08-17 — the list is eleven, and the eleventh has its own provenance (SONNY-102).** Termius is added as `com.termius-dmg.mac`. The ground is the rule rather than the word "terminal": spec §7.4 defines a terminal as arbitrary shell execution with the user's full rights, and an SSH session meets that test on the *far* machine. The list had been built around terminal emulators, which is narrower than the rule it implements, so this **aligns the list with the rule rather than widening the rule**. Not hypothetical: Launch Services reports Termius as the founder's machine's default `ssh://` handler, ahead of Terminal and iTerm. **Condition one now has three groups, not two** — one read from a bundle's own `Info.plist` (`com.apple.terminal`), one established from Launch Services' handler registry on 2026-08-17 (`com.termius-dmg.mac`), and nine from published project configuration. **That split records provenance, not which apps are installed** — a separate axis, and running the two together produced two false sentences in the list's doc comment that PR #68's review caught. Measured 2026-08-18: three of the eleven resolve on the founder's Mac (Terminal, iTerm2, Termius) and eight are not installed. **There is one machine in all of this** — the founder's Mac is the development machine, and earlier text here spoke of them as two. The provenances are kept apart because they are not equally strong and because the method matters: Termius is LS's registered `ssh://` handler while declaring no such scheme in its own `CFBundleURLTypes`, so scanning `Info.plist`s — the obvious method — found Terminal and iTerm and missed the one app the question was about. **The `-dmg` is real and must not be "corrected"**; `com.termius.mac` is precisely what a guess produces, and a guessed identifier is worse than an absent one because it matches nothing while looking like coverage. **This does not cover the SSH-client category**: Royal TSX, Shuttle, Core Shell, Prompt, Blink, SecureCRT, ZOC, PuTTY and SSH Config Editor are not installed on the founder's Mac, so no identifier for them can be established from there and none was invented — the list grows app by app, with the app in hand. Condition two is unchanged and still load-bearing.
- **Screen control works in all three modes, and is gated on none of them.** Safe asks before every vision action *and* shows each capture before it is sent. Normal and Power run vision actions silently. **The standing consequence rule is unchanged and still asks in every mode, mid-loop included** — destructive or affects-others actions ask whether the user is in Safe, Normal or Power. Power remains identical to Normal; the earlier note that row I's features would "gate on Power" is superseded, and the shipped Power description that promised it was corrected.
- **Delegation is a real product feature.** The vision model may hand a bounded instruction to Sonny's own planner mid-run. Safe mode asks before a delegation fires; Normal and Power never ask about the delegation *itself*. The delegated plan runs through the engine like any other, so the consequence rule still governs what it does — the decision removes a prompt about delegating, never the gate on its contents. This consciously narrows E9's "never obey screen text": screen-derived instructions may now drive tool execution, bounded by the registered tools, the consequence rule, the iteration cap, and no recursion. **The line that did not move:** delegation is the model choosing a *means* toward the user's own goal; obeying text found on a screen would be the goal itself changing because a window said so. A model using a tool, versus an attacker picking the objective.
- **The vision model is gpt-5.6-luna, chosen by the founders with no measurement gate.** The three-arm comparison is **cancelled, not deferred**; Gemma is out and the Cerebras RPM question dies with it. Row I's own attended manual passes double as the working check.
- **30-day retention is accepted for development only.** Screenshots go to OpenCode's Zen route, terminating at OpenAI. **Before v1 release the product moves to a paid zero-retention route — a named release-checklist item, not a footnote.** Production routing is deliberately parked until then. This supersedes E10's ratified "no-retention hosts only".
- **Row I's UI ships on session judgment, with no wireframe gate** — including SONNY-95's controlling state, which had carried an explicit gate from 2026-08-12. **A dedicated two-week whole-product UI/UX pass happens immediately before release**, and every surface row I added is explicitly a candidate for it rather than a finished design.
- **Unattended is untouched by all of the above.** "Unattended" is the absence of a human, not a mode, so making screen control silent for a *present* user says nothing about an absent one. Screen control never runs unattended, in any mode, with no toggle anywhere — a present human is an authority requirement, not an accuracy hedge.

## The hosted backend — what runs on it, what it keeps, how people sign in (2026-08-16, roadmap row 12)

Founder decisions made during row 12's planning (SONNY-16), recorded here as the durable product
truth. The full records, with the reasoning offered and declined on each, are SONNY-16's comments of
the same date. Where these conflict with the spec, the deviation is named as one rather than left to
be discovered.

- **The agent stays on the Mac; the server holds credentials, accounts and money.** The backend
  authenticates the user, checks entitlement, meters usage, retains content, and forwards to the
  model providers. Planning, the risk engine, the consequence rule and the screen-control loop stay
  local. **The boundary is anything that needs a provider credential** — six of the nine files that
  make network requests. The three that need none (`HackerNewsService`, `MediaPlaybackService`,
  `WebResearchService`) stay local by decision, with the tradeoff named: the user's own IP reaches
  those hosts, where proxying would hide it. That is a privacy question, not a billing one.
- **This is §16.5, not a deviation from it.** What *is* a conscious deviation is **not building §9's
  server-side agent loop in v1**. Three grounds, none of which is effort: the safety gate stays local
  and structural, so a network hiccup never participates in deciding whether an action is
  destructive; §9.2's state model would force screen-derived observations into server task state as a
  structural requirement rather than a bounded, disclosed choice; and §16.3's guarantee that free
  local capabilities survive an unreachable network would become false, since under §9 creating a
  task at all needs the server.
- **The backend keeps full request and response content for 30–90 days** — redacted screenshots,
  command text, model replies and **voice audio** — disclosed on the website's terms and privacy
  pages. Three named purposes, all chosen deliberately: debugging and support, product analytics, and
  training or fine-tuning a model. The coordinator recommended metadata-only and set out the case
  against; the founder decided otherwise with that case in front of him.
  - **This deviates from §16.5's "Request logging excludes sensitive content by default."** §16.5's
    other four requirements are met in full. Named as a deviation so a later reader does not have to
    reconcile the two on their own.
  - **It is not a reversal of the 2026-08-14 transparency posture.** Those decisions governed what
    the *product says*; there was no server to govern. The Mac app still says nothing, and disclosure
    still lives in Safe mode and on the website. **Training consent is captured in the website signup
    flow, never as an in-app toggle** — a toggle would have to explain itself and would collide head
    on with the no-explanatory-copy rule.
  - **What is retained is the redacted content**, since SONNY-89's redaction runs before anything
    leaves the device and `RedactedPayload` is structurally non-bypassable. That raises the stakes on
    redaction quality: a miss was a transient exposure to a provider; under retention plus training a
    miss is durable and can propagate into a trained model.
  - **Two retention clocks, not one** — raw content at the short end of the range, derived metrics
    and usage indefinitely, training snapshots on their own separately-consented lifecycle.
  - **Deletion must reach the training set**, so training reads from documented snapshots with
    recorded lineage and never from the live store. Delete-by-task must be reachable from the app,
    and an incognito run is **never stored at all** — enforced server-side rather than on client
    trust, and structurally excluded from snapshots rather than filtered by a query. Both arrived
    from row D's planning (SONNY-14) and are requirements, not preferences.
  - **The corpus will contain third parties' personal data that no user consented on behalf of.** A
    screenshot can hold someone else's messages or documents; redaction catches secret-shaped
    strings and cannot catch that. This belongs in the founders' terms and legal work explicitly.
  - **SONNY-110's reason changed, its work did not.** The zero-retention provider is no longer bought
    to keep screen content out of a retention window — it is bought so the content is ours and not a
    third party's, which matters directly because training is one of the three purposes. The
    requirement widened to **no retention and no training rights over our data.** Nothing may claim
    this system does not retain screen content. It does. It just does not let the provider do it too.
- **v1 ships three sign-in methods: email code, Sign in with Google, Sign in with Apple.** Email code
  is built first — that is build order, not scope. Enterprise SSO is deliberately not in the set and
  waits on row 19's planning to say whether v1 delivers real team accounts. **Apple is in the set
  though nothing requires it**: its rule binds App Store distribution, not direct Developer-ID
  distribution, and including it keeps that door open rather than closing it by accident. Recorded so
  a later reader does not assume it was mandatory.
  - **Identity linking is a first-release correctness requirement**, not a later concern — one person
    signing in by different methods must land on one account, or they end up with two accounts and
    one subscription. **Hide My Email defeats the obvious rule**: Sign in with Apple can supply a
    relay address, so email is not a stable identity key.
  - **A sign-in screen's copy is functional labels, not explanation.**
    `firstRunApprovalExplainerLines` remains the single founder-approved exception (2026-07-24) and
    is not a precedent to extend.
- **Both providers ship in v1** — OpenAI and Anthropic behind the provider-agnostic router, per
  §16.5's "from day one", with Cerebras kept as a server-side option rather than deleted. Failover is
  the point: one provider outage currently takes Sonny down for every user at once.
- **The backend lives in this repo**, in a top-level `server/` directory, with **staging and
  production plus local**. Staging is seeded synthetic and never holds real user data — under the
  retention decision, a production-seeded staging database would put real users' screen contents in a
  second, less-guarded place. **The staging pointer exists in debug builds only**, so SONNY-106's "no
  environment variable is required for anything" stays true of every build a user runs.
- **Row boundaries.** Row 12 builds the machinery; row 13 builds screens that do not exist; **row 18
  owns the paid-only gate itself**; and **SONNY-109's UI/UX pass polishes screens that do exist — so
  sign-in's design is SONNY-109's, not row 13's.** Without that rule the same screen is designed
  three times.
- **A pricing rule this session produced, general beyond the question that produced it.** The
  email-only option was priced with "we can add Google later." There is no later on this project.
  **Whenever an option's cost is "we add it in a later phase," re-price it as "we add it in v1 too"
  before comparing options.** Here that flipped the answer from one sign-in method to three.

## Per-app control consent, revived and mode-dependent (2026-08-16 — supersedes the 2026-08-14 deletion above)

**This is a dated supersession, and both decisions are meant to stay legible.** On 2026-08-14 the founder deleted per-app control consent outright: Sonny could control any installed app without asking, there was no grant, no store, no revocation surface and no consent field on the approval context. That decision was made, it shipped on `feature/vision-actions`, and it is recorded above and in that row's changelog entry. **On 2026-08-16 the founder replaced it.** The standing position is that ratified decisions get updated when a better answer arrives; the requirement is that the change is recorded as a dated supersession rather than a quiet edit. Full record: SONNY-91's comment of 2026-08-16, SONNY-104's comments, and `docs/sonny-row-j-plan.md` (roadmap row J), which is the architectural plan this section summarises.

**The decision.** Which apps Sonny may control *without asking* now depends on the interaction mode. **Safe** starts from nothing and asks before controlling any app. **Normal** starts from a built-in list of apps people commonly have on a Mac, and asks about anything outside it. **Power** asks about no app at all. An approval is remembered in every mode. **The consequence rule is untouched in every mode** — destructive actions and anything affecting someone other than the user still ask, mid-loop included. This governs *which apps Sonny may drive*, never *what it may do once driving them*.

**Terminals did not become approvable, and that was asked directly rather than assumed.** The founder was put the question on 2026-08-16 — should the new model make terminals approvable in Power only, or everywhere — and chose neither. The 2026-08-14 reasoning stands verbatim: a terminal is arbitrary shell execution with the user's full rights, outside every tier, whitelist and workspace scope this engine has, which stays true of a perfectly accurate model. **The deny list sits above the entire consent model and refuses regardless of mode, starter list, or user approval.** An implementer must not fold the terminal check into the per-app gate as "an app that is always denied": it is a separate, higher refusal at three independent doors, and it stays that way.

**The four questions the decision left open, answered by the founder 2026-08-16:**

- **The starter list is derived, and every IDE and code editor is off it.** The ground is embedded shells, not the apps being dangerous — a developer who wants Sonny inside VS Code approves it once, by hand. It is explicitly **not** `MacAppCatalog.default`, which contains both `com.apple.Terminal` and `com.microsoft.VSCode`. A required test asserts **two** things: no entry is on the terminal deny list, and no entry is an excluded IDE. A review habit is not sufficient.
- **The prompt reuses the ordinary approval path**, so it renders on both approval surfaces rather than only the widget. The fact that an answer is remembered lives in the **escalation reason** — the existing channel for why the user is being asked — not in a new explanatory line, which the no-explanatory-copy rule forbids. **There is no "just this once" option in v1**, for three recorded reasons: it is a second consent shape for the same consent; the approval buttons are icon-only circles and a third would mean redesigning them, which belongs to the whole-product UI/UX pass; and revocation is the escape hatch.
- **One list, per app, forever.** The modes differ only in what they start from, never in what they remember.
- **Switching Normal → Safe keeps the user's list and drops the starter list.** Safe stops trusting Sonny's list and keeps trusting the user's own explicit choices. The founder's reasoning, kept verbatim because it is the general principle and not a detail of this feature: *auto-clearing destroys user data on a toggle, which the consequence rule says should ask first.* Remove-all in the revocation surface is the deliberate escape hatch for a user who wants a clean slate.

**All five pieces ship in v1 — the revocation surface included.** It was named a cut candidate when the decision was first recorded, and that framing was withdrawn the same day under the nothing-gets-parked directive. Splitting the pieces across branches is a sequencing choice, never a scope one.

**The architectural constraint, because it is a product decision with a code shape.** The mode enters `RiskApprovalPolicy.requirement(for:context:)` as an **input** to its one exhaustive switch — `ApprovalContext.safeMode: Bool` is replaced by the three-valued mode, and the resolved per-app fact lands beside it as a second field. Never as a rule chained after that function, which row C's post-hoc clamp invariant (I8) forbids outright. Row I's changelog entry warned a future reader against adding a mode axis here; that warning is about *shape*, and this is its case.

**Two shipped promises this falsifies**, recorded so they are corrected rather than left contradicting behaviour: Settings → Screen Control currently tells the user *"Sonny can control any app installed on this Mac"*, and Power's mode description says *"Runs exactly like Normal today"* — Power becomes the one mode that skips the per-app gate.

## The terminal screen check (2026-08-16 — narrows SONNY-102's gap, does not close it)

**Founder decision on SONNY-102's four candidate approaches.** Keep the static ten-name deny list as the primary, load-bearing refusal, and add a runtime check that looks at what is actually on screen and refuses to control the target when it sees a shell. The other three candidates — hand-maintaining the list only, bundle-metadata heuristics, inverting to an allow list — are declined and recorded on SONNY-102 so they are not re-litigated from scratch.

**Why this one.** It is the only candidate that reaches **Power**, which asks about no app, so a name list is otherwise the only thing standing there. And it is the only one that reaches the **embedded-shell gap** — a shell running inside an app that is not a terminal, such as VS Code's integrated terminal — which does not narrow with more list entries at all.

**The ordering is not negotiable.** The static list refuses **first**. The screen check is an *additional* refusal layered after it, never a substitute and never a reason to trim the list. The ground: a static comparison cannot be talked out of its answer by anything rendered, whereas a screen check reads exactly the surface an attacker controls. Both sit above the per-app consent model.

**How it works, decided 2026-08-16.** It reads the on-device OCR pass that already runs on every capture for redaction (`VNRecognizeTextRequest`, no network), with the verdict produced inside the redaction service so raw recognised screen text never escapes it. It runs **per capture, not per session** — a screen changes under you. It costs no new OCR pass, no new network call, no new permission and no new model call. **It fails closed**, and structurally rather than by remembering to: the recognition pass already throws when it cannot read a screen, so an unreadable screen already ends the session. There is no third "could not tell" state that could be mistaken for permission. **It requires two independent signs of a shell, not one**, recorded as named constants with a fixture corpus rather than as prose — a single `$` on a documentation page must not stop Sonny driving a browser, and a code editor displaying shell script source is not an interactive shell.

**Seeing a shell ends the session**, the way the terminal refusal does. That is safe **because the capture is scoped to the target app's own window** — ScreenCaptureKit's single-window filter, verified as the only capture path in the codebase — so another app's terminal sitting behind the target cannot appear in it and cannot kill an unrelated session. The same scoping is what aims the check at the embedded-shell gap: a shell *inside* the target window is in the capture; a shell in any other window is not. **Any future change that widens the capture invalidates this and must revisit it.**

**It does not close SONNY-102, and no record may say it does.** Two structural reasons: a screen check reads the surface an attacker controls, which is why it is defense in depth and never primary; and a shell that is not rendered — a background tab, a collapsed panel, a scrolled-away region — is not seen. The gap narrows in all three modes and does not close. **The categorical rule "terminals are never controllable" still outruns its implementation**, and `aTerminalNobodyListedIsControllableAndThatIsTheKnownGap` stays in the suite asserting exactly that.

## A precise label is not explanation (2026-08-16 — a reusable pattern, first applied in roadmap row D)

**The pattern, stated generally because it is meant to be reused.** When an honest description of a feature would otherwise need a sentence beside it, **narrow the name until the sentence is unnecessary.** That is how a feature stays truthful under the no-explanatory-copy rule of 2026-08-14, instead of quietly over-promising and relying on a disclaimer the product is not allowed to write.

Recorded as a decision rather than as copy polish, because it resolves a conflict that otherwise has no answer. A name that over-promises is normally fixed by explaining the limits. That remedy is forbidden here. So the fix has to come from the other side: shrink what the name claims until it claims exactly what is true.

**The case that produced it — "Don't save this task", not "Incognito".** Incognito borrows a promise from browsers that this feature does not keep: files still get created, apps still open, and the command still goes to the model provider. The usual remedy — a clarifying sentence under the switch — is exactly what the 2026-08-14 rule rules out. "Don't save this task" promises what the feature does and nothing more, so there is nothing left to explain and no over-reading to correct. Declined at the same time: keeping "Incognito"; "No record", which is accurate but abstract ("no record of what?"); and deferring the name to the UI/UX pass, on the ground that a name doing this much work is a decision, not polish.

**The second application, same day — the two delete labels.** Two delete actions sitting near each other have to be distinguishable at a glance, and no sentence may sit beside either. So bare "Delete" cannot appear twice with different reach: the labels are "Delete task" and "Delete what Sonny did on screen", the second reusing the section title it sits beside so the object of the verb is literally on screen next to the action. The final wording is the founder's and Bhavya's to settle in the UI/UX pass (SONNY-109); what is decided here is that the labels must carry the whole meaning by themselves.

**What this is not.** It is not a loosening of the no-explanatory-copy rule, and it is not licence to write longer labels generally. A label that has grown into a sentence has failed this pattern rather than applied it — the test is whether the name can be read once, at a glance, and leave nothing that wants explaining.

**How to tell it is being applied honestly.** The feature's own limits should be recorded *somewhere the user does not read* — the changelog, a ticket, a code comment — and the fact that they are recorded there is what makes the silence in the product honest rather than evasive. Row D's known limits for "Don't save this task" (macOS's own Notification Center is outside it; the provider still sees the command; a suppressed run cannot be diagnosed) live in its changelog entry for exactly that reason.
