# MacAgentCore conventions

`MacAgentCore` is business logic only — no SwiftUI, no UI state. Capabilities, risk/approval, local stores, planner integration.

## Capability adapters

Every executable capability is a `CapabilityAdapter`, registered in `DefaultCapabilityAdapters.all()`. A new capability follows the same shape as the existing ones (`OpenSafeURLCapabilityAdapter`, `RunRoutineCapabilityAdapter`, etc.) — don't add a one-off switch case in the executor instead. Adapters own `preview(plan:context:)` (synchronous and throwing — `throws`, never `async`, so a dry-run cannot await anything — and it must never make a live network/OAuth/API call, because dry-run has to stay truly free of side effects; SONNY-175 found this written as `preview(_:)` and as non-throwing, and it is neither) and `assessRisk(plan:context:)` (defaults to a static `defaultRiskTier` when the capability doesn't need dynamic escalation). Capabilities whose plans can contain nested sub-plans (routines) use the `previewNestedPlan`/`executeNestedPlan`/`assessNestedPlan` closures on `CapabilityExecutionContext` — all three, not a subset, or nested risk silently doesn't get assessed.

## Risk tiers and the approval boundary

Tiers: 0 auto-run, 1 auto-run unless policy tightens, 2 lightweight confirmation, 3 explicit approval, 4 refuse. `AgentRunner` is the only thing that decides approve/refuse — it calls `AgentActionExecutor.assessRisk(plan:scope:)` for a read-only assessment, then gates. `AgentActionExecutor.execute(plan:log:)` is the already-approved execution primitive and must never re-gate itself; if you're tempted to add a confirmation check inside `execute()`, the gating belongs in `AgentRunner` instead. Approval decisions carry the approved tier, not a bool, so a stale approval can be rejected if a fresh reassessment lands at a higher tier.

## Local stores

Every local store (routines, workspaces, clipboard history + settings, snippets, recent artifacts, Shortcut run history, task history, the vision session journal, what past tasks planned, row J's approved apps, row 13's common output locations, and whatever `LocalStore.allCases` has grown to since) shares one pattern via `LocalStorageEncryption`: a defaulted `encryption: LocalStorageEncryption = .shared` constructor param, AES-GCM encryption with the `SONNYENC1\n` file header, and transparent legacy-plaintext-JSON migration (decode once, rewrite encrypted on next successful load). A new store follows this exactly — don't invent a variant encryption scheme or skip migration. `LocalStorageEncryption.shared` auto-detects test processes (bundle path / `XCTestConfigurationFilePath`) and supplies a deterministic ephemeral key under SwiftPM/XCTest; new tests should still prefer an explicitly injected key manager over relying on that fallback, and must never exercise the user's real login Keychain.

Load failures and write failures need different user-facing handling. An existing file that fails to decrypt/decode on load is a real, visible problem — surface it via `recordLocalStorageLoadFailure(_:error:)` / `clearLocalStorageLoadFailure(_:)`, never collapse it into empty/default state with `try?`. A *write* failure is a different thing and must not reuse that same load-failure banner (its wording is hardcoded to "could not be decrypted or decoded," which is wrong for a save failure) — call `recordLocalStorageWriteFailure(_:)` with wording that names what could not be saved. **It also must not use `errorMessage`**, which this line used to send it to: `errorMessage` means "the task you asked for did not happen", and the widget picks `.failure` ahead of `.result`, so a storage failure routed there makes a task that ran and produced a result render as a failed one. That is the defect `publishLocalStorageLoadError` was written to end, and it kept arriving by other doors — the foreground plan write (PR #89, F4) and the foreground task-history row write (SONNY-201), both since moved onto the notice channel their scheduled twins already used.

## Testing

Everything OpenAI/network/Shortcuts/filesystem-adjacent is behind an injectable seam so tests never make live calls — fixture-backed HTTP protocols, fake planners/transcribers, `FailingPlanner: Planning` conformances for exercising planner-independent paths. When you change a `Planning` method signature, every existing conformance (including the test fakes) needs updating in the same change, not left to bit-rot.

## Untrusted content boundary

**There are two untrusted sources, and the delimiters live in one place.** `UntrustedContentBoundary` owns the four marker *names* and the escaping, and `UntrustedContentBoundary.Delimiters` is the only thing that turns a name into a delimiter. Never re-declare them — two independently maintained copies of a security boundary is the shape where one gets hardened and the other does not. `WebResearchPromptBuilder` used to forward the four as constants of its own; **SONNY-234 deleted them**, because after that ticket there is no such thing as a fixed delimiter and a constant reading `observedBeginDelimiter` would be a second vocabulary saying the old thing. What a caller wants instead is the `Delimiters` value the prompt was built with, or — when it only needs the vocabulary — `UntrustedContentBoundary.allNames`.

**"The escaping" includes the attribute fold, and that had to be said out loud (SONNY-219).** Row I promoted the four constants and left `WebResearchPromptBuilder`'s own `private static func escapeAttribute` where it was, so this rule shipped on 2026-08-14 alongside its own counter-example and the counter-example outlived it by a week. Both copies folded `"\n"` and `" "` and nothing else, which left CR, VT, FF, NEL (U+0085) and the Unicode line and paragraph separators free to begin a line inside a wrapper whose opening line is `DELIMITER id=… source=…`. There is one `escapeAttribute` now; it folds `CharacterSet.whitespacesAndNewlines`, because an attribute has to stay one *token* as well as one line and a tab ends a token as surely as a space; and it folds on **both sides** of `escape` rather than after it, because a fold that runs only afterwards *rebuilds* delimiters — they are `[A-Z_]` only, so `UNTRUSTED_OBSERVED CONTENT_END` carries nothing for `escape` to find and the space fold completes it. `UntrustedContentBoundaryAttributeTests` pins all three properties, and three of its seventeen tests scan **both Swift targets** — `Sources/MacAgentCore` and `Sources/MacAgent`, recursively — so that a second declaration, a re-narrowed twin under another name, or a delimiter name written into a prompt somewhere else (SONNY-234) fails a test rather than waiting to be noticed. They walk both because this rule carries no directory qualifier and the first version of the scan did (PR #97, F3). The fold also takes `CharacterSet.controlCharacters`, for defence in depth rather than to close a live hole; the reasoning, and the one thing it deliberately does **not** reach — the combining-mark weakness in `escape` itself, which is **SONNY-222** and needs scalar or byte matching rather than a wider fold — are recorded at the code.

**"The escaping" also includes the line-break fold, and there are three answers rather than one (SONNY-226, SONNY-231; founder decision 2026-08-26).** `UntrustedContentBoundary.foldingLineBreaks` is the one home, and which fold a value gets follows from the *position* it lands in, not from where it came from. An **attribute** — the `id=`/`source=` tokens on a wrapper's opening line — has to stay one *token* as well as one line, so `escapeAttribute` folds every separator to `_`, one character for one. A **field on a line of an otherwise multi-line block** — `Window title: …`, a vision history entry, the web block's `Title:`/`Author:`/`Headings:`/link/image/citation lines, `Previous outcome: …` — is readable prose that must not begin a line, so line-break runs collapse to the two literal characters `\n`; `_` is wrong here because it would destroy every space in a sentence a model is meant to read. The **body of a deliberately multi-line block** — a fetched page's `readableText`, the observed block as a whole — is **not folded at all**, and that is a decision: flattening an article to one line would destroy what the synthesizer is there to read, and every forged line stays inside the wrapper either way. The fold runs *before* `escape` at every call site **by convention, not by necessity** — this sentence claimed necessity until PR #130's review (F2) and was wrong: `escape` steps over neither a line break nor the `\` and `n` the fold puts in its place, so a break-split delimiter matches nothing either way, and `escape(fold(v))` and `fold(escape(v))` are scalar-identical over the corpus `foldingBeforeEscapingAndAfterItAgreeOnEveryCorpusValue` measures — **693 values since SONNY-234**, 265 before it (5 + Σ over every string `escape` neutralises of (5 + 2·length), derived in the test rather than written as a literal; the population grew from the four bare names to this prompt's four tagged delimiters plus those four names). What *is* load-bearing is the other direction: `escapeAttribute`'s fold emits `_`, a delimiter character, so it can **rebuild** a delimiter and its fold-escape-fold ordering really does carry the safety; this fold's marker appears in no delimiter and can rebuild nothing. **SONNY-234 shrank what `escapeAttribute`'s fold can rebuild without retiring its ordering**: `_` is still the one delimiter character a fold supplies, and no fold can supply twenty tag letters, so a rebuilt string is a bare *name* now — which `escape` still neutralises, so a fold running only after it would still hand one into the wrapper's opening line. **And the fold never replaces the escape** — every field position takes both. A mutant reducing `WebResearchSynthesizer.escapeObservedField` to the fold alone left the whole suite green until F1 was fixed, because the guard that read like it covered it (`everyWebResearchFieldNeutralisesAForgedDelimiter`) counted lines *beginning* with a delimiter, which an interpolated field can never produce. **The invariant that must not drift is the character set** — `CharacterSet.newlines`, so LF, VT, FF, CR, CRLF, NEL and U+2028/U+2029 — because narrowing one copy of a two-copy rule silently restores that copy's own defect and nothing fails. SONNY-226 hoisted the fold out of `PriorTaskContext` and moved that caller onto it; `ClarifiedCommand.foldingLineBreaks` is the one private copy left, and SONNY-262 is the ticket for it. `InterpolatedFieldLineFoldTests` holds all of this and splits on line-break **scalars**, never on `"\n"` — a test written the other way passes against the unfolded tree, which is the same trap PR #94 found in SONNY-198's separator test.

**Delimiters are matched over Unicode scalars, never with `String.replacingOccurrences(of:with:)` (SONNY-222).** Swift compares extended grapheme clusters, so `UNTRUSTED_OBSERVED_CONTENT_END` followed by U+0301 COMBINING ACUTE ACCENT is a string whose final `Character` is not `D` — the substring search finds nothing, the near-verbatim delimiter passes through unescaped, and it lands as its own well-formed line inside what is supposed to be pure data. `hasPrefix`, `==`, `range(of:)` and `components(separatedBy: String)` share the identical blind spot, so a regression test written with any of them **passes against a vulnerable tree**; assertions about this boundary go over `unicodeScalars` or UTF-8 bytes, and the helpers for that live in `Tests/MacAgentCoreTests/ScalarTextAssertions.swift`, which is the one copy — `UntrustedContentBoundaryScalarMatchingTests` defined them, `VisionPromptInjectionTests` had its own, and `WebResearchSynthesizerTests` was still on `hasPrefix` until all three were consolidated there. `UntrustedContentBoundary.neutralizingDelimiters(in:delimiters:replacement:)` is the one matcher — `PriorTaskContext.escapeForPlanner` uses it for its own two delimiters. `options: .literal` is not the fix: it closes a trailing mark and leaves an interior one and a zero-width space between two letters wide open.

**What the matcher steps over is decided by rendering, that frontier has no bottom, and the comment must say so (PR #100 rounds 1 and 2).** Two earlier statements of this rule were cleaner than the code and therefore wrong. Visibility died on U+200A HAIR SPACE, a one-pixel gap less visible than the U+0301 accent the fix closes. Its replacement — "a scalar that cannot legitimately occur inside a token drawn from `[A-Z_]`" — would admit `x` and `3`, which are obviously not stepped over, so it described a boundary the code does not draw. **A comment that states a cleaner rule than the code follows is how the next reader concludes a gap is deliberate.** The honest statement: the matcher steps over a scalar that **contributes no visible glyph of its own** — marks, format and default-ignorable scalars, space separators (U+0020 included), control characters, and U+2800 BRAILLE PATTERN BLANK, category `So`, listed by scalar because `So` also holds `©` and most emoji. The one exclusion is `CharacterSet.newlines`, and it is structural rather than perceptual: a delimiter split by a real line break is two lines, and two lines cannot forge one boundary line.

**The two skip positions take different sets, and that is what let U+0020 be closed at all.** `isIgnorableInsideADelimiter` steps over the ordinary space; `isIgnorableAfterADelimiter` does not. Inside a thirty-character identifier a space is a forgery every time; immediately after one it is ordinary text. **That cost is prospective, and the note that first stated it named a path that does not exist**: `WebResearchMarkdownCapabilityAdapter` never calls the boundary (`git grep -n "UntrustedContentBoundary" -- Sources/MacAgentCore/WebResearchMarkdownCapabilityAdapter.swift` exits 1). Every caller of the matcher produces prompt text that goes to a model API and nowhere else, so nothing renders an escaped string today; the trailing carve-out is precautionary, kept because a silent deletion inside escaped text is what a future rendering consumer would inherit. The carve-out that kept U+0020 open for two rounds was justified by SONNY-219's substitution decision and by a fear of bracketing prose, and **both were disproved by measurement**: `_` is an expected scalar a skipped one cannot supply, so `UNTRUSTED_OBSERVED CONTENT_END` stays a near-miss either way, and prose has no underscores. **Insertion is closed; substitution is a near-miss and stays open** — that sentence was false for two rounds and is true now.

**SONNY-234 ended that class, and everything above it is now defence in depth (2026-08-28).** Three adversarial rounds each found the next blank-rendering character — a combining mark, the invisible spaces, the braille blank — because recognising forgeries of a fixed delimiter is an unbounded problem. A boundary line is now a name **plus a tag generated at wrap time**, after the content being wrapped already exists, so a forgery is not a delimiter regardless of how it renders and the question of whether a blank-looking scalar is "close enough" has stopped being asked. `UntrustedContentBoundary.Delimiters` carries the whole decision record — the entropy arithmetic, why `A`–`Z`, why one tag for both pairs, why fresh per prompt rather than per session — and it is the file to read before changing any of it. What matters at this level:

- **The tag is twenty letters from `A`–`Z`, and the alphabet is load-bearing — by one argument, not three** (PR #158 review, F3). The census, re-derived over the whole scalar range rather than the U+0080–U+212B window the in-tree test scans: **244** scalars canonically decompose to an ASCII `[A-Z_]` base, **0** to a digit, **246** to an ASCII `[a-z]` base and all 246 are not category `uppercaseLetter`. So a **lowercase** tag falsifies `canonicalBase`'s `uppercaseLetter` guard, and that is the whole of it — a digit costs that guard nothing because nothing decomposes to one, and neither a digit nor a lowercase letter touches `escapeAttribute`'s fold-escape-fold ordering (`foldingSeparators` emits `_` whatever the alphabet is) or `foldingLineBreaks`' marker (completing a delimiter from that fold needs a literal `\`, which no alphabet of letters or digits contains). Keep the alphabet; do not repeat the "all three" framing.
- **`escape` still neutralises the four bare names, and the scalar matcher stays.** That is a decision the ticket asked to be made rather than assumed, and the reason is degradation: a prompt that ever stops declaring its tag must fall back to exactly the protection this repository had before SONNY-234 and never below it. So the escape list is **eight** strings — this prompt's four delimiters and the four names — and everything the paragraphs above record about matching a decorated delimiter is still live for the second half of that list. **Longest-first is load-bearing now** rather than a footgun-remover: every tagged delimiter has its own bare name as a proper prefix.
- **The model is told which lines count, in one sentence from one place.** `Delimiters.segmentTagRule` names the tag and all four of this prompt's markers; `VisionSessionPromptBuilder.systemRules` and `WebResearchPromptBuilder.systemPrompt` both interpolate it and neither writes a delimiter name of its own. The rule is one line and every marker inside it sits mid-line, because a rule that put one at the start of its own line would *be* a boundary line inside the system prose. `everyPromptThatWrapsContentDeclaresItsTag` and `theSegmentTagRuleOpensNoBoundaryLine` are what fail if either property goes.
- **A tag belongs to one prompt.** `forOnePrompt()` is called per `decisionPrompt` and per `WebResearchPromptBuilder.prompt`, never hoisted to a session — the vision loop feeds model-authored history back into the next iteration, and the model is the one party that has seen a tag, so a session-scoped tag would be echoable into untrusted content. A stale tag matches nothing; `aDelimiterCarryingAnotherPromptsTagIsNotADelimiter` pins it.
- **Locating a segment by `range(of:)` is now wrong** and gives a wrong answer rather than none, because the rule sentence names all four markers before the segments begin. A boundary is a line that *starts with* the marker. `VisionPromptInjectionTests.onlyBoundaryLine` is the shape to copy.

`UntrustedContentBoundaryTagTests` is where the tag properties live, and `BoundaryTestFixtures.swift` holds the two fixed-tag boundaries every suite asserts delimiter text against plus the forgery corpus that used to be private to one suite. **Do not add another category to the ignorable predicate and call anything closed** — the predicate is now the fallback, and the thing that closes the class is the tag.

**Canonically equivalent spellings match; look-alikes do not (PR #100 review, F2).** `UNTRUSTED_OBSERVED_CONTENT_` + U+00C9 + `ND` and the same string written `E` + U+0301 are the *same text* by Unicode's definition — Swift's `==` says so — so closing one and leaving the other open was incoherent, and it was the precomposed spelling, the one a reader types, that stayed open in the code while four records cited it as closed. A content scalar matches an expected one when it canonically decomposes to it followed only by marks. A Cyrillic `Е`, a fullwidth `Ｅ` and a lowercase `end` are *different characters*, are not canonically equivalent, and are deliberately not matched. **Never paste the rendered character into a record** — write `E` + U+0301 or U+00C9 explicitly; pasting `É` is exactly how the two spellings got confused across five documents.

**Every branch of that predicate is held by a corpus entry, because a branch no test holds is a comment (PR #100 review, F3).** The `.format` clause shipped once justified by U+200B, which is *also* default-ignorable and therefore establishes nothing about it — a reviewer's mutation battery deleted `.format` and the suite stayed green. U+0600 ARABIC NUMBER SIGN (Cf, not default-ignorable) is in the corpus for that clause, U+3164 HANGUL FILLER (Lo, default-ignorable) for the other, U+20DD for `Me`, and U+200A and U+0009 for the separators.

**A source scan is only a guard once it has been shown to flag the defect it names (PR #100 review, F4).** The first version of `noSourceFileNeutralisesADelimiterWithGraphemeComparison` required the call and a delimiter name on one line, case-sensitively, and flagged **0 of 13** candidate lines at `e421242` and **0 of 9** at `dac12b9` — it would have caught none of the three defects this branch fixed, while its own doc comment and this file both promised it would. It now reads the whole call by parenthesis balance, strips comments, matches case-insensitively, and `theSweepFlagsEveryHistoricalInstanceOfTheDefeatedIdiom` runs it against the historical code verbatim before the live sweep is believed. Replayed over the real trees: **9 of 13 flagged at `e421242`, 9 of 9 at `dac12b9`, 0 at the fixed head.**

**Look-alikes are folded in exactly one place, and it is not the boundary (SONNY-272).** `LatinConfusables` is the tree's one fold of cross-script look-alikes to the ASCII letters they resemble — U+0430 to `a`, U+0131 to `i`, the fullwidth letters to their own — and `SecretTextDetector.matches(in:)` is its one caller: the recognizer types those in place of Latin glyphs (SONNY-260 measured four in one reading of one key), every secret pattern is an exact match, and the fold runs once over the whole document before any class matches, with every range mapped back into the caller's text so the mask lands on the scalars the reader saw. It is not a fourth copy of the folds above it — `normalized(_:)`, `MacAppCatalog.normalize` and `ScreenControlPolicy.normalize` fold case and diacritics for names, and none of them touches U+0430 — and it is not to be adopted by `UntrustedContentBoundary`, whose refusal of look-alikes two paragraphs up is deliberate and stays: there a look-alike is a forgery to leave alone in text that is never normalised; here it is a misreading to see through on text that goes to a matcher and nowhere else. Its table is generated (`scripts/confusables-table`, from UTS #39, filtered to letters of the scripts Vision's supported languages are written in — Greek, the mathematical alphanumerics and every ASCII look-alike of another ASCII character are deliberately outside it), and `LatinConfusablesTests` holds both directions of that rule. A second table, or a hand edit to this one, is the shape where the two drift; regenerate instead.

**The vision path's untrusted text is the window title and the observed history, not OCR (SONNY-222 established it).** `LocalRedactionService.redactCapture` returns `maskedText: nil` and uses its Vision observations only to choose which pixels to paint, so recognized text never becomes prompt text and the framework's normalisation of it is not this boundary's problem. Measured on macOS 25.5.0 for the record: Vision normalises a decomposed `E`+U+0301 to precomposed U+00C9, and misreads a delimiter carrying a trailing combining mark as `…ENÓ` — so OCR would have *destroyed* that forgery rather than passing it on. What does carry it is `capture.windowTitle`, which an app names for itself and a webpage sets with `document.title`, and the history lines quoting control labels — plain UTF-8 the whole way to the prompt.

**Fetched web content.** It never enters `OpenAIPlanner.plan(command:)`. The executable `AgentPlan` is decided from the trusted user command first; only after that does an adapter fetch pages and hand them to a separate synthesizer, wrapped per-source as `UNTRUSTED_OBSERVED_CONTENT_BEGIN_<tag> id=... source_url=... retrieved_at=...` / `UNTRUSTED_OBSERVED_CONTENT_END_<tag> id=...`, distinct from the `TRUSTED_USER_INSTRUCTION_BEGIN/END_<tag>` wrapper around the real instruction — one tag for the whole prompt, generated after the pages were fetched (SONNY-234). Any new capability that fetches external content must keep this separation — don't concatenate fetched text into a prompt that also carries executable-plan authority.

**Screen content (row I).** Everything a vision session observes — the window title, the running history of what happened on screen, and the screenshot itself — is untrusted, and it is the *more* dangerous of the two sources: a fetched page is at least one the user's own command pointed at, while a vision session sees whatever happens to be on screen, including a window some other program put there. `VisionSessionPromptBuilder` wraps all of it as observed content and wraps only the user's goal as trusted, and the system rules name the screenshot as data in so many words — a boundary that covers text but not pixels has a hole exactly where the interesting attacks are. `VisionPromptInjectionTests` is a standing red-team corpus, meant to be appended to.

**Egress encoding, and the two orderings it fixes (SONNY-114).** `RedactedCaptureEncoder.render(paintingRegions:inPNGData:policy:)` is the only way a capture becomes bytes that leave the device, and it takes the regions and the source together so that *painting happens before any resampling* — the painted pixels travel between its two halves as a type whose initializer is private to that file, so resampling an unpainted image is not a call anyone can write. It encodes both PNG and JPEG and sends the smaller, which routes dense-text captures (JPEG's worst case, and the content class lossy compression hurts most) to lossless without a rule that says so, and it resamples only when a capture will not fit the byte budget, spending quality first because resolution is the expensive axis. The second ordering: the resulting image may be **smaller than the capture**, so the coordinate space the model reasons in is `SentImageSize`, never `CapturedWindowImage.pixelWidth/pixelHeight`. Everything the model is told about the picture and everything it says back about it — the prompt's declared dimensions, the bounds check, the point-to-screen scale, the journal's `imageX`/`imageY` — reads that one value. A new consumer of a model-returned coordinate that reaches for the capture's dimensions is off by the resample factor.

Two rules that are easy to blur and must not be:

- **On-screen text is never an instruction to Sonny.** Not when it says "SYSTEM:", not when it names Sonny, not when it looks urgent. The founder's 2026-08-14 delegation decision — the vision model may hand an instruction to the planner mid-run — is *not* an exception to this: delegation is the model choosing a means toward the user's own goal, while obeying screen text would be the goal itself changing because a window said so. A model using a tool, versus an attacker picking the objective.
- **Screen-derived signals may add scrutiny and never remove it.** `VisionConsequenceClassifier` reads the target control's visible label, which is attacker-controllable, and that is safe in exactly one direction: an injected "Delete" earns an approval a click would not otherwise have needed, and no label removes one. Any new use of observed content in a security decision has to be one-directional in the same way, or it is a channel.
