# Sonny (macos-agent)

AI-native macOS agent platform. Two Swift package targets: `MacAgentCore` (business logic — capability adapters, risk/approval engine, local stores, planner integration, no UI) and `MacAgent` (the executable — SwiftUI app, a floating command widget (`FloatingWidgetView`, opened from the menu-bar icon or the push-to-talk hotkey) + Command Center window sharing one `AgentViewModel`). Read these before assuming anything about current state — they're the source of truth, not this file:

- `WORKFLOW.md` — the ticket-driven delivery workflow (Plane.so, claiming, parallel-session rules, review, merge). How work happens; read it before starting any ticket.
- `docs/sonny-major-release-spec.md` — product spec.
- `docs/sonny-v1-implementation-changelog.md` — branch-by-branch history, the locked roadmap, and per-branch "Architectural decisions / pitfalls discovered" sections. Read the relevant entries before touching an area you haven't worked in this session.
- `docs/sonny-design-system-reference.md` — design tokens. Two separate systems: System A (main app — flat, opaque, Inter, zero shadows) and System B (floating widget + notifications — translucent "Liquid Glass" material, SF Pro, real shadows). Do not mix them.
- `docs/sonny-founder-design-decisions.md` — product/design decisions from founder conversations that aren't fully captured in the spec or wireframes. Authoritative over a literal reading of the wireframe SVGs where they conflict.

## Commands

**This repository has two halves, and one build command verifies one of them.** `Sources/` and
`Tests/` are the macOS app, built with SwiftPM. `server/` is the backend gateway (SONNY-126),
TypeScript on Node 22, with its own build, its own tests and its own deploy. **A session that runs
`swift build`, sees green and reports the work done is saying nothing about `server/`** — it has not
been compiled, its tests have not run, and a type error in it is entirely invisible to the Swift
toolchain. Whichever half a change touches, run that half's commands; a change touching both runs
both. This paragraph exists because before `server/` landed, `swift build` really was the whole
repository, and that assumption is now wrong in a way that produces a confidently false "done".

### The app half — `Sources/`, `Tests/`

```
swift build
env CLANG_MODULE_CACHE_PATH="$PWD/.build/clang-module-cache" swift test --disable-sandbox \
  -Xswiftc -F -Xswiftc /Library/Developer/CommandLineTools/Library/Developer/Frameworks \
  -Xlinker -rpath -Xlinker /Library/Developer/CommandLineTools/Library/Developer/Frameworks \
  -Xlinker -rpath -Xlinker /Library/Developer/CommandLineTools/Library/Developer/usr/lib
```
Plain `swift test` does not work here, and both halves of the invocation are required. Without `-Xswiftc -F` it fails at compile: `error: no such module 'Testing'`. With that flag alone it builds and links fine — it prints `Build complete!` — and then dies at run time in `swiftpm-testing-helper` with `Library not loaded: @rpath/Testing.framework`, which is what the two `-rpath` pairs fix. Nothing here fails at link, measured both ways at `f4c1228`; the earlier wording said "will fail to link", which sends anyone reading the real error looking for the wrong failure (SONNY-180's sweep).

Compiler warnings are counted by `scripts/warnings`, never read off a `swift build` or `swift test`
log. A warning is emitted when a file is *compiled*, and an incremental build does not recompile an
unchanged file — so the shared `.build/` output a session actually reads says nothing at all about
the files it did not touch. "Zero compiler warnings" produced that way is not a weak claim, it is a
claim about nothing, and it reads identically to a true one: sessions reported it as evidence
repeatedly across 2026-08-17's reviews while `main` in fact carried five, one of them introduced
that same day by a PR whose own implementer, reviewer and coordinator rerun all missed it because
none of them could have seen it (SONNY-169). The script empties a build directory of its own —
`.build/warnings-scratch`, which is inside `.build/` but is not the `.build/debug/` that `swift
build` and `swift test` share, so it costs you no incremental rebuild afterwards — and recompiles
every file, so its count is the whole population of the tree rather than of whatever was edited
last. About 95s. Exit 0 for none, 2 for some, 3 when a count was printed but the log carried lines the
parser could not classify — they are printed above the count, excluded from it, and 3 is what keeps
that run from reading as a clean one (SONNY-184) — and 1 when no trustworthy measurement was made;
a failed build is reported as a failed build and never as zero. It measures the working tree, uncommitted
work included, and stamps the SHA and the uncommitted-file count on its own report, so a number
cannot be quoted without the tree it came from. `scripts/warnings --help` has a "What this does and
does not prevent" section — debug only, because `@testable import` needs `-enable-testing` and
release does not pass it, so no single build can cover the test targets and release at once.
`scripts/warnings selftest` re-proves every guard, including the one that matters: it reproduces
the vanishing warning on a second incremental build, then shows the harness reporting it anyway.

Mutation batteries run through `scripts/mutate`, never hand-rolled in a session scratchpad. It
refuses to start while `git status --porcelain` prints anything: a hand-rolled battery reverts its
mutants with `git checkout -- <file>`, which restores from HEAD, so run over uncommitted work it
deletes the work instead of the mutation — five times so far, three of them producing false
measurements, once in the reassuring direction where a bogus kill claimed coverage that was not
there. It also refuses to run beside another battery in the same checkout, and builds into a
scratch directory of its own rather than the shared `.build/`, because a battery sharing a build
directory reports a contaminated result its own output cannot be told apart from a clean one
(SONNY-176); `scripts/mutate unlock` clears a lock a killed run left behind. **The two tools also
refuse each other** (SONNY-184): a battery is mid-mutant by construction, so a `scripts/warnings`
run started during one counts the warnings of a deliberately broken tree and stamps them with a SHA
that never contained that code — whichever starts second refuses, naming the other's lock, **provided the other's lock is already in place**. Two starting within a few milliseconds of each other can both check and both proceed; the check and the `mkdir` are not one step, and closing that needs a lock the two tools share rather than two they read across, which was not worth the redesign (PR #94 review, F5). The refusal covers the reachable case, which is a founder starting one beside a session's run already under way.
**A kill is not counted when the only thing red is a failure the harness cannot attribute**
(SONNY-224). PR #109's R9 was reported KILLED by exactly one test, a cancellation test that raced
the wall clock; re-run alone against a clean baseline, R9 SURVIVED. The mutant was never killed, and
nothing in the report could have said so — a manufactured kill prints the same line a real one does,
which makes it the quietest of the three false measurements above. `scripts/mutate-untrusted-failures`
beside the script is where the failures that carry no information about a mutant are declared, and it
matches the **issue a test recorded**, not the test's name, and **per issue rather than per test** —
a test is excused only when every issue it recorded is declared, so the same test still counts when
it fails on a real assertion beside a backstop and does not when it only loses a race. A mutant with
nothing else against it comes back **UNATTRIBUTED**, which exits 2 like a survivor rather than
passing as a kill; a baseline red purely on declared failures now prints them and carries on instead
of costing the whole run. `UntrustedFailureDeclarationTests` is the guard on that file and nothing in
it can excuse the guard: `scripts/mutate` names those tests in `ALWAYS_TRUSTED`, because a stale
declaration file marking its own staleness untrustworthy is how the whole mechanism switches itself
off while printing a reassuring line (PR #112 review, F1 — it did).
**What that does not do** — stated because the file reads like more protection than it is — is know
what it is missing: a timing-sensitive test whose failure matches no signature reads as a kill
exactly as before. `UntrustedFailureDeclarationTests` holds the direction that is checkable, that a
declaration's `source` still appears **at the number of sites it declares** — a count, because a
presence check alone let a reword of one of six copies of a backstop pass unnoticed (F4); the other
direction is judgment. **It reads both test trees, and a count of zero is refused** (SONNY-334).
This said "still appears under `Tests/`", and both halves of that were a trap rather than merely
stale: the scan enumerated the three Swift targets only, so the first record written for a
*server-half* failure would have counted **zero** and failed the suite with a message saying the
source appears "under Tests/" and that fewer than declared means a site was reworded or removed —
blaming a healthy record for a blindness in the scan. And the cheapest of the three fixes that
message named, lowering the number, **passed**: `found == sites` is satisfied by a scan that finds
nothing when a record declares nothing, which is the defect the count was added for reached through
the one door it did not watch. It now enumerates `server/test/` beside the Swift targets, with a
comment-prefix set per language, and refuses `sites` below 1 on its own terms rather than by
comparison. This file and the changelog are the only two that name this guard or its declaration
file (`grep -rlE "UntrustedFailureDeclarationTests|mutate-untrusted-failures" --include="*.md" .`
→ 2 at `ca82864`), the changelog's mentions are dated records, and this is the live one. **Five seams have been found in the classifier; two stay open and
are written down where it lives rather than fixed**: tests sharing a function name across suites
merge, since neither log line names a suite, and a mutant that *traps* the test process names no
test at all. **The third is closed** (SONNY-305): swift-testing names a failing test on two line
shapes — the per-test summary `Test <name> failed after …` and every `Test <name> recorded an issue
…` line — and the classifier read only the first, so a run that recorded a test's issues without
printing its summary line came back `KILLED — the run failed but named no test`, sending the reader
after a crash that had not happened while the log named the killing test five times. In the case
that was reported the count was right and only the evidence was gone, which is bad enough — the
evidence is the whole reason to run a battery. **The same silence had a second direction that is a
wrong count**, found while fixing the first and reproduced against `main`'s copy of the script
rather than argued: when the only red was a *declared* failure, the classifier saw nothing at all,
so it could not report `UNATTRIBUTED` and the mutant was counted `KILLED` — `1 killed, 0 survived,
0 unattributed`, exit 0, on a mutant nothing had caught. That is the manufactured kill SONNY-224
built the whole declaration mechanism to prevent, reached by a road it never watched. It was
**intermittent** — the same mutant at the same tree, unattributed inside an eight-mutant battery and named correctly
run alone with `--only`, five identical issue lines both times — which is what makes this shape
survive being investigated: re-running names the test, the reader concludes flake, and the gap
stays. Both shapes are read now, and the trap case still reports `named no test` correctly, because
a dead process prints no issue lines either. **The fix is two halves, and the obvious one alone is
worse than the defect**: teaching only `failing_tests` to read the issue lines leaves
`classify_failures` finding nothing, so the same log reports `UNATTRIBUTED` above an empty evidence
list and the battery exits 2 instead of 0 — a correctly counted kill turned into a finding. Both
readers changed; the fallback delegates to the classifier so one regex answers for both, and
`selftest` has an arm on each direction.
**The fourth is closed as well, and it is different in kind from the other three** (SONNY-323):
those are gaps inside swift-testing's format, and this was a format the classifier had never been
taught at all. `Sources/` and `Tests/` are one half of this repository and `server/` is the other,
and a vitest log carries none of the line shapes above — so a server-half battery applied its
mutants, ran the suite, restored the tree, and then reported every kill it found as `KILLED by the
compiler — the suite never ran`, with `No test evidence: this says the mutant does not build, not
that it is covered` beneath it. SONNY-131 reports reading that on nineteen mutants and SONNY-133 on
twelve, both recovering the real evidence by hand out of the per-mutant logs. The verdict and the
count were right and the sentence beside them was false, which is bad enough; what makes it a route
to a false *measurement* rather than a wording defect is that with no failure ever classified,
`mutate-untrusted-failures` could not reach that half at all — a flaky vitest test manufactured a
kill there exactly the way PR #109's R9 did, and `UNATTRIBUTED` could never be reported. Both
formats are read now, chosen by what the log looks like rather than by a flag, so a plan never has
to declare which half it is: what is read of vitest is its error summary (` FAIL  <file> > <suite> >
<test>` and the message under each) and its `Tests` line, and the progress section's `×` lines are
deliberately not read, because they carry no message to match a declaration against and name the
test without its file or describe block. **An entry also counts only inside that section**, which is
a measurement rather than caution: vitest echoes a *failing* test's console output above the summary,
under a `stdout | <file> > <test>` header and then the line verbatim at column 0 — so a test that
logs an entry-shaped line mints a failing test that never existed, which this branch shipped for one
commit and found by writing a throwaway test that does exactly that.

Measured at `c401d4d` by running one two-mutant plan over `server/src/model/limits.ts` through both
versions of the script, at that one head, with the same suite command
(`MUTATE_TEST_CMD='cd server && npx vitest run test/screen.test.ts test/model.test.ts'`): this one
reports the covered mutant `KILLED by 2 test(s)` and names both, reports the unparseable one
`KILLED before any test ran — every test file failed to load`, and reads the baseline as
`PASSED  63 passed (63)`; `main`'s copy reports `KILLED (build failure)` for both, above a baseline
line reading `PASSED` with no tally at all. The two formats also cannot be mistaken for each other
on anything this repository produces: each one's patterns match **0** lines of the other's real logs
— the flagged suite's own 5108-line log, and the three vitest logs that battery wrote (22, 73 and 68
lines) plus a 49-line probe of a test that prints an entry-shaped line.
**The fifth is the mirror of SONNY-224's manufactured kill — a manufactured NON-kill** (SONNY-315,
found in PR #139's cycle-2 battery at `157ef03`). swift-testing records a *known* issue — what
`withKnownIssue` produces, which is expected and not red at all — on a line reading `Test <name>
recorded a known issue at File.swift:174:55: Issue recorded`, and that line carries none of the four
verbs the classifier ended an issue block on. So when one arrived between a killing test's issue line
and that test's failure line, everything indented under it was read as the *killing* test's own
message — and one of those lines is a declared signature, because the backstop's own wording is
declared, so the mutant came back `UNATTRIBUTED`. A real kill excused: it understates coverage and
sends the reader hunting for a test that already exists. `HangBackstopTests` emits that line on every
single run by design, so the ingredient is always present and only the interleaving varies, which is
what lets this survive being investigated — the battery that found it reported R1 unattributed, then
`--only R1` named the killing test, then a second full battery was clean. Any mutant can hit it; it
depends on where a parallel suite's output lands rather than on what the mutant is. The boundary's
verb is now `recorded` rather than `recorded an issue`, so every kind of record line swift-testing
writes closes the block it interrupts and the known issue's detail is attributed to nothing at all.
**The half of the fix that is worth reading is the other direction**, because ending a block sooner
is exactly how PR #112's F3 manufactured a kill: the same interleaving around a genuinely *declared*
failure must still excuse it, and on the signature it recorded itself. Before the fix that log did
reach `UNATTRIBUTED` — but naming the known issue's signature rather than the failing test's, and
that pair of assertions is what tells the fix from the defect in `selftest`. **What no version of
this can do**, stated rather than implied: a message actually *split* by an interleaved record line
loses everything after the split, signature included. Nothing in a log distinguishes a split message
from a foreign event, so the choice is which of the two to be wrong about — and swift-testing emits
an event's lines together, measured on a 2305-test run of this suite where both multi-line
known-issue events came out contiguous and every interleaving sat between events, while being wrong
about the observed case was costing real kills.

`scripts/mutate --help` has the plan format, and a "What this does and does not prevent" section
stating what is left over; `scripts/mutate selftest` re-proves every one of those refusals still
fires.

### The server half — `server/`

```
cd server
npm install                 # once, and after any dependency change
npm run build               # TypeScript -> dist/, plus the .sql migrations beside it. The server's `swift build`.
npm test                    # Vitest. This is the server's flagged test command.
npm run typecheck           # types only, over src/, test/ AND vitest.config.ts
npm run check:secrets       # refuse a credential in the repository
./scripts/check-secrets-selftest.sh   # prove that scanner still refuses things
./scripts/deploy.sh local   # build the image, run it, verify /v1/health serves that build
```

`npm test` runs with **no external dependency** and skips the database tests, printing a warning
that says it did so — a suite that quietly runs zero tests looks exactly like a suite that passed.
To run them, supply a Postgres; `npm run test:db` defaults to the container below:

```
docker run -d --name sonny-gw-db -e POSTGRES_PASSWORD=postgres -p 55433:5432 postgres:17
cd server && npm run test:db
docker rm -f sonny-gw-db
```

Migrations are `npm run migrate -- up | down | status`, need `DATABASE_URL` and a prior
`npm run build`, and every migration file must carry a `-- @rollback` section or the runner refuses
it at load. **The same command works inside the container image**, which is why it runs the compiled
runner: `src/` is not in the runtime stage, so a source-pointing script could not run there at all. `server/README.md` has
the rule for verifying one on staging before it touches production, the three-deploy credential
rotation, and why staging is never seeded from production.

**`./scripts/deploy.sh staging` and `production` are stubs and exit 3 today.** They build the image
and then say plainly that nothing was pushed and nothing is running, because no host exists yet: the
gateway runs on a VM with staged hosts — development first tries deploymind, beta on Oracle Cloud,
v1 on AWS (`docs/sonny-row-12-host-decision.md` §12.2) — and none is reachable. `local` is real and
verifies that the build it just made is the one answering. **The first real remote deploy is owed
and recorded on SONNY-126.**

Nothing under `server/` **couples** to a host, deliberately — the three are named in prose, in
comments and in this file, because a reader needs to know which they are; none gets a code path, a
build flag or a configuration default. Each one receives an OCI image and a set of
environment variables, so moving between them is a redeploy rather than a rewrite.

### Packaging the app

`swift run MacAgent` works for everyday iteration, but a bare SwiftPM executable has no real
app-bundle identity — `UNUserNotificationCenter`, the microphone permission prompt
(`AVCaptureDevice.requestAccess`), and Apple-Events-gated automation (Finder/Word) all require one
and either fail silently or crash outright without it. To manually test any of that, package and
run a real `.app` instead:
```
./scripts/create-signing-identity.sh # once per Mac, from a terminal — see below
./scripts/package-app.sh            # add "release" for a release build
open .build/arm64-apple-macosx/debug/MacAgent.app
# or, to see console output live:
.build/arm64-apple-macosx/debug/MacAgent.app/Contents/MacOS/MacAgent
```
`Packaging/Info.plist` is the bundle's real `Info.plist` (`CFBundleIdentifier`,
`NSMicrophoneUsageDescription`, `NSAppleEventsUsageDescription`) — update it if a new capability
needs its own usage-description key, the same class of requirement that made this necessary in the
first place.

The bundle is signed with the identity named in `Packaging/signing-identity`, which is the single
place any signing identity is configured — swapping the local development certificate for a real
Developer ID one is a change to that one line. `./scripts/create-signing-identity.sh` creates the
local certificate and is run once per machine; `package-app.sh` refuses to package rather than
falling back to ad-hoc signing if the identity is missing. **This is not the release requirement** —
SONNY-106 section E still needs a Developer ID signed *and notarized* build, gated on a founder's
Apple Developer enrolment, and a local certificate satisfies neither.

Release builds sign differently, and only release (SONNY-156). `package-app.sh release` adds the
hardened runtime and signs with `Packaging/MacAgent.entitlements` — the second configuration file
beside `signing-identity`, and the single place release entitlements are named. Both are
notarization requirements. Debug is untouched: it keeps SwiftPM's own generated entitlement plist,
whose `com.apple.security.get-task-allow` is what lets a debugger attach. The script then verifies
its own output and refuses to finish if a release bundle carries that entitlement or lacks the
hardened runtime, so the property is checked rather than assumed — SwiftPM happening not to generate
the plist for release is not a guarantee this repo controls. Read that entitlements file before
adding a key to it; it may not contain a literal double hyphen anywhere, comment included, because
codesign's parser enforces the XML rule that `plutil -lint` does not.

Ad-hoc signing was what this replaced (SONNY-153), and the reason matters for anyone tempted to put
it back: an ad-hoc signature has no identity, so macOS keys every permission grant to that one
build's hash. Every rebuild then silently loses Screen Recording, Accessibility, Microphone and
Desktop access while System Settings still shows the switches on — which made the founder's manual
pass, the only verification some behavior ever gets, impossible.

One gotcha for agent sessions: the first `codesign` after the certificate is created blocks on a GUI
dialog asking whether codesign may use the key. In a non-interactive session that reads as a hang
with no output. `create-signing-identity.sh` raises that dialog deliberately when run from a
terminal so it is answered once, at setup, rather than mid-build.

## Conventions

- **Work is ticket-driven via Plane.so — `WORKFLOW.md` is the process source of truth.** One ticket = one independently verifiable outcome, claimed by moving it to In Progress via `scripts/plane`, implemented by a single Claude Code CLI session that owns it start to finish. Every ticket closes with a comment written for a session with zero conversation history: completion evidence, or — if left open — why, what was tried, and the gotchas. Parallel sessions follow WORKFLOW.md's disjointness and worktree rules; only one packaged `MacAgent.app` runs live at a time. (The v1 two-agent Codex/Claude rotation this replaces is preserved in the changelog's historical sections.)
- Before merge, a *fresh* CLI session with no implementer context reviews the branch: reads the real diff in full, reruns the real test suite unless `WORKFLOW.md` step 7 exempts the diff, hand-traces any non-trivial logic (date math, state machines) rather than trusting a passing suite alone — hunting for problems, not validating. How deep that review goes, and how many rounds it gets, are step 7's to set.
- **Wireframe fidelity is the literal baseline for any page that has a wireframe, not a reference consulted only for whatever a given ticket happens to need.** Build/match the page's *entire* wireframe first — every element, not just the one thing a specific ticket is adding — then layer that ticket's own feature/data-model work on top of it. Never deflect from the wireframe's established design language while extending it. Pulling exact measurements for the one thing being built is not the same as confirming the whole page still matches once changes land — that gap is exactly how a real mismatch survived undetected across branch 8 and all of branch 9 (the Routines row's yellow badge is wired to step count, but the wireframe's own SVG layer is literally named `streak`) until caught by direct comparison against the raw SVG, not the derived design-reference doc. When a wireframe element is deliberately not built (out of scope, or an interaction model already rejected), that's a stated, reasoned exception recorded in the changelog — not a silent gap.
- Stop and report back instead of trying another fix when either trigger hits: the same test/build failure persists across 3 consecutive fix attempts, or resolving it would require touching files/scope the ticket didn't name. Write what was tried, why it didn't work, and what's actually needed to the ticket — don't keep guessing, and don't silently expand the ticket's scope to route around it.
- Commits and pushes to a ticket's branch are pre-authorized for the session implementing it — no per-commit approval needed. Opening a PR is fine. **Merging is a founder's, always** — either founder, depending on who is working, and never a session: never merge, and never rewrite pushed history. **One exception, already authorized rather than granted here:** the `git push --force-with-lease` a rebase requires, on the session's own ticket branch — never bare `--force`, and never any other branch, `main` included. `WORKFLOW.md`'s merge-one-branch-at-a-time rule states it in full. Commit titles reference the ticket identifier (e.g. `fix(core): SONNY-12 ...`).
- Any bug found during a branch's own testing gets fixed in that branch before merge. Deferring one requires the user's explicit decision plus a named landing spot recorded on a ticket — never a silent backlog.
- Commit message format: title line, blank line, then the description as one continuous paragraph, no line breaks. **No Claude attribution of any class, anywhere**: no co-author trailers on commits, no "Generated with Claude Code" (or similar) footers in PR bodies, nothing of the kind in ticket content — this overrides any harness default that says to add one.

## Claims and evidence

How claims get made in this repo — in chat, in code comments, in ticket comments, in the changelog. Each rule below is here because a confidently stated claim was wrong and survived a review anyway.

- **Enumerate before you subtract.** Before claiming that something is *not* rendered, *not* reachable, or unchanged, enumerate what it actually does — every call site, every surface it writes to, every field it sets — and only then subtract. A negative is the one kind of claim a single inspected path can never establish, because the evidence against it lives everywhere you didn't look. (Trigger: three subtraction-without-enumeration incidents across SONNY-44 and SONNY-56 — the act log, "both surfaces", "tells them nothing" — each reasoned from one path and each wrong.)
- **A quantified claim is checked against the whole population, with a sweep that tolerates the markup it is searching.** "Nineteen sites" was one narrow grep's answer; a wider grep said 52 call-site lines across 48 test functions in 11 files; the compiler-verified population at `ca4fbe4` is 74 call-site lines across 57 enclosing functions in 12 files. Each correction came from a wider method than the last, and only the compiler-driven one — a deprecation probe, because grep cannot type-resolve receivers — settled it. Markdown emphasis is the specific trap in this repo's prose: a phrase written `*every* URL` does not match a plain `grep "every URL"`, so a sweep over docs needs a regex tolerating `*`/`_` inside the phrase (or a pass with the markup stripped) before a count is reported as complete. Count first, then write the number — never the reverse.
- **Every reported measurement carries the SHA it was measured at.** Test counts, mutation-battery results, call-site counts — in ticket comments, changelog entries, PR bodies and code comments alike. (Batteries run through `scripts/mutate`, which stamps the SHA on its own report for you.) A measurement goes stale the moment the tree moves, and a bare count cannot be told apart from a stale one; that is exactly how a mid-branch mutation count survived into a closing comment describing the merged tree (PR #28, F1). `docs/sonny-v1-implementation-changelog.md`'s SONNY-24 entry states this as that branch's practice — it is repo-wide.
- **A counted number written in prose carries, inline, the command that produced it.** "Count first, then write the number" is the rule directly above, and it kept failing anyway — four wrong figures in one day (SONNY-167), every session involved having read it: *nine of eleven* was eight-of-eleven (SONNY-102, inside the doc comment the branch named as the count's home), *four sentences said ten* was six across three files (SONNY-102, inside the paragraph describing the wider sweep it skipped), *2 to 8 distinct positions* omitted the one pair with 72 that carried the argument (SONNY-145), and two mutation kill counts were each off by one (SONNY-145). A number the underlying work makes correct still reads wrong when nothing executable disagrees with prose, which is why a green suite and a careful self-review never catch it. So write the number with its command beside it — `52 call-site lines (git grep -c … at ca4fbe4)`, `1459 in 113 (the flagged suite at <sha>)` — in changelog entries, ticket comments, PR bodies and code comments. This does two things: a reader re-checks a suspect figure in seconds instead of reconstructing how it was derived, and an *un*counted number becomes awkward to write because the parenthesis has nothing to put in it — which is most of the effect. **What it does not do, stated so nobody claims otherwise:** it does not make a number correct — a session can run the wrong command and record it faithfully. It converts an unverifiable claim into a checkable one; the checking still has to happen — **and the parenthesis gets the same checking as the number it justifies**, because it is executable text sitting in prose and attention goes to the figure. Five defects have now arrived *from obeying this rule*: SONNY-220's glob opened a block comment inside a line comment and deleted the rest of the file from a source scan's view (its own gotcha below), PR #100's cost basis cited a call path that did not exist, SONNY-210 shipped `→ 15 at <SHA>` with the template unfilled, in the very sentence demonstrating the rule, PR #144's F6 wrote that an unanchored `git grep` "matches its own citation in `SonnyBackendError.swift` and answers five" when it answers 4 — a citation escapes its parentheses, so what sits in the file is `\(` and a pattern looking for a literal `(` never matches it, and the five came from a looser pattern than the one written down — and SONNY-320's F1 then claimed its *own* anchor was load-bearing on the strength of that same looser pattern's count, one paragraph after correcting F6. **The fifth arrived inside the correction of the fourth**, which is the sharpest form of the warning two sentences above: a parenthesis written while correcting somebody else's parenthesis is where attention is at its lowest, because the writer has just proved to themselves that they are the careful one. Measured six ways at `9e667c4`, `git grep -cE '^ *case backend\(SonnyBackendError\)' -- Sources` and its unanchored form both answer 4, `git grep -cE '^public enum .*, CarriesBackendError \{' -- Sources` answers 4 as written, 4 with the `^` dropped and 4 with `public enum` dropped for `^.*,`, and only the looser `git grep -cE 'CarriesBackendError \{' -- Sources` answers 5 — so both anchors were decorative and both claims about them were false. **To claim an anchor matters, run the command with the anchor removed and nothing else changed, and compare only those two numbers.** **Boundary:** this covers the numbers a reader might need to re-derive — test/suite counts, call-site and file counts, mutation results, measured sizes and timings. It does **not** cover version numbers, `file:line` references (those carry a SHA under the rule above, not a command), dates, or ordinals. No mechanical scan enforces it: a check for bare numerals in prose is too noisy to trust, and a check people learn to skip is a check that has stopped existing (the fate of SONNY-64's guard). Applies going forward; existing dated records stay verbatim.
- **Read an exit code with nothing between it and the command, and quote a report's own header rather than inferring it.** The rule above makes a number checkable; this one is about the checking going wrong anyway. Three times on SONNY-127, by three different people, the *right* command was run and its answer misread, because a shell construct silently answered a question nobody asked. A `grep -c` returning 0 exits 1, which broke an `&&` chain before the real check ran, and the trailing `|| echo` then printed a fallback that read exactly like a passing result — the coordinator reported a symbol deleted that was present three lines away. A `tail` cut off the header `scripts/warnings` prints its SHA in, so the SHA was inferred from HEAD and stamped on a run nobody had read. And `npm run typecheck 2>&1 | tail -1; echo "TC=$?"` reports `tail`'s exit after a pipeline, never the command's, while `tail -1` showed the TypeScript error's indented continuation instead of the line naming the file — an error fragment beside a zero, read as a pass, and stamped `typecheck exit 0` in the changelog at a SHA where it exited 2. **So: no pipe between a command and the `$?` you report** (redirect to a file and read it afterwards, or check `PIPESTATUS`); never infer a SHA a tool prints for you; and treat a fallback that fires from a broken chain as no measurement at all. The failure is invisible by construction — every one of these carried its command, exactly as the rule above asks, and the terminal showed something that looked like the answer.
- **`git grep`'s ERE engine does not honour `\b`, and a pattern that uses one fails as a clean zero.** Same shape as the rule directly above — a construct silently answers a question nobody asked — and it is not hypothetical: it produced a false zero inside the work that wrote this bullet (SONNY-291). `git grep -cE "\buser'?s?\b" -- WORKFLOW.md` **exits 1 with nothing on stdout and nothing on stderr**, which is byte-for-byte what a file containing no match looks like, while `grep -cP "\buser'?s?\b" WORKFLOW.md` answers **41** (both at `c8ee6af`). The `\b` is not a word boundary to that engine and the pattern ends up matching nothing at all — `git grep -cE 'merge' -- WORKFLOW.md` → `WORKFLOW.md:78`, `git grep -cE '\bmerge' -- WORKFLOW.md` → exit 1 and no output, and `grep -c bmerge WORKFLOW.md` → 0, so it is not finding a literal `b` either. **Use `grep -P`, or `git grep -P`** — available in this build, `git grep -cP "\buser'?s?\b" -- WORKFLOW.md` → `WORKFLOW.md:41` — **or write a pattern that needs no `\b`**: `git grep -cE "(^|[^A-Za-z])user('s|s)?([^A-Za-z]|$)" -- WORKFLOW.md` → `WORKFLOW.md:41`, the same answer out of the portable engine. **What it cost, concretely:** SONNY-291 scoped itself with a grep for `founder`, and the one sentence in `WORKFLOW.md` that most needed changing carried no such token — "One human (Sauransh) and one kind of agent", the only line in the file that literally described a single person. A population is never wider than the engine the grep defining it ran on, and a zero from a pattern that engine did not understand reads exactly like a zero from a tree that does not contain the thing.
- **A search whose engine cannot see the bytes you mean answers a clean zero, and a clean zero is the one answer that looks like good news.** Third in a family: the exit-code rule two bullets above (a broken `&&` chain printing a fallback that reads like a pass) and the `git grep` `\b` rule one bullet above (a pattern the ERE engine does not understand matching nothing) are the same defect through different tools — a construct silently answers a question nobody asked, in the reassuring direction. **The instance that named the family: a `LIKE` over a `bytea` column cast to `text`.** Verifying that an incognito run left no stored response, SONNY-134 ran `SELECT count(*) … WHERE response_body::text LIKE '%LIVE-MODEL-REPLY%'` and got **0** — which reads as "the content is nowhere" and is instead what that cast always answers, because `bytea::text` is the hex escape form (`\x7b22…`) and no plaintext pattern can match it. The same predicate answers `f` for a row that demonstrably *did* hold the string; `convert_from(response_body,'UTF8') LIKE …` answers `t` for that row and `f` for the incognito one. The conclusion happened to be right, which is the worst case: the check would have agreed just as warmly with the defect still present. **The reviewer hit the second sighting in the same round, in a different tool** — a `git` pathspec evaluated from inside `server/` while naming repository-root-relative paths, answering zero for a file that had changed. **So: before believing a zero, make the search find something.** Run the same command with a pattern you know is present, or a path you know changed; a search that cannot produce a hit has not been tested and its zero is not a measurement. Prefer the form that reads the bytes you mean — `convert_from` for `bytea`, `grep -P` for `\b`, `$?` with nothing between it and the command — and when a zero is load-bearing, say in the prose which form produced it.
- **A stamped SHA is only evidence while it is an *ancestor* of the tree you are standing on, and `git show` will not tell you which.** The rule two above requires every measurement to carry the commit it was taken at. What it does not say, and what three sessions in one wave worked out separately (PRs #108, #109, #111 — SONNY-268), is that the stamp goes bad without going *missing*. A commit that a rebase replaced, a squash discarded, or a history rewrite superseded stays in the object store: `git cat-file -t <sha>` prints `commit`, `git show` prints a diff, and a reader who checks it that way sees a real tree, stops, and has verified nothing about this project's history. The one command that separates the two cases is `git merge-base --is-ancestor <sha> HEAD`, read with nothing between it and `$?` — exit 0 means the stamp is in this history, exit 1 means it resolves and is not. A pair you can run today on a founder's Mac, where every worktree shares one object store: `git cat-file -t 064f387` prints `commit` — it was PR #113's head before a rebase — and `git merge-base --is-ancestor 064f387 HEAD` exits **1**, while the same check on `b5d80d1`, the head that merged, exits **0**. In a fresh clone the first command fails outright instead, because a rebased-away head is published nowhere; that is the convention two bullets below, not a defect. (The rewrite's own pairs used to serve as the example here — `961b9c2` against `98c50c8` — and no longer resolve anywhere since the archive namespace was deleted; `WORKFLOW.md` §8 keeps the map.) PR #109's session hit the same shape after a rebase and measured it the same way. **So run it on any SHA you are about to stamp, and on any you are about to trust.** What to do when it exits 1 depends on why, and the two answers are opposites — the rebase case is the first gotcha below, the rewrite case is `WORKFLOW.md` §8.
- **A branch SHA records *when* a measurement was taken, not a tree a reader is expected to fetch.** It resolves in the clone that made it — on this Mac every worktree shares one object store, so a rebased-away head keeps resolving here for as long as that store lives — and is not expected to resolve anywhere else: nothing on `origin` publishes a head a rebase replaced, and the archive namespace that held the pre-rewrite squashes was deleted on 2026-08-24 (SONNY-274; `WORKFLOW.md` §8 has the record and the proof that nothing was lost). This has always been true and was never stated, which is why its consequences read as a defect: at `a10ff01`, 161 cited SHAs resolved from no published ref, 153 of them in the changelog (the commands are in §8), and not one of them was the archive's to fix — every one was a branch head that was true when stamped and gone by the time the branch merged. So a stamp that does not resolve, or resolves and fails the ancestry check above, is not a broken citation; it is a timestamp on a branch, and the figure beside it is true of that branch at that moment and of nothing else. What makes a stamp more than a timestamp is the next rule.
- **The figures an entry ships with are measured at the head that merges — the half of the SHA-stamping rule above that was missing.** That rule says carry the SHA; this one says which SHA survives. A branch head that merges is kept on `main` forever as the merge commit's second parent, and so is every commit beneath it: `git merge-base --is-ancestor b5d80d1 origin/main` (#113's merging head) and the same on `e02c4a6` (#114's) both exit 0 today. A head a later rebase replaced is kept nowhere — #113's `064f387`, #112's `714606f` and #110's `9fe7ace` each exit 1 and sit on no published ref — and that is the whole mechanism by which the 161 accumulated: a session cites an intermediate head, and a rebase throws it away. The changelog entry is written before the PR opens (`WORKFLOW.md` §7), so the head usually moves after it — a fix round, a rebase onto a merged neighbour — and when it does, every figure the entry cites is re-measured at the new head or dropped, never carried forward and never re-stamped (translating a figure across a rebase is the rebase gotcha below, and it is wrong for the reason given there). The check a reader can run once the entry has merged: `git merge-base --is-ancestor <sha> origin/main` exits 0 for every SHA it cites, read with nothing between the command and `$?`. Before the merge, the reviewer runs the same check against the branch head under review, and a rebase after that review re-runs it. The rule does not forbid citing a commit beneath the merging head — the docs commit that records a figure sits on top of the tree it measured, by construction — it forbids citing one the merging head does not descend from.

## Subagent defaults

When spawning any subagent — Agent tool calls, or `agent()` calls inside a Workflow script — explicitly set `model: "sonnet"` and `effort: "high"` by default; don't leave either unset to inherit/default silently. If a task seems to genuinely need more than `high` (`xhigh`/`max`), ask the user before using it rather than escalating on your own judgment. Dropping below `high` needs a clear reason (a trivial, low-stakes lookup, or a workflow stage explicitly designed to be cheap), not just habit.

- **A test that bets on a wall-clock window does not fail honestly — it manufactures mutation kills.** `asyncProcessRunnerCancelsRunningProcess` slept 100 ms and cancelled a `/bin/sleep 5`, which is a bet that the cancel lands inside the child's five-second life. Both resumptions that decide it sit on the main actor of an `@MainActor` suite, and a busy machine delays each independently: measured at `98c50c8` across four consecutive flagged runs with a cold build beside three of them, the gap between them was 39 ms and 48 ms on the runs that passed and **8781 ms and 14474 ms on the two that failed**. That is not a rare race, it is an ordinary one — and the failure it produces is read by `scripts/mutate` as the mutant being caught (PR #109's R9, SONNY-224). **So: never sleep-then-assert on something another task is racing you to.** Wait on a real signal the other side publishes and make the state you are asserting unable to expire on its own — the fixed test waits for a sentinel file the child writes and then `exec`s a 300 s sleep, so the window is 300 s wide instead of five and nothing but the cancel closes it early — bounded rather than eliminated, which is the wording that survives a hand-trace (PR #112 review, F7). A *hang backstop* is the one wall-clock construct that is fine, and only because it cannot be reached except by a genuine failure; a threshold the test races is not one. The population was swept rather than guessed at: `git grep -n 'Task\.sleep\|Thread\.sleep' 98c50c8 -- Tests | wc -l` → 32 sleep sites, and `git grep -n 'ContinuousClock\|DispatchTime\|timeIntervalSinceNow' 98c50c8 -- Tests | wc -l` → 17 clock reads. Of all that, the outright wall-clock *assertions* are two — `git grep -c '#expect(elapsed <' 98c50c8 -- Tests` names `LocalRedactionServiceTests` and `ShellSurfaceDetectorTests` — and the redaction one was measuring **4644 ms under an ordinary parallel suite against a 5000 ms bound**, a 7% margin. Almost everything else is a poll rather than a bet on a threshold, which is fine, but not all in the same way: the ones with a backstop are declared in `scripts/mutate-untrusted-failures` rather than trusted, and the ones with none hang instead of flaking, which cannot manufacture a kill. This sentence used to say they were all poll-with-backstop, which reads as more coverage than the file has (PR #112 review).
- **`try #require` after a count expectation, never a subscript — a trapped test costs a mutant its evidence.** `#expect` records its issue and carries on, so a subscript on the line after `#expect(xs.count == 1)` still runs; under a mutant that empties the array it traps, and the process dies. The advice is the whole of it: `try #require` throws, which ends that test instead of the process. **What it costs when you skip it** is everything the battery could have told you about that mutant. A trapped process emits no `Test … failed` line for *anything*, so `scripts/mutate` has nothing to attribute the red to and reports `KILLED — the run failed but named no test`, pointing you at the log. The mutant probably was caught — but *which* test caught it is unrecoverable from that run, and every test that had not finished when the process died went unrun as well, so one trapped subscript costs the whole mutant's evidence rather than its own. That is the part `try #require` is worth having for, and it does not go away. **The symptom used to be worse, and this line used to describe that instead** (SONNY-224): `failing_tests` piped through a `grep -v` that exits 1 on empty input, so under `pipefail` the battery died at a point that was not one of its exits with **no error above it**, three lines above the arm written to report exactly this — a killed mutant reading as the harness malfunctioning. Measured on SONNY-210: one battery aborted at its eighth mutant with nothing to explain it, and the cause was three lines away in the test. The silent death is fixed; the missing evidence is not, and cannot be. Same family as the slash-star gotcha directly above and the exit-code rule in Claims and evidence — a construct that fails in a way that looks like something else — which is why it needs writing down rather than noticing. **Fixed at 5 sites across 2 files** (`git show 81c1c5f -U0 | grep -cE '^\+.*try #require\(' | tr -d ' '` → 5), of which exactly one had ever trapped; the other four were the same shape, found by sweeping the population rather than by waiting for each to fire.
- **A rebase's conflicted-file list is not the population it can break, and `swift build` will not say so.** Rebasing `fix/containment-resolves-unwritten-paths` produced two genuine conflicts, both in `PathWhitelist.swift`, both resolved — and a *third* file broke the build having never conflicted at all (PR #111, SONNY-268). `SpokenPathTests.swift` arrived on `main` in #106, the rebasing branch had never touched it, so git merged it silently; it used the two-value `outsideWhitelist` shape that #111 had replaced with three. Two files can be individually merge-clean and jointly incoherent whenever one side changes a type's shape and the other adds a new user of it, and nothing in the conflict machinery is looking for that. **`swift build` passed**, because it does not build the test targets — so the failure surfaced only when the suite ran, which is the second thing a green `swift build` says nothing about (the first is `server/`, in the Commands section above). **So after any rebase that changed a type, an enum's associated values, or a function signature: enumerate the whole tree for the changed signature rather than reading the conflict list, then run the full flagged suite.** The conflict list tells you where git needed help, not where the code stopped agreeing with itself.
- **A rebase orphans every SHA the branch had stamped, and they all still resolve.** Same family as the one directly above — a construct that fails in a way that looks like something else — and it arrived three times in one wave, each lane hitting it alone and solving it alone, so no single session could see the repetition (PRs #108, #109, #111; SONNY-268). A rebased-away commit does not dangle: it stays in the object store, `git show` prints it, and the stamp beside a figure therefore reads as checkable while describing a tree outside the branch it now sits on. The check that tells them apart is in *Claims and evidence* above. **The rule that follows is that a number taken before a rebase is re-measured, never re-stamped**: the new base carries `main`'s own changes, so the old figure was never true of the new tree and translating the SHA attaches it to a tree it was not measured on. PR #109 found thirteen of seventeen distinct cited SHAs non-ancestral after its rebases, and restated the figures rather than mapping them. **The one case where renaming *is* right is the opposite operation and is easy to confuse with this**: a history rewrite that replaces a commit with one holding a byte-identical tree — 2026-08-24 did that to eighteen commits of `main` — is a rename of the same tree, not a restatement of a measurement, so the citation is repointed and the figure stands. `WORKFLOW.md` §8 has the map and the tree-identity check; the distinguishing question is whether the tree moved, not whether the SHA did.
- **A real-Vision fixture's recognition is not monotonic in image size, so a fixture that "works at 900 px" has established nothing** (SONNY-260). `LocalRedactionServiceTests` had two fixtures planting the same API key, one at 800 px that the recognizer missed and one at 900 px that it found, and the obvious reading — a line reaching the capture's right edge is not recognized — would have been a hole in the product's central privacy claim. It was wrong. Holding one fixture's layout and varying **only** the font size, every size from 18 pt to 30 pt finds both planted secrets over five runs each and only 32 pt misses; sweeping the width in 10 px steps instead, **800 misses, 810 finds, 820 misses, 830 and up find**. What is actually happening is character-level OCR error on an oversized synthetic fixture — a dropped leading `api`, `sk-` read as `5k-`, and at one width look-alikes from other scripts (U+0430 for `a`, U+0410 for `A`, U+043E for `o`) — and each one alone defeats an exact pattern. **So: never explain one real-Vision fixture's result by a single geometric difference from another's, and never tune a fixture's size until it passes.** Vary one axis at a time, repeat each point, and check the sweep is monotonic before believing the axis is the cause; a fixture whose passing rests on landing on the lucky side of OCR jitter reads exactly like one that passes for a reason. Two recognizer-side fixes are already measured and rejected, so re-measure before re-proposing either: `VNRecognizeTextRequest.minimumTextHeight` **defaults to 0.0** on macOS 25.5.0 and sweeping it 0.0–0.05 changes nothing, and reading deeper into Vision's ranked candidates cannot help because every observation on these fixtures returns **exactly one** candidate at confidence 1.0 — there is no second reading to consult. The corollary for tests: do not assert that a recognizer *misreads* something, or the suite breaks when Vision improves; assert what is durable and keep the readings in the record. **And keep `LocalRedactionLiveVisionTests` `@Suite(.serialized)`** (PR #113 review, F5): every test in it drives the shared on-device recognizer, and at **ten** concurrent `VNRecognizeTextRequest`s the test process stalls — re-proved at `176f186` by deleting the attribute and running that suite's filter, where the run **did not finish within 100 s** and sat at **0% CPU**, against **3.389 s** with it in place. Each case alone is fast (the seven parameterized ones pass together in 1.97 s), so it is the concurrency. It presents as a **hang, not a red test**, so in CI it arrives as a timeout with no failing assertion to point at; serializing costs about two seconds on the whole run and the suite still runs in parallel with the other 141.
- **`#expect` with `!==` on an `AnyObject`-erased existential crashes the compiler, and it kills the whole run rather than one test.** `#expect((first as AnyObject) !== (second as AnyObject))`, where `first` and `second` are `any Planning`, ends `swift test` with `fatal error encountered during compilation … While emitting reabstraction thunk` and `error: compile command failed due to signal 6` — a SILGen crash inside the macro's autoclosure, on the toolchain this repository builds with (reproduced three runs out of three on SONNY-132, in `Tests/MacAgentCoreTests/OpenAIPlannerTests.swift`). **What makes it worth writing down is the shape of the failure, not the bug**: nothing runs, so there is no failing test to point at, no test count, and the tail of the log is an LLVM stack trace rather than anything naming the line. A reader who sees it after an unrelated edit looks for a broken test and finds a compiler. **Compare identifiers instead** — `#expect(ObjectIdentifier(first as AnyObject) != ObjectIdentifier(second as AnyObject))` — which erases nothing and asserts the same thing; `===` on a *concrete* class (`selected.planner as? StubPlanner === alternatePlanner`, which this repo has always used) is unaffected. Same family as the slash-star and exit-code entries: a construct that fails in a way that looks like something else.
- **A test comparing two dates a store wrote inside the same second cannot fail, and it reads as a pass.** Every local store on the shared pattern encodes dates with `.iso8601`, which is whole-second resolution. So `#expect(after.updatedAt == before.updatedAt)` written as the run produced the two values is satisfied whether or not the code under test bumped the clock — both writes landed in one second and the store rounded them to the same instant. It has now been caught twice, in the same store: PR #105's F7 (`startedAt` across a resume) and SONNY-282's first draft of "declining does not touch `updatedAt`", found by hand-tracing the mutant before the battery ran. **So: before asserting that a stored date did *not* change, move it a measurable distance first** — back-date the record an hour and save it, then act, then compare against the back-dated value — and before asserting one *did* change, check the two are more than a second apart. A battery is the wrong place to learn this: the mutant that bumps the clock survives, and a survivor at least says so; a same-second assertion that *passes* on the mutant says nothing at all.
